# v4.2.2 — Testnet Reliability & Failure Injection Specification

## Objective
v4.2.2 is the reliability gate after v4.2.1 connector certification. It does not add trading intelligence. It proves that deterministic decision, order, reconciliation, protection, and runtime layers behave safely under infrastructure failure.

## Frozen Architecture Rules
1. A transport failure MUST NOT create a second logical order from the same OrderIntent.
2. Every submission remains correlated by deterministic client_order_id / cloid.
3. WebSocket disconnect MUST enter an explicit degraded/recovery state.
4. After reconnect, required subscriptions and authoritative account/order snapshots MUST be re-established before normal execution resumes.
5. Missed WebSocket events MUST NOT be assumed replayed; reconciliation restores authoritative state.
6. Unknown execution outcome MUST remain UNKNOWN until reconciled; it MUST NOT be treated as confirmed rejection.
7. Protection loss MUST block new risk-taking orders until protection is restored or the emergency policy executes.
8. Kill-Switch / FROZEN semantics remain authoritative over normal strategy signals.
9. Retry logic MUST be idempotent and bounded; blind retry loops are forbidden.
10. Failure handling MUST NOT modify ChanLun geometry or decision rules.

## Failure Classes
### Transport
- WebSocket disconnect
- REST timeout
- DNS/TCP/TLS failure
- HTTP 5xx
- malformed/partial response

### Exchange acknowledgement
- order accepted but acknowledgement delayed
- acknowledgement timeout with unknown server state
- explicit order rejection
- cancel acknowledgement timeout
- duplicate cloid / idempotency conflict

### Market-data integrity
- missing 1m candle
- out-of-order candle
- duplicate candle
- stale market data
- reconnect gap

### Account-state integrity
- local/exchange position mismatch
- local/open-order mismatch
- unexpected fill
- missing fill notification
- stale account snapshot

### Protection
- stop order missing
- stop order rejected
- stop replacement timeout
- reduce-only protection not confirmed

### Runtime
- process restart
- state-store recovery
- clock skew
- signer unavailable
- configuration checksum mismatch

## Recovery State Machine
NORMAL -> DEGRADED -> RECONCILING -> PROTECTED -> NORMAL

Any unresolved safety-critical condition may transition:
ANY -> FROZEN

Rules:
- DEGRADED: block new non-reduce-only exposure.
- RECONCILING: query authoritative exchange state and rebuild local state.
- PROTECTED: verify position + protection invariant before resuming.
- FROZEN: no new opening exposure; only explicitly permitted emergency/reduce-only actions.
- Recovery MUST be evented and auditable.

## Failure Injection Matrix
| Injection | Expected result |
|---|---|
| Drop WS connection during idle | reconnect + resubscribe + snapshot verification |
| Drop WS after order submission | reconcile before any retry |
| Delay order acknowledgement | order state remains UNKNOWN/PENDING; no duplicate order |
| Explicit rejection | terminal rejection recorded |
| Drop fill notification | reconciliation detects actual fill |
| Delete local open-order record | reconciliation reconstructs state |
| Remove protection order | PROTECTION_LOST / recovery path |
| Lose two 1m bars | DATA_GAP safety path |
| Restart runtime | deterministic state restoration |
| Signer unavailable | no order submission; safety state preserved |
| Clock skew | signed-action preflight failure / recovery |
| Duplicate execution callback | idempotent event handling |
| REST timeout | bounded retry + authoritative reconciliation |
| Rate-limit response | backoff/throttle; no retry storm |

## External Protocol Constraints
Hyperliquid documentation describes aggregate REST request weights, WebSocket connection and subscription limits, message throughput and simultaneous in-flight POST limits. These are external protocol constraints, not strategy parameters.
The testnet uses separate API/WebSocket endpoints, and reconnect handling must restore subscriptions and refresh authoritative snapshots because streamed events can be missed during disconnects.

## Deterministic Acceptance Invariants
### I1 — No Duplicate Logical Order
For one logical intent and cloid, at most one live exposure-producing order may exist unless an explicit replacement transition is recorded.

### I2 — Unknown Means Unknown
An acknowledgement timeout cannot be converted into REJECTED by timeout alone.

### I3 — Protection Before Exposure
No new exposure may be opened while the required protection invariant is false.

### I4 — Reconciliation Is Authoritative
When local and exchange state diverge, exchange-authoritative state plus the event ledger determines recovery.

### I5 — Strategy Isolation
Injected execution/data failures cannot alter ChanLun structural state except through explicitly defined data-integrity state transitions.

### I6 — Replayability
Every failure injection and recovery transition must be representable as deterministic events suitable for replay.

## Tunable Parameters
These belong in configuration, not architecture:
- reconnect backoff bounds
- request timeout
- maximum retry count
- reconciliation polling interval
- data-gap threshold
- protection-recovery timeout
- circuit-breaker cooldown
- rate-limit backoff policy

Exact values are deployment parameters and must not redefine safety invariants.

## Exit Criteria
1. All mandatory failure classes have deterministic test cases.
2. No injected failure creates duplicate exposure.
3. Unknown outcomes are reconciled correctly.
4. Protection loss reliably prevents unsafe new exposure.
5. Runtime restart restores canonical state.
6. Recovery transitions emit auditable events.
7. Test results are reproducible from recorded event streams.
8. v4.2.1 connector certification remains green after reliability testing.

## Scope Boundary
v4.2.2 does not change ChanLun definitions, BUY/HOLD/SELL gates, strategy parameters, LLM decision authority, or production-capital authorization. It is a reliability and failure-injection gate only.
