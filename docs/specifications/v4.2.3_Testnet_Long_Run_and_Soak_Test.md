# v4.2.3 — Testnet Long-Run & Soak Test Specification

## 1. Objective

v4.2.3 validates that the v4.2.1 connector and v4.2.2 failure-recovery layer remain stable during prolonged continuous operation.

It is a runtime reliability gate, not a strategy-development phase.

## 2. Scope

The soak environment must exercise, over repeated long-running sessions:

- 1-minute market-data ingestion
- ChanLun live-state updates
- deterministic decision evaluation
- OrderIntent generation
- testnet order lifecycle
- fills and partial fills where available
- stop/protection lifecycle
- reconciliation
- event persistence
- state restoration
- WebSocket reconnect
- REST recovery
- signer availability transitions
- kill-switch / FROZEN transitions

## 3. Required Test Modes

### Mode A — Clean Soak

Continuous operation with no injected faults.

Purpose:
- establish baseline latency;
- detect resource growth;
- detect state drift;
- verify event continuity.

### Mode B — Reconnect Soak

Repeated controlled WebSocket disconnect/reconnect cycles.

Acceptance:
- subscriptions restored;
- authoritative snapshots restored;
- no duplicate logical orders;
- no silent event gap;
- runtime returns to the correct recovery state.

### Mode C — Runtime Restart Soak

Repeated controlled process restarts.

Acceptance:
- state store loads successfully;
- open positions/orders are reconstructed;
- protection status is reconstructed;
- replayed state matches authoritative state;
- no duplicate exposure after restart.

### Mode D — Order-Lifecycle Soak

Repeated testnet order creation, cancellation, fill and reconciliation cycles.

Acceptance:
- every lifecycle transition is represented in the event ledger;
- duplicate callbacks are idempotent;
- unknown outcomes converge through reconciliation;
- local and exchange state remain convergent.

### Mode E — Fault-Injection Soak

Combine v4.2.2 failures during long-running operation:
- transport interruption;
- acknowledgement delay;
- fill-notification loss;
- data gaps;
- signer unavailable;
- rate limiting;
- runtime restart;
- protection loss.

Acceptance:
- no safety invariant is violated;
- recovery converges;
- FROZEN conditions do not silently return to NORMAL.

## 4. State-Consistency Invariants

### S1 — Position Conservation
Local canonical position must reconcile to the authoritative exchange position after each recovery cycle.

### S2 — Order Conservation
Every exchange-live order must have a corresponding local lifecycle record.

### S3 — Fill Conservation
Every observed fill must be represented exactly once in the canonical event ledger.

### S4 — Protection Conservation
Every protected position must have the required protection state recorded and verifiable.

### S5 — Event Monotonicity
Event sequence/cursor handling must not move backwards.

### S6 — Replay Equivalence
A recorded session replay must reconstruct the same canonical state and terminal lifecycle outcomes.

### S7 — Idempotence
Reprocessing the same external event must not create a second position, fill, order or ledger entry.

## 5. Resource-Stability Checks

Track throughout the soak:

- process memory;
- CPU;
- event-store growth;
- open WebSocket connections;
- subscription count;
- pending REST requests;
- pending order intents;
- pending reconciliation jobs;
- signer queue depth;
- event-processing latency;
- market-data lag;
- reconciliation latency.

The test must distinguish:
- expected monotonic data growth;
- bounded operational queues;
- abnormal memory/resource growth.

## 6. Time & Clock Checks

The runtime must record:

- exchange event timestamp;
- local receive timestamp;
- local processing timestamp;
- order submission timestamp;
- acknowledgement timestamp;
- fill timestamp.

Clock anomalies must be observable and must not silently corrupt ordering or replay semantics.

## 7. Soak Metrics

Minimum metrics:

- uptime;
- reconnect count;
- recovery success rate;
- recovery duration;
- reconciliation count;
- reconciliation divergence count;
- duplicate-event count;
- unknown-order count;
- protection-loss count;
- DATA_GAP count;
- FROZEN transitions;
- event-processing latency;
- order lifecycle latency;
- state-replay checksum/equivalence result.

## 8. Exit Criteria

v4.2.3 passes only if:

1. The planned soak duration completes without an unrecovered safety-critical fault.
2. No duplicate exposure is created.
3. No fill is double-counted.
4. No unexplained local/exchange position divergence remains.
5. All reconnect cycles converge.
6. Runtime restart cycles converge.
7. Replay reconstructs the recorded canonical state.
8. Resource usage remains within configured operational bounds.
9. Protection invariants remain valid whenever exposure exists.
10. All FROZEN states require an explicit recovery transition.
11. v4.2.2 failure-injection tests remain green.
12. The final evidence bundle is reproducible from recorded events and test configuration.

## 9. Evidence Bundle

Each soak run must produce:

- run manifest;
- configuration checksum;
- software build/version;
- event-stream archive;
- order/fill ledger;
- reconciliation reports;
- recovery timeline;
- resource metrics;
- failure-injection schedule;
- final canonical-state snapshot;
- replay verification result;
- pass/fail report.

## 10. Non-Goals

v4.2.3 does not:
- optimize trading performance;
- alter ChanLun geometry;
- alter BUY/HOLD/SELL logic;
- introduce new strategy signals;
- authorize production capital;
- weaken FROZEN or kill-switch behavior.

## 11. Promotion Gate

Only after v4.2.3 passes should the project promote the execution stack to the next production-signing architecture stage.

The next stage is v4.3.0 — MPC Production Signing Gateway.
