# v4.3.0 — MPC Production Signing Gateway Architecture

## Objective
v4.3.0 promotes the v3.4.6 MPC Wallet & Signing Gateway design into a production-grade signing boundary.

The production architecture separates Trading Agent, ChanLun Decision Engine, Risk/Capital Guard, Signing Policy Engine, MPC Signing Gateway, Exchange Gateway, and exchange account state.

The Trading Agent never receives or reconstructs production private key material.

## Trust Boundaries
Trading Agent:
- produces deterministic OrderIntent;
- has no signing secret;
- cannot bypass Risk.

Risk / Capital Guard:
- validates exposure, leverage, notional, reduce-only status, protection state and account limits;
- produces signed-action authorization;
- cannot access private key shares.

Signing Policy Engine:
- verifies exact action against authorization;
- enforces account, asset, action type, side, size, price, reduce-only, nonce and expiry constraints;
- rejects policy mismatch before MPC signing.

MPC Gateway:
- performs distributed signing only after policy authorization;
- does not decide whether a trade is strategically desirable;
- does not modify the payload;
- emits signing audit events.

Exchange Gateway:
- submits the exact signed payload;
- records acknowledgement, rejection or unknown state;
- performs reconciliation.

## Hyperliquid Identity Model
Hyperliquid API wallets (agent wallets) sign on behalf of a master account or sub-account. Account queries must use the actual account address rather than the agent signer address. Nonces are tracked per signer, so signer separation is a deliberate architecture boundary. 

For vaults/subaccounts, exchange actions are signed by the master account and may include vaultAddress where applicable.

Production implementation must maintain separate identities:
- account_owner_address
- trading_account_address
- signer_address
- MPC keyset identifier

These identifiers must never be implicitly substituted for one another.

## Signing Pipeline
Signal -> Decision -> RiskApproval -> OrderIntent -> ActionBuilder -> SigningPolicyCheck -> MPC Sign -> Signature Verification -> Exchange Submit -> Exchange Ack -> Reconciliation

Any failed stage blocks downstream submission.

## Authorization Contract
Every signing request must contain:
- request_id
- intent_id
- account_owner
- trading_account
- signer_id / keyset_id
- exchange
- action_type
- asset
- side
- size
- price / trigger price where applicable
- reduce_only
- order_type
- tif
- cloid
- nonce
- expires_after
- risk_decision_id
- protection_state
- configuration_hash
- payload_hash

The MPC signer signs only the exact canonical payload whose hash matches the authorization.

## Production Signing Policy
The policy engine must enforce:
- allowlisted account addresses;
- allowlisted assets;
- separately allowlisted trading actions;
- per-order, per-symbol, per-session and per-day size limits;
- leverage ceilings;
- separate reduce-only policy;
- bounded validity windows where supported;
- atomic nonce allocation;
- configuration checksum binding.

## Critical Prohibition
The MPC Gateway must not accept a free-form transaction payload from an LLM, UI, strategy process or arbitrary caller.

Only a canonical, policy-approved SigningRequest is eligible for signing.

## MPC Key Architecture
Logical keyset:
- Share A — secure signer environment
- Share B — independent signer environment
- Share C — recovery/governance environment

Exact threshold and physical deployment are deployment parameters. No single application process may possess enough key material to reconstruct the production private key.

## Agent/API Wallet Boundary
Where Hyperliquid API wallets are used, the API wallet is treated as a constrained execution signer, not the account identity.

API-wallet registration, replacement and revocation are privileged lifecycle operations and must not be executable by the ordinary trading loop.

Separate API wallets should be used for separate trading processes where nonce isolation is required.

## Nonce Service
The Nonce Service must:
- allocate unique nonces per signer;
- persist allocation state;
- survive runtime restart;
- detect nonce reuse;
- detect nonce-window violations;
- serialize competing signing requests where required;
- expose nonce allocation events for replay.

A stale or conflicting nonce must fail closed.

## Payload Canonicalization
Before signing:
1. Build canonical action.
2. Normalize address representation.
3. Normalize numeric representation.
4. Serialize using the exchange-required signing format.
5. Compute payload hash.
6. Compare hash with RiskApproval.
7. Sign only after equality.
8. Verify recovered signer/signature validity where supported.
9. Submit the exact signed payload.

Hyperliquid documentation warns that field ordering, number formatting, address normalization and signing-scheme differences can invalidate signatures. Existing SDK signing implementations should therefore be preferred over custom cryptographic serialization.

## Emergency Controls
The production signing gateway must support:
- global kill switch;
- account-level freeze;
- signer-level disable;
- asset-level disable;
- reduce-only mode;
- withdrawal prohibition;
- API-wallet revocation workflow;
- emergency keyset rotation.

Emergency actions must be separately audited.

## Withdrawal / Transfer Separation
Trading authorization must not imply withdrawal or fund-transfer authorization.

The production trading signer/policy must reject arbitrary USDC transfers, vault withdrawals, administrative approvals, builder permission changes, and agent registration/replacement unless handled by a separate privileged workflow.

## Audit Events
Minimum events:
- SIGN_REQUEST_CREATED
- SIGN_POLICY_APPROVED
- SIGN_POLICY_REJECTED
- MPC_SESSION_STARTED
- MPC_SESSION_COMPLETED
- MPC_SESSION_FAILED
- SIGNATURE_VERIFIED
- SIGNATURE_REJECTED
- EXCHANGE_SUBMIT
- EXCHANGE_ACK
- EXCHANGE_UNKNOWN
- NONCE_ALLOCATED
- NONCE_CONFLICT
- SIGNER_DISABLED
- ACCOUNT_FROZEN
- KILL_SWITCH_TRIGGERED
- KEYSET_ROTATION_STARTED
- KEYSET_ROTATION_COMPLETED

## Deterministic Replay
Replay must verify:
RiskApproval.payload_hash == SigningRequest.payload_hash == SubmittedPayload.hash

Replay verifies authorization and payload integrity without exposing private key shares.

## Failure Behavior
If MPC is unavailable:
- no new exposure;
- preserve existing protection;
- remain reconcilable.

If policy service is unavailable:
- no new signing;
- reduce-only emergency path only if separately authorized.

If nonce service is unavailable:
- no new signed action.

If signature verification fails:
- no submission;
- emit SIGNATURE_REJECTED;
- enter recovery/investigation state.

If exchange acknowledgement is unknown:
- do not blind retry;
- reconcile first.

## Exit Criteria
v4.3.0 is complete only when:
1. Production key material is inaccessible to the Trading Agent.
2. Every signed action is policy-authorized.
3. Payload hash is bound across Risk -> MPC -> Exchange.
4. Nonce allocation is persistent and collision-safe.
5. Trading permissions cannot be used as withdrawal permissions.
6. Signer failure fails closed.
7. Emergency freeze is independently testable.
8. MPC signing events are auditable and replayable.
9. v4.2.2 and v4.2.3 reliability suites remain green.
10. Testnet and production configuration are cryptographically distinguishable.

## Scope Boundary
v4.3.0 does not change ChanLun geometry, BUY/HOLD/SELL decision logic, position-sizing formulas, or stop-anchor semantics. It establishes the production cryptographic execution boundary.
