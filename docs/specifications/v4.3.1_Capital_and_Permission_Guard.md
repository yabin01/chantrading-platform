# v4.3.1 — Capital & Permission Guard Specification

## 1. Objective

v4.3.1 establishes an independent capital and permission firewall between Risk-approved OrderIntent and the production MPC Signing Gateway.

It controls how much risk the system may create, how much capital may be exposed, and which classes of exchange actions the trading runtime is allowed to request.

It does not generate trading signals and does not modify ChanLun geometry.

## 2. Architecture

Trading Agent
-> Decision Engine
-> Risk Engine
-> Capital Guard
-> Permission Guard
-> Signing Policy
-> MPC
-> Exchange Gateway
-> Reconciliation

Capital Guard answers:
"Is this amount of exposure permitted?"

Permission Guard answers:
"Is this class of action permitted at all?"

Both must approve before production signing.

## 3. Capital Domains

The guard must maintain separate limits for:

- total account equity;
- available margin;
- total open notional;
- symbol notional;
- gross exposure;
- net exposure;
- initial margin usage;
- maintenance-margin buffer;
- leverage;
- per-order notional;
- session notional;
- daily notional;
- daily realized loss;
- daily realized + unrealized loss;
- consecutive-loss circuit breaker;
- protection coverage.

Hyperliquid documents that cross margin shares collateral across cross positions, while isolated margin constrains collateral to the isolated position. Initial margin depends on position size, mark price and leverage; liquidation depends on maintenance margin and open notional. These exchange calculations are external constraints and must be treated as authoritative rather than reimplemented as an independent liquidation truth. citeturn0search0

## 4. Hard Limits

Hard limits are non-bypassable.

Examples:
- maximum account exposure;
- maximum symbol exposure;
- maximum leverage;
- maximum order notional;
- maximum daily loss;
- minimum maintenance-margin buffer;
- maximum number of simultaneous positions;
- maximum number of pending opening orders.

A hard-limit violation produces DENY.

No strategy signal can override a hard limit.

## 5. Soft Limits

Soft limits may trigger:
- warning;
- size reduction;
- entry throttling;
- reduce-only mode;
- temporary cooldown.

Soft limits must never weaken a hard limit.

## 6. Risk State Machine

NORMAL
-> WARNING
-> RESTRICTED
-> REDUCE_ONLY
-> FROZEN

Recovery may occur only through explicit, auditable transitions.

Definitions:

NORMAL:
- normal opening and closing actions permitted within limits.

WARNING:
- exposure approaching configured thresholds.

RESTRICTED:
- new exposure is size-limited or selectively blocked.

REDUCE_ONLY:
- opening exposure prohibited;
- reduce-only orders permitted if independently authorized.

FROZEN:
- no new trading exposure;
- only explicitly permitted emergency actions.

## 7. Capital Reservation

Before signing an opening order, the system must reserve the incremental capital/risk budget represented by the OrderIntent.

Reservation lifecycle:

PROPOSED
-> RESERVED
-> SIGNED
-> SUBMITTED
-> LIVE / FILLED
or
-> RELEASED / EXPIRED / REJECTED

A failed or expired intent must release its reservation exactly once.

This prevents concurrent orders from individually passing limits while collectively exceeding the account budget.

## 8. Position-Aware Sizing Gate

The final order size must be checked against:

current exposure
+ pending reserved exposure
+ proposed incremental exposure

The guard must use authoritative exchange position/order state after reconciliation.

## 9. Leverage Guard

The guard must check:
- configured strategy leverage ceiling;
- exchange-supported leverage;
- resulting effective leverage;
- margin availability;
- maintenance-margin buffer.

Hyperliquid states that leverage can be selected within the asset's maximum leverage and that leverage is checked when opening a position; ongoing monitoring remains the user's responsibility to avoid liquidation. citeturn0search0

Therefore the Agent must maintain a stricter internal buffer rather than relying solely on the exchange's maximum leverage.

## 10. Loss Guard

The system must calculate and track:

- session realized PnL;
- daily realized PnL;
- daily unrealized PnL;
- combined daily loss;
- drawdown from session high-water mark;
- consecutive losing trades.

Configured thresholds may trigger:
- WARNING;
- RESTRICTED;
- REDUCE_ONLY;
- FROZEN.

The exact thresholds are deployment parameters, not ChanLun rules.

## 11. Permission Classes

Exchange actions must be explicitly classified.

### Trading
- place order;
- cancel order;
- modify order;
- reduce-only order.

### Risk / Position Management
- update leverage;
- isolated-margin modification;
- emergency close.

### Funds
- USDC transfer;
- spot transfer;
- vault transfer;
- withdrawal-related actions.

### Administration
- API wallet approval;
- API wallet replacement/revocation;
- configuration/permission changes.

The ordinary trading runtime must be allowlisted only for the minimum trading actions required.

Hyperliquid's exchange API exposes distinct actions for orders, leverage, isolated margin, USDC transfers, vault transfers and API-wallet approval. These must therefore remain separate permission classes in our architecture. citeturn0search1

## 12. Withdrawal Firewall

The trading runtime MUST NOT possess withdrawal authority.

The Permission Guard must reject:
- arbitrary USDC transfers;
- spot asset transfers;
- vault withdrawals;
- API-wallet approval/replacement;
- administrative permission changes.

These operations require a separate privileged workflow and separate signing policy.

## 13. API Wallet Isolation

An API wallet is treated as an execution signer, not as the account identity.

Account data must be resolved against the master/sub-account address.

Signer identity and account identity must be stored separately.

Hyperliquid documents that API-wallet nonce state is signer-specific and can be pruned when an agent is deregistered or expires. Therefore production agent-wallet rotation must use explicit lifecycle tracking and must not casually reuse retired signer addresses. citeturn0search2

## 14. Daily Budget

At the start of a risk day:

- establish daily loss baseline;
- establish notional budget;
- establish order-count budget;
- establish maximum exposure budget.

The daily budget must be persisted and survive runtime restart.

A restart MUST NOT reset loss counters or capital reservations.

## 15. Kill Switch

Triggers include:
- daily hard loss exceeded;
- maintenance-margin buffer breached;
- exchange/account divergence;
- protection loss;
- repeated signing failure;
- repeated reconciliation failure;
- unexpected withdrawal-capable action request;
- configuration checksum mismatch;
- manual emergency trigger.

Kill switch result:
- freeze new exposure;
- cancel permitted opening orders where safe;
- preserve/restore protection;
- enter FROZEN;
- emit auditable event.

## 16. Deterministic Guard Decision

Every guard decision must produce:

- guard_decision_id;
- request_id;
- account_state_hash;
- risk_state;
- current_exposure;
- reserved_exposure;
- proposed_exposure;
- applicable_limits;
- violations;
- resulting_state;
- decision = ALLOW / REDUCE / DENY / FREEZE;
- configuration_hash;
- timestamp;
- reason_codes.

The decision must be replayable from the recorded state and configuration.

## 18. Invariants

I1 — No OrderIntent can bypass Capital Guard.

I2 — No Capital Guard approval can bypass Permission Guard.

I3 — Reservations cannot exceed hard limits.

I4 — Restart cannot reset loss or exposure state.

I5 — Trading permission cannot imply withdrawal permission.

I6 — FROZEN cannot be cleared by a strategy signal.

I7 — Exchange-authoritative account state wins after reconciliation.

I8 — Guard decisions are deterministic for identical state, configuration and request.

I9 — Reduce-only emergency actions cannot silently become opening orders.

## 19. Exit Criteria

v4.3.1 passes only when:

1. Concurrent intents cannot exceed capital limits.
2. Daily-loss limits survive restart.
3. Leverage and margin-buffer checks are enforced.
4. FROZEN and REDUCE_ONLY states are deterministic.
5. Withdrawal/transfer actions are blocked from the trading runtime.
6. API-wallet and account identities remain separated.
7. All guard decisions are auditable and replayable.
8. v4.2.2 and v4.2.3 reliability suites remain green.
9. v4.3.0 signing policy cannot be bypassed through the guard.
10. No production-capital action is possible without the complete approval chain.

## 20. Scope Boundary

v4.3.1 does not change:
- ChanLun geometry;
- fractal/bi/segment rules;
- divergence rules;
- BUY/HOLD/SELL gates;
- stop-anchor semantics.

It is a capital and permission firewall only.
