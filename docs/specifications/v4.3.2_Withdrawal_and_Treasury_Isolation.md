# v4.3.2 — Withdrawal & Treasury Isolation Architecture

## 1. Objective

v4.3.2 creates a hard security boundary between trading execution capital and treasury / withdrawal authority.

The trading runtime is designed to trade, not to move funds out of the controlled trading domain.

## 2. Trust Domains

### Domain A — Trading Runtime
Contains:
- ChanLun Agent
- Decision Engine
- Risk Engine
- Capital Guard
- Permission Guard
- Exchange Gateway
- Trading API Wallet / constrained signer

Allowed:
- open positions within limits;
- close positions;
- cancel orders;
- reduce-only emergency actions.

Forbidden:
- arbitrary transfers;
- withdrawals;
- treasury reallocation;
- API-wallet administration.

### Domain B — Treasury
Contains:
- treasury policy;
- withdrawal workflow;
- treasury MPC keyset;
- withdrawal approval service;
- treasury audit ledger.

Allowed:
- approved capital movements;
- approved withdrawals;
- treasury rebalancing.

Not callable by the ordinary trading loop.

### Domain C — Governance / Recovery
Contains:
- key rotation;
- emergency recovery;
- signer revocation;
- policy changes;
- break-glass procedures.

This domain requires a separate privileged workflow.

## 3. Core Principle

Trading permission MUST NOT imply fund-transfer permission.

A valid trading signature must never be reusable as a treasury signature.

A trading API wallet must not be granted withdrawal authority.

Hyperliquid documentation distinguishes agent/API-wallet roles from the master account and supports separate account/vault/sub-account operations; the architecture therefore treats signer identity, account identity and treasury authority as separate principals. citeturn0search0turn0search3

## 4. Wallet Topology

Recommended logical topology:

Treasury / Cold Reserve
        |
        | approved capital allocation
        v
Trading Capital Account
        |
        +--> Trading API Wallet
        |
        +--> MPC Trading Signer
        |
        +--> Exchange Gateway

The trading account contains only the capital allocated to the strategy.

Treasury funds remain outside the ordinary trading runtime.

## 5. Capital Allocation

Treasury -> Trading Account is an explicit capital-allocation action.

It must contain:
- allocation_id;
- source account;
- destination account;
- amount;
- asset;
- reason;
- expiry;
- approvers;
- policy hash;
- execution status.

The trading Agent cannot originate this action.

## 6. Withdrawal Workflow

Withdrawal requires a dedicated state machine:

REQUESTED
-> POLICY_CHECK
-> RISK_CHECK
-> HUMAN / GOVERNANCE_APPROVAL
-> MPC_TREASURY_SIGN
-> EXCHANGE_SUBMIT
-> CONFIRMED
or
-> REJECTED / CANCELLED

No ordinary trading OrderIntent can enter this state machine.

## 7. Withdrawal Policy

The Treasury Guard must enforce:

- destination allowlist;
- asset allowlist;
- maximum single withdrawal;
- daily withdrawal limit;
- rolling-period limit;
- cooldown for new destinations;
- approval threshold;
- dual-control requirement;
- emergency freeze;
- configuration checksum;
- reason / ticket reference.

A newly introduced destination must never inherit the permissions of an existing destination automatically.

## 8. Destination Allowlist

Each approved destination must have:

- destination_address;
- chain/network;
- asset;
- owner/label;
- creation timestamp;
- approval record;
- activation delay;
- status.

Destination changes are privileged operations.

## 9. Hyperliquid Action Separation

Hyperliquid exposes distinct mechanisms for trading, USDC transfers, vault transfers, sub-account transfers and withdrawals. The treasury architecture must therefore map each action to an explicit permission class rather than treating all signed exchange actions as equivalent. citeturn0search1turn0search2

For vaults and sub-accounts, the address used for trading and the transfer destination/source must be explicitly bound in the authorization. citeturn0search3

## 10. Trading Wallet Limits

The trading account should be treated as a bounded operational wallet.

Controls:
- maximum balance;
- maximum open notional;
- maximum daily loss;
- maximum withdrawal = 0 for trading runtime;
- maximum transfer authority = 0 for trading runtime;
- automatic treasury top-up disabled by default.

This limits the blast radius of a compromised trading process.

## 11. Treasury MPC

Treasury MPC MUST use a separate keyset from trading MPC.

Example logical separation:

Trading Keyset:
- K_T

Treasury Keyset:
- K_R

Recovery/Governance:
- K_G

No production service may possess enough shares to reconstruct another domain's key.

## 12. Dual Control

Treasury withdrawals require at least two independent approval factors according to deployment policy.

Examples:
- two authorized human approvals;
- governance approval + treasury operator;
- policy engine + independent human confirmation.

The exact threshold is deployment configuration, but single-process withdrawal authorization is prohibited.

## 13. Cooldown

High-risk treasury operations should support an activation/cooldown window before signing.

During cooldown:
- request can be reviewed;
- destination can be revoked;
- governance can freeze;
- policy changes can invalidate the request.

Emergency break-glass is separately audited.

## 14. Break-Glass

Break-glass may be used for:
- compromised signer;
- compromised trading account;
- urgent fund recovery;
- key rotation.

Break-glass does not mean unrestricted automation.

It requires:
- explicit privileged invocation;
- independent authentication;
- reason;
- incident ID;
- audit trail;
- post-incident review.

## 15. Treasury Reconciliation

Treasury state must reconcile:

internal treasury ledger
+
approved allocation ledger
+
exchange balances
+
pending withdrawals
+
confirmed transfers

A discrepancy must trigger TREASURY_RECONCILIATION_REQUIRED and block new treasury actions until resolved.

## 17. Deterministic Authorization

Every treasury action must bind:

action_hash
+
source_account
+
destination
+
asset
+
amount
+
policy_hash
+
approval_set
+
keyset_id
+
nonce
+
expiry

Any mismatch invalidates the authorization.

## 18. Failure Rules

If treasury policy is unavailable:
- no new treasury signing.

If approval service is unavailable:
- no new treasury signing.

If destination validation fails:
- DENY.

If exchange acknowledgement is unknown:
- do not blind retry;
- reconcile.

If treasury reconciliation diverges:
- freeze treasury actions.

If trading runtime requests a treasury action:
- DENY;
- emit PERMISSION_BOUNDARY_VIOLATION.

## 19. Security Invariants

I1 — Trading runtime cannot withdraw.

I2 — Trading signer cannot sign treasury actions.

I3 — Treasury signer cannot be invoked by ordinary trading code.

I4 — A destination change cannot become active without its approval workflow.

I5 — Treasury withdrawal requires explicit authorization.

I6 — Trading account balance is bounded independently from treasury balance.

I7 — Treasury state divergence freezes treasury actions.

I8 — Keysets are domain-separated.

I9 — Break-glass actions are separately audited.

## 20. Exit Criteria

v4.3.2 passes only when:

1. A compromised trading runtime cannot originate a withdrawal.
2. Trading and treasury MPC keysets are cryptographically and operationally separated.
3. Treasury destinations are allowlisted and controlled.
4. Withdrawal limits and cooldowns are enforced.
5. Single-process treasury authorization is impossible.
6. Treasury reconciliation is deterministic.
7. Trading-to-treasury permission-boundary violations are detected and audited.
8. v4.3.0 and v4.3.1 remain green.
9. Recovery and break-glass workflows are tested.
10. No ordinary OrderIntent can reach the treasury signing path.

## 21. Scope Boundary

v4.3.2 does not change ChanLun decisions, trading risk formulas or execution strategy.

It establishes the treasury trust boundary and withdrawal firewall.
