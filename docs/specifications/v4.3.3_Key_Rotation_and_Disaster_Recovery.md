# v4.3.3 — Key Rotation & Disaster Recovery Specification

## 1. Objective

v4.3.3 defines production procedures for key-share loss, signer compromise, key refresh, keyset rotation, API-wallet revocation, disaster recovery and post-recovery verification.

It distinguishes:
- key-share refresh while preserving account identity;
- keyset replacement that changes signing authority;
- API-wallet revocation/replacement;
- operational recovery;
- asset migration when cryptographic identity cannot be safely recovered.

No recovery workflow may silently restore production signing authority.

## 2. Recovery Principles

1. Never reconstruct the full production private key as a recovery shortcut.
2. Recovery authority is separate from ordinary trading authority.
3. A recovered system starts in FROZEN state.
4. Signing remains disabled until identity, state, policy and protection are verified.
5. Old key material is treated as compromised when compromise cannot be ruled out.
6. Every rotation creates an auditable epoch transition.
7. Recovery must be tested in an isolated environment before production use.
8. Recovery must not reset capital, PnL, nonce, order or risk state.
9. Treasury and trading keysets remain domain-separated.
10. Break-glass recovery is an incident workflow, not an ordinary API.

MPC/TSS resharing can refresh key shares while preserving the underlying cryptographic identity and can invalidate previously held shares without reconstructing the private key. This is materially different from changing the wallet identity or migrating assets. citeturn0search0turn0search1

PROVISIONING
-> ACTIVE
-> REFRESHING
-> ACTIVE

or:

ACTIVE
-> ROTATION_REQUIRED
-> ROTATING
-> VERIFIED
-> ACTIVE

Compromise path:

ACTIVE
-> COMPROMISED_SUSPECTED
-> FROZEN
-> REVOKED / ROTATED
-> VERIFIED
-> ACTIVE

Terminal path:

ACTIVE
-> RETIRED

## 4. Refresh vs Rotation vs Migration

### Key Share Refresh
Purpose:
- reduce long-term share exposure;
- preserve the same cryptographic identity where supported.

The public identity remains unchanged while share material is refreshed.

### Keyset Rotation
Purpose:
- replace the active signer set;
- respond to participant/device compromise;
- change quorum composition.

The resulting identity may remain the same or change depending on the cryptographic mechanism and exchange registration model.

### API Wallet Replacement
Purpose:
- revoke a compromised or retired exchange signer;
- create and register a replacement signer.

This is an exchange/account lifecycle operation, not merely a local MPC refresh.

### Asset / Account Migration
Purpose:
- move capital to a new cryptographic identity when the old identity cannot be safely trusted.

This is the highest-impact recovery path and requires an explicit migration plan.

## 5. Epoch Model

Every keyset has:

- keyset_id
- epoch
- threshold
- participant_set
- public_key / signer_address
- creation_time
- activation_time
- retirement_time
- policy_hash
- registration_status
- recovery_status

Every signed action records the active keyset_id and epoch.

Old epochs cannot sign new production actions after retirement.

## 6. Share Refresh Procedure

1. Freeze or enter controlled maintenance mode according to operational policy.
2. Confirm current signer quorum and participant health.
3. Start a new refresh session.
4. Generate refreshed shares without reconstructing the private key.
5. Verify public identity remains unchanged where refresh semantics require it.
6. Persist new epoch metadata.
7. Invalidate old share material according to secure-destruction policy.
8. Run signing verification in a non-production or constrained test path.
9. Re-enable signing only after verification.

Resharing can put a quorum into maintenance mode and should therefore be scheduled deliberately; backup material must be regenerated after a reshare because prior backups may no longer match the active share set. citeturn0search2

## 7. Compromised Share Procedure

If one share is suspected compromised:

1. Enter risk assessment.
2. Freeze affected signing path if required by threshold/security policy.
3. Determine whether the remaining quorum is trustworthy.
4. Initiate emergency refresh/reshare.
5. Remove the compromised participant/device.
6. Rotate credentials and access paths associated with the participant.
7. Verify the new quorum.
8. Audit all actions signed during the suspected compromise window.
9. Restore NORMAL only after independent verification.

If the compromise threshold may have been reached, assume signing authority is compromised and proceed to full keyset replacement or identity migration.

## 8. Lost Share / Unavailable Participant

A lost share does not automatically mean key compromise.

The system must distinguish:
- unavailable;
- irrecoverably lost;
- suspected compromised.

If the remaining quorum can safely satisfy the threshold, controlled operation may continue only according to policy.

Otherwise:
- enter FROZEN;
- initiate quorum restructuring/recovery;
- verify the new signer set;
- re-enable only after acceptance tests.

Threshold designs such as 2-of-3 allow continued signing when one participant is unavailable, but the exact threshold is a deployment parameter and must be validated against the production threat model. citeturn0search1

## 9. Disaster Recovery Procedure

### Phase 1 — Detect
- identify failure;
- classify severity;
- open incident;
- freeze affected actions.

### Phase 2 — Contain
- disable compromised signer/device;
- revoke affected credentials;
- block new exposure where required;
- preserve evidence.

### Phase 3 — Reconstruct Control Plane
Restore:
- configuration;
- policy;
- event store;
- nonce state;
- order ledger;
- position state;
- protection state;
- keyset metadata.

### Phase 4 — Verify
Compare:
- exchange account state;
- local canonical state;
- event ledger;
- risk state;
- capital reservations;
- open orders;
- protection.

### Phase 5 — Restore Signing
Only after:
- signer quorum verified;
- policy verified;
- configuration checksum verified;
- account identity verified;
- protection verified;
- nonce state verified.

Start in constrained / canary mode.

## 10. Recovery State Machine

NORMAL
-> INCIDENT
-> FROZEN
-> RECOVERY
-> RECONCILING
-> VERIFIED
-> CANARY
-> NORMAL

Any verification failure returns to FROZEN.

No direct:

FROZEN -> NORMAL

transition is permitted.

## 11. API Wallet Revocation

For exchange API wallets:

1. Identify signer address.
2. Freeze dependent trading runtime.
3. Stop new signed actions.
4. Reconcile all outstanding orders and positions.
5. Revoke/remove the compromised or retired signer using the exchange-supported lifecycle.
6. Create replacement signer.
7. Register replacement through privileged workflow.
8. Verify nonce and account authorization.
9. Run constrained testnet/canary signing.
10. Resume only after acceptance.

The API wallet must be treated as a lifecycle-managed signer, not as a permanent account identity.

## 12. Nonce Recovery

Recovery must preserve:

- signer identity;
- nonce allocation history;
- pending signing requests;
- submitted-but-unknown requests.

Never reset nonce state merely because the runtime was restored.

If nonce state is uncertain:
- stop signing;
- reconcile with authoritative exchange state;
- establish a new valid nonce baseline;
- record the recovery decision.

## 13. State Recovery

The recovery system must restore, at minimum:

- canonical ChanLun state;
- position;
- open orders;
- fills;
- protection orders;
- capital reservations;
- PnL baseline;
- risk state;
- daily loss state;
- signer/keyset state;
- event cursor;
- configuration hash.

Recovery must not create synthetic fills or positions to make local state appear consistent.

## 14. Backup Policy

Backups must be domain-separated.

Backup categories:
- control-plane configuration;
- event/state data;
- key-management metadata;
- recovery authorization metadata.

Private key shares must never be assembled into a single backup file.

After a share refresh/reshare, stale backups must be invalidated and new recovery material generated according to the active keyset. citeturn0search2

## 15. RTO / RPO

Deployment must define:

- maximum acceptable signing outage;
- maximum acceptable state-data loss;
- maximum acceptable event replay window;
- maximum acceptable reconciliation delay.

These are operational parameters.

For the trading runtime, the safety requirement is stronger than availability:

If recovery confidence is insufficient, remain FROZEN.

## 16. Post-Recovery Verification

Before production signing resumes:

### Identity
- account owner verified;
- trading account verified;
- signer verified;
- keyset epoch verified.

### State
- position verified;
- orders verified;
- fills verified;
- protection verified;
- capital limits verified.

### Cryptography
- quorum verified;
- public identity verified;
- signer authorization verified;
- payload-signing test verified.

### Runtime
- configuration checksum verified;
- event cursor verified;
- nonce state verified;
- monitoring active.

### Security
- compromised credentials revoked;
- old key epoch disabled;
- recovery evidence archived.

## 17. Recovery Canary

The first post-recovery signed action must be constrained.

Recommended sequence:
1. no-op / non-exposure verification where supported;
2. minimal permitted action;
3. immediate reconciliation;
4. verify event ledger;
5. verify signer identity;
6. only then restore normal limits.

No recovery canary may bypass Capital Guard or Permission Guard.

## 18. Disaster Scenarios

Mandatory drills:

| Scenario | Required response |
|---|---|
| One signer node unavailable | quorum continuity or controlled freeze |
| One share suspected compromised | isolate + refresh/reshare |
| Threshold compromise suspected | full signer replacement / migration |
| API wallet compromised | revoke + replace + reconcile |
| Nonce database lost | freeze + authoritative reconciliation |
| Event store unavailable | freeze + restore state store |
| Configuration backup corrupted | reject restore; use verified backup |
| Treasury signer unavailable | treasury-only recovery |
| Trading signer unavailable | trading-only recovery |
| Full region outage | independent recovery environment |
| Recovery credential compromise | break-glass credential rotation |

## 19. Security Invariants

I1 — Full private key is never reconstructed for recovery.

I2 — Recovery cannot bypass Risk, Capital Guard or Permission Guard.

I3 — FROZEN is the default state after uncertain recovery.

I4 — Old compromised epochs cannot sign new production actions.

I5 — Trading and Treasury recovery domains remain independent.

I6 — Recovery does not reset capital, PnL, nonce or position state.

I7 — Unknown exchange outcomes remain UNKNOWN until reconciled.

I8 — Every key lifecycle transition is auditable.

I9 — Every production recovery ends with an explicit VERIFIED state before CANARY.

## 20. Exit Criteria

v4.3.3 passes only when:

1. Key-share refresh is successfully demonstrated without reconstructing the full private key.
2. Signer replacement is demonstrated.
3. API-wallet revocation/replacement is demonstrated.
4. Runtime restart and state recovery are demonstrated.
5. Nonce recovery is demonstrated.
6. Position/order/protection reconciliation is demonstrated.
7. Old signer epochs cannot produce new production signatures.
8. Break-glass recovery is independently tested.
9. Recovery evidence is replayable and auditable.
10. v4.3.0, v4.3.1 and v4.3.2 remain green after recovery drills.

## 21. Scope Boundary

v4.3.3 does not change:
- ChanLun geometry;
- trading signals;
- capital limits;
- ordinary order execution semantics.

It defines production cryptographic lifecycle and disaster recovery.
