# v4.4.0 — Canary Trading Runtime Architecture

## 1. Objective

v4.4.0 defines the controlled transition from certified testnet infrastructure to limited-production trading.

The purpose is not to maximize profit.

The purpose is to prove that the complete production stack behaves correctly under real market conditions while limiting financial blast radius.

## 2. End-to-End Runtime

Market Data
-> ChanLun State Engine
-> Decision Engine
-> Risk Engine
-> Capital Guard
-> Permission Guard
-> Signing Policy
-> MPC Signing Gateway
-> Exchange Gateway
-> Exchange
-> Reconciliation
-> State Store
-> Monitoring
-> Canary Controller

All production actions must remain observable and attributable to a deterministic event chain.

## 3. Canary Trust Model

The canary must be a smaller-capital instance of the same production architecture, not a simplified architecture.

Required:
- same event contracts;
- same state model;
- same risk controls;
- same signing policy;
- same reconciliation;
- same monitoring;
- same emergency controls.

Only explicitly configured exposure limits differ.

## 4. Canary Modes

### MODE_0 — SHADOW
Live market data is processed through the full runtime.
Outputs:
- ChanLun state;
- Decision;
- OrderIntent;
- Risk decision;
- simulated execution.

No exchange order is submitted.

### MODE_1 — TESTNET
Real signing/execution path against testnet where supported.

### MODE_2 — MICRO_CANARY
Small real-capital deployment with strict opening-exposure caps.

### MODE_3 — CONTROLLED_CANARY
Capital may increase only after acceptance gates.

### MODE_4 — PRODUCTION
Normal approved production limits are enabled only after formal promotion.

## 5. Canary State Machine

SHADOW
-> TESTNET
-> MICRO_CANARY
-> CONTROLLED_CANARY
-> PRODUCTION

Any serious invariant violation:
ANY_STATE -> FROZEN

Recovery:
FROZEN -> INCIDENT -> RECOVERY -> RECONCILIATION -> VERIFIED -> MICRO_CANARY

There is no direct FROZEN -> PRODUCTION transition.

## 6. Capital Ramp

Capital increases only in discrete stages.

Stage 0: simulated capital.
Stage 1: minimum operational capital.
Stage 2: bounded micro allocation.
Stage 3: controlled allocation.
Stage 4: approved production allocation.

Exact amounts are deployment parameters.

Promotion depends on safety evidence, not profitability alone.

## 7. Exposure Limits

Every canary instance must have independent hard limits for:
- account balance;
- maximum open notional;
- maximum single-order notional;
- maximum symbol exposure;
- maximum leverage;
- maximum pending opening orders;
- maximum daily loss;
- maximum drawdown;
- maximum order frequency;
- maximum capital allocation.

Canary limits are enforced by Capital Guard and cannot be overridden by strategy code.

## 8. Order Gate

Before every real-capital order:

Decision
-> Risk
-> Capital Guard
-> Permission Guard
-> Signing Policy
-> MPC
-> Exchange

Any failed gate blocks submission. No bypass path exists.

## 9. Position Protection

A canary position must not become live without a valid protection state.

Checks:
- stop anchor exists;
- stop trigger is valid;
- reduce-only semantics are correct;
- protection quantity covers intended exposure;
- protection acknowledgement is known;
- reconciliation confirms protection.

If protection is missing or uncertain:
- REDUCE_ONLY or FROZEN according to policy.

## 10. Canary Promotion Gates

All mandatory gates must pass:

A — Determinism
B — Execution Integrity
C — Reconciliation
D — Risk
E — Protection
F — Signing
G — Treasury Isolation
H — Recovery
I — Observability
J — Stability

No single profitability metric can substitute for these gates.

## 11. Promotion Evidence

Each promotion creates an immutable evidence bundle containing:
- build_id;
- git_commit;
- configuration_hash;
- strategy_version;
- risk_policy_version;
- signing_policy_version;
- keyset_id / epoch;
- test results;
- replay results;
- reconciliation results;
- incident history;
- performance/resource metrics;
- capital exposure;
- approval record.

Promotion without an evidence bundle is invalid.

## 12. Automatic Demotion

The runtime must demote or freeze on:
- daily loss hard limit;
- unexpected position/order;
- reconciliation divergence;
- missing protection;
- signer mismatch;
- configuration checksum mismatch;
- nonce conflict;
- repeated exchange errors;
- event-store failure;
- state-store corruption;
- excessive latency;
- stale market data;
- abnormal resource usage;
- treasury permission violation.

## 13. Demotion Levels

LEVEL_1 — THROTTLE
Reduce order frequency or size.

LEVEL_2 — RESTRICTED
Block new exposure.

LEVEL_3 — REDUCE_ONLY
Permit only authorized exposure reduction.

LEVEL_4 — FROZEN
Stop all trading actions except explicitly approved recovery operations.

Transitions must be monotonic toward safety.

## 14. Rollback

Rollback means:
- stop new canary exposure;
- reconcile exchange state;
- preserve positions and protection;
- restore last known-good software/configuration;
- verify state;
- resume only in an approved lower-risk mode.

A code rollback never implies an automatic capital or position rollback.

## 15. Shadow Comparison

Before real orders, the canary should support comparison between:
- current implementation;
- candidate implementation.

Compare:
- ChanLun state;
- completed fractals;
- Bi;
- segments;
- center state;
- Decision;
- OrderIntent;
- risk decision.

Only one implementation may have real execution authority.

Shadow implementations have no financial side effects.

## 16. Version Compatibility

The runtime must record compatible versions of:
- event schema;
- state schema;
- strategy;
- risk policy;
- signing policy;
- exchange adapter;
- configuration.

Incompatible contracts fail closed.

## 17. Runtime Health

Mandatory health signals:

Market Data:
- freshness;
- sequence continuity;
- missing candles;
- timestamp drift.

Strategy:
- ChanLun update latency;
- decision latency;
- state consistency.

Execution:
- acknowledgement latency;
- fill latency;
- rejection rate;
- unknown-order rate.

Risk:
- guard decisions;
- capital reservations;
- risk-state transitions.

Security:
- signing failures;
- nonce conflicts;
- policy violations;
- keyset status.

Infrastructure:
- CPU;
- memory;
- queue depth;
- event-store latency;
- network health.

## 18. Real-Time Kill Switch

Kill switch must be independently operable from the strategy process.

Minimum controls:
- freeze account;
- disable signer;
- cancel permitted opening orders;
- force REDUCE_ONLY;
- disable canary promotion;
- block new capital allocation.

The strategy process cannot re-enable a kill switch it does not own.

## 19. Canary Incident Protocol

On incident:
1. Freeze new exposure.
2. Preserve protection.
3. Reconcile orders and positions.
4. Snapshot runtime state.
5. Preserve event evidence.
6. Classify incident.
7. Determine whether rollback is safe.
8. Restore known-good version if required.
9. Reconcile again.
10. Remain in MICRO_CANARY until re-qualified.

## 20. Canary Scorecard

Do not use a single profitability score for promotion.

Promotion evidence covers:
- correctness;
- safety;
- reconciliation;
- signing integrity;
- protection;
- availability;
- resource stability;
- incident rate;
- recovery behavior.

Profitability is a separate performance metric.

## 22. Security Invariants

I1 — Canary cannot bypass production security gates.
I2 — Smaller capital does not mean weaker signing controls.
I3 — Promotion cannot override a failed safety gate.
I4 — Profitability cannot override a safety gate.
I5 — FROZEN cannot self-clear.
I6 — Rollback never blindly reverses financial state.
I7 — Only one execution authority may submit real orders for a given canary account.
I8 — Shadow implementations have no financial side effects.
I9 — Capital increases require explicit promotion evidence.
I10 — Treasury authority remains inaccessible to trading runtime.

## 23. Exit Criteria

v4.4.0 is complete only when:
1. SHADOW mode is operational.
2. TESTNET mode is operational.
3. MICRO_CANARY can run real orders within hard limits.
4. Automatic demotion works.
5. Kill switch works independently.
6. Position protection is enforced.
7. Reconciliation remains deterministic.
8. Restart and recovery preserve state.
9. Promotion evidence is generated.
10. Capital ramp is explicitly gated.
11. No trading process can access treasury authority.
12. A failed canary can return to a verified lower-risk state.

## 24. Scope Boundary

v4.4.0 does not alter:
- ChanLun geometry;
- fractal/Bi/segment definitions;
- divergence rules;
- Decision Engine semantics;
- position-sizing formulas.

It defines the controlled production rollout and runtime safety layer.
