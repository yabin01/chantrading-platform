# v4.4.0 — Canary Trading Runtime Architecture

## 1. Objective

v4.4.0 defines the controlled path from production-ready software to limited real-capital operation.

The purpose of Canary Runtime is not to prove that the ChanLun strategy is profitable. It is to prove that the complete production runtime can execute a tightly bounded amount of real trading capital while preserving all safety invariants.

Canary release is a staged rollout technique that limits initial exposure and allows rollback when problems are detected. citeturn0search0turn0search2

## 2. Scope

The Canary Runtime integrates:

- Market Data
- ChanLun State Engine
- Decision Engine
- Risk Engine
- Capital Guard
- Permission Guard
- Order Manager
- MPC Signing Gateway
- Exchange Gateway
- Reconciliation
- State Store
- Event Store
- Monitoring
- Kill Switch
- Recovery Runtime

No new trading logic is introduced.

## 3. Canary Trust Model

The canary must be a smaller-capital instance of the same production architecture, not a simplified architecture.

Required properties:

- same event contracts;
- same state model;
- same risk controls;
- same signing policy;
- same reconciliation logic;
- same monitoring;
- same emergency controls.

Only explicitly configured exposure limits differ.

Production-like environments should minimize environment mismatch because deployment and runtime differences can hide defects. citeturn0search5

## 4. Canary Modes

### MODE_0 — SHADOW

The full runtime processes live market data.

It produces:

- ChanLun state;
- Decision;
- OrderIntent;
- Risk decision;
- simulated execution result.

No exchange order is submitted.

Purpose:
- validate deterministic behavior;
- compare expected execution;
- verify observability.

### MODE_1 — TESTNET

Real signing/execution path against testnet where supported.

Purpose:
- validate complete order lifecycle;
- validate reconciliation;
- validate failure handling.

### MODE_2 — MICRO_CANARY

Small real-capital deployment.

Opening exposure is strictly capped.

### MODE_3 — CONTROLLED_CANARY

Capital may increase only after acceptance gates.

### MODE_4 — PRODUCTION

Normal production limits are enabled only after formal promotion.

## 5. Canary State Machine

SHADOW
-> TESTNET
-> MICRO_CANARY
-> CONTROLLED_CANARY
-> PRODUCTION

Any serious invariant violation:

ANY_STATE
-> FROZEN

Recovery:

FROZEN
-> INCIDENT
-> RECOVERY
-> RECONCILIATION
-> VERIFIED
-> MICRO_CANARY

There is no direct FROZEN -> PRODUCTION transition.

## 6. Capital Ramp

Capital must increase in discrete stages.

Example:

Stage 0:
- simulated capital.

Stage 1:
- minimum operational capital.

Stage 2:
- bounded micro allocation.

Stage 3:
- controlled allocation.

Stage 4:
- approved production allocation.

Exact amounts are deployment parameters.

Promotion must depend on safety evidence, not on profitability alone.

## 7. Exposure Limits

Every canary instance must have independent hard limits for:

- account balance;
- maximum open notional;
- maximum single-order notional;
- maximum symbol exposure;
- maximum leverage;
- maximum pending opening orders;
- maximum daily loss;
- maximum drawdown;
- maximum order frequency;
- maximum capital allocation.

The canary limit must be enforced by Capital Guard and cannot be overridden by the strategy.

## 8. Order Gate

Before every real-capital order:

Decision
-> Risk
-> Capital Guard
-> Permission Guard
-> Signing Policy
-> MPC
-> Exchange

If any gate fails:
- no order submission.

The canary must not implement a bypass path.

## 9. Position Protection

A canary position must not become live without a valid protection state.

Required checks:

- stop anchor exists;
- stop trigger is valid;
- reduce-only semantics are correct;
- protection quantity covers the intended exposure;
- protection order acknowledgement is known;
- reconciliation confirms expected protection.

If protection is missing or uncertain:
- enter REDUCE_ONLY or FROZEN according to policy.

## 10. Canary Promotion Gates

Promotion requires all mandatory gates to pass.

### Gate A — Determinism
Repeated replay produces equivalent canonical state.

### Gate B — Execution Integrity
Order, fill and position conservation remain valid.

### Gate C — Reconciliation
Exchange state converges with local canonical state.

### Gate D — Risk
No hard risk invariant is violated.

### Gate E — Protection
All live positions have valid protection.

### Gate F — Signing
Only authorized payloads can reach MPC.

### Gate G — Treasury Isolation
No trading runtime action can invoke treasury authority.

### Gate H — Recovery
Restart and recovery drills remain successful.

### Gate I — Observability
Required metrics, alerts and event streams are healthy.

### Gate J — Stability
Long-run runtime remains within resource and latency budgets.

## 11. Promotion Evidence

Each promotion must create a signed or immutable evidence bundle containing:

- build_id;
- git_commit;
- configuration_hash;
- strategy_version;
- risk_policy_version;
- signing_policy_version;
- keyset_id / epoch;
- test results;
- replay results;
- reconciliation results;
- incident history;
- performance/resource metrics;
- capital exposure;
- approval record.

A promotion without an evidence bundle is invalid.

## 12. Automated Demotion

The runtime must automatically demote or freeze when configured triggers occur.

Examples:

- daily loss hard limit;
- unexpected position;
- unexpected order;
- reconciliation divergence;
- missing protection;
- signer mismatch;
- configuration checksum mismatch;
- nonce conflict;
- repeated exchange errors;
- event-store failure;
- state-store corruption;
- excessive latency;
- stale market data;
- abnormal resource usage;
- treasury permission violation.

## 13. Demotion Levels

### LEVEL_1 — THROTTLE
Reduce order frequency or size.

### LEVEL_2 — RESTRICTED
Block new exposure.

### LEVEL_3 — REDUCE_ONLY
Permit only authorized exposure reduction.

### LEVEL_4 — FROZEN
Stop all trading actions except explicitly approved recovery operations.

The transition must be monotonic toward safety.

## 14. Rollback

Rollback must mean:

- stop new canary exposure;
- reconcile exchange state;
- preserve positions and protection;
- restore the last known-good software/configuration;
- verify state;
- resume only in an approved lower-risk mode.

A code rollback must never imply an automatic capital or position rollback.

Canary deployment is useful because a failed rollout can be stopped and traffic/execution returned to the previous known-good version; the same principle is adapted here to trading exposure rather than user traffic. citeturn0search0

## 15. Shadow Comparison

Before enabling real orders, the canary should support shadow comparison between:

- current production implementation;
- candidate implementation.

Compare:

- ChanLun state;
- completed fractals;
- bi;
- segments;
- center state;
- Decision;
- OrderIntent;
- risk decision.

Only one implementation may have real execution authority.

This is analogous to dark-launch/parallel-run techniques where a new implementation can be exercised without allowing it to produce side effects. citeturn0search11turn0search3

## 16. Version Compatibility

The runtime must record compatible versions of:

- event schema;
- state schema;
- strategy;
- risk policy;
- signing policy;
- exchange adapter;
- configuration.

A component with an incompatible contract must fail closed.

## 17. Runtime Health

Mandatory health signals:

### Market Data
- data freshness;
- sequence continuity;
- missing candles;
- timestamp drift.

### Strategy
- ChanLun state update latency;
- decision latency;
- state consistency.

### Execution
- order acknowledgement latency;
- fill latency;
- rejection rate;
- unknown-order rate.

### Risk
- guard decisions;
- capital reservations;
- risk-state transitions.

### Security
- signing failures;
- nonce conflicts;
- policy violations;
- keyset status.

### Infrastructure
- CPU;
- memory;
- queue depth;
- event-store latency;
- network health.

## 18. Real-Time Kill Switch

Kill switch must be independently operable from the strategy process.

Minimum controls:

- freeze account;
- disable signer;
- cancel permitted opening orders;
- force REDUCE_ONLY;
- disable canary promotion;
- block new capital allocation.

The strategy process must not be able to re-enable a kill switch it did not own.

## 19. Canary Incident Protocol

On incident:

1. Freeze new exposure.
2. Preserve protection.
3. Reconcile orders and positions.
4. Snapshot runtime state.
5. Preserve event evidence.
6. Classify incident.
7. Determine whether rollback is safe.
8. Restore known-good version if required.
9. Reconcile again.
10. Remain in MICRO_CANARY until re-qualified.

## 20. Canary Scorecard

The system must not use a single profitability score to determine promotion.

Promotion evidence is multidimensional:

- correctness;
- safety;
- reconciliation;
- signing integrity;
- protection;
- availability;
- resource stability;
- incident rate;
- recovery behavior.

Profitability may be reported as a separate trading-performance metric, but it must not override a safety gate.

## 22. Security Invariants

I1 — Canary cannot bypass production security gates.

I2 — Smaller capital does not mean weaker signing controls.

I3 — Promotion cannot override a failed safety gate.

I4 — Profitability cannot override a safety gate.

I5 — FROZEN cannot self-clear.

I6 — Rollback never blindly reverses financial state.

I7 — Only one execution authority may submit real orders for a given canary account.

I8 — Shadow implementations have no financial side effects.

I9 — Capital increases require explicit promotion evidence.

I10 — Treasury authority remains inaccessible to the trading runtime.

## 23. Exit Criteria

v4.4.0 is complete only when:

1. SHADOW mode is operational.
2. TESTNET mode is operational.
3. MICRO_CANARY can run real orders within hard limits.
4. Automatic demotion works.
5. Kill switch works independently.
6. Position protection is enforced.
7. Reconciliation remains deterministic.
8. Restart and recovery preserve state.
9. Promotion evidence is generated.
10. Capital ramp is explicitly gated.
11. No trading process can access treasury authority.
12. A failed canary can return to a verified lower-risk state.

## 24. Scope Boundary

v4.4.0 does not alter:
- ChanLun geometry;
- fractal/bi/segment definitions;
- divergence rules;
- Decision Engine semantics;
- position sizing formulas.

It defines the controlled production rollout and runtime safety layer.
