# v4.4.10 — Hyperliquid Production Adapter Specification

## 1. Objective

v4.4.10 defines the concrete production adapter specification for Hyperliquid perpetual execution.

It implements the exchange-independent contract defined in v4.4.9 while keeping all Hyperliquid-specific behavior inside the adapter boundary.

Primary project instrument:

ETH-USD

The adapter MUST support a staged path:

Fake Adapter
→ Test Environment / Controlled Verification
→ Micro Canary
→ Production

Production certification is not implied by this specification alone.

## 2. Adapter Boundary

The architecture is:

ChanLun Core
    ↓
Execution Contract
    ↓
Hyperliquid Adapter
    ↓
Hyperliquid API / WebSocket
    ↓
Venue

Optional infrastructure:

ChanLun Core
    ↓
Execution Contract
    ↓
Hyperliquid Adapter
    ↓
Hummingbot Connector
    ↓
Hyperliquid

Hummingbot is an implementation option, not the canonical semantic layer.

## 3. Canonical Identity

The adapter exposes:

venue = hyperliquid

environment = explicit deployment profile

adapter_id = hyperliquid_perpetual

instrument identity is maintained through an explicit mapping layer.

The core canonical symbol for this project remains:

ETH-USD

The adapter MUST NOT scatter exchange-specific symbol strings throughout the core.

## 5. Market Data

The adapter must expose canonical:

- order book;
- trades;
- candles;
- mark/reference data where available;
- exchange timestamps;
- sequence information where provided.

Market data must retain:
- raw source reference;
- received timestamp;
- exchange timestamp where available;
- normalization version.

## 6. 1M Candle Contract

The ChanLun engine consumes canonical 1-minute candles.

Required properties:

- deterministic open/close boundaries;
- exchange/venue timestamp;
- OHLC;
- volume where available;
- final/closed status;
- source identity.

Only completed candles enter the certified structural path unless a separate preview path is explicitly defined.

The adapter MUST NOT silently revise a finalized candle without emitting a correction/revision event.

## 7. Market Data Safety

The adapter reports:

MARKET_HEALTHY
MARKET_DEGRADED
MARKET_STALE
MARKET_GAP
MARKET_UNKNOWN

The Live Risk Control Plane consumes these states.

If canonical data required for a new decision is unsafe:

NEW_ENTRY = DENIED

## 8. Order Contract Mapping

Canonical OrderIntent fields:

- intent_id
- instrument
- side
- position_effect
- order_type
- quantity
- price
- trigger_price
- reduce_only
- post_only
- time_in_force
- reason
- policy_hash

The Hyperliquid adapter converts these into venue-native parameters.

The conversion MUST be deterministic for the same:
- adapter version;
- instrument metadata;
- policy;
- OrderIntent.

## 9. Market Orders

A market-style order must be represented using the adapter's canonical semantics rather than assuming that all venues implement identical market-order mechanics.

The adapter must record:
- requested quantity;
- effective execution constraint;
- venue order representation;
- resulting fills.

The core records what was requested and what actually occurred separately.

## 10. Limit Orders

Required mapping:

LIMIT
→ venue-native limit representation

The adapter validates:
- tick size;
- quantity increment;
- minimum quantity/notional where applicable;
- price constraints;
- post-only compatibility.

Invalid normalization results in DENY rather than silent unsafe adjustment.

## 11. Reduce-Only

Reduce-only is a first-class protection property.

For a protective OrderIntent:

reduce_only = REQUIRED

If the venue rejects or does not support the required semantics:

PROTECTION_FAILED

and v4.4.6 emergency handling is invoked.

The adapter must never silently remove reduce-only from a protective order.

## 12. Position Mode

The adapter must explicitly expose the effective position model:

NET
HEDGED
UNKNOWN

The core must not assume position semantics from the symbol name.

The effective mode is recorded in the execution environment state.

## 13. Position Mapping

Canonical position fields:

- account;
- instrument;
- side;
- quantity;
- entry price;
- mark price;
- liquidation price where available;
- unrealized PnL;
- realized PnL where available;
- margin;
- leverage;
- timestamp.

Raw venue fields remain available for forensic inspection.

## 14. Account Mapping

Canonical account snapshot includes:

- equity;
- balance;
- available margin;
- used margin;
- unrealized PnL;
- realized PnL;
- margin state.

The adapter must distinguish:
- unavailable;
- zero;
- unknown.

Missing values MUST NOT be silently converted to zero.

## 15. Leverage

The adapter exposes leverage state and, where permitted by the environment:

set_leverage()

A leverage mutation requires:
- permission;
- capital policy;
- risk validation;
- audit;
- reconciliation.

Strategy code cannot directly mutate leverage.

## 16. Margin

The adapter reports the effective margin mode and relevant margin state.

Any margin-mode mutation is classified as a high-impact account configuration change.

It requires explicit authorization and certification for production.

## 17. Order Submission Lifecycle

Canonical:

OrderIntent
→ Permission
→ Signing
→ Adapter Submit
→ Venue Response
→ Canonical Order State

Possible immediate result:

ACCEPTED
REJECTED
UNKNOWN

UNKNOWN MUST enter v4.4.8 reconciliation.

## 18. Client Order Identity

The adapter must preserve a stable mapping:

intent_id
↔
client_order_id
↔
venue_order_id

where venue capabilities permit.

If the venue does not provide equivalent identity semantics, the adapter must maintain its own durable correlation record.

## 19. Idempotency

The adapter must make duplicate logical submissions detectable.

Conceptual identity:

logical_order_key =
hash(account + intent_id + action_version)

The adapter MUST check for an existing venue order before retrying an UNKNOWN mutation.

## 20. Cancel

Canonical:

cancel_order(order_reference)

State mapping:

CANCEL_REQUESTED
→ CONFIRMED_CANCELLED

or:

UNKNOWN
→ RECONCILE

A timeout is never interpreted as cancellation.

## 21. Cancel/Fill Race

If a cancellation request races with a fill:

authoritative venue state wins.

The adapter must reconcile:
- order;
- fills;
- position.

Local request state cannot override confirmed fills.

## 22. Modify

If venue-native amend is supported and certified:

modify_order()

Otherwise:

cancel
→ confirm cancellation
→ create replacement

A replacement MUST NOT be submitted while the original order's state is unresolved unless an explicitly certified emergency policy allows it.

## 23. Fill Mapping

Every fill becomes a canonical Fill event.

Required:
- venue fill ID when available;
- venue order ID;
- canonical instrument;
- side;
- quantity;
- price;
- fee;
- fee asset;
- exchange timestamp;
- raw reference.

Duplicate fill messages must be deduplicated.

## 24. WebSocket

The adapter maintains separate logical subscriptions for:
- market data;
- orders;
- fills;
- positions/account;
- system/connection state.

Each subscription tracks:
- session;
- channel;
- last message;
- last sequence if available;
- reconnect count;
- health state.

## 25. WebSocket Recovery

On disconnect:

1. mark affected stream unhealthy;
2. stop trusting incremental state after the last validated point;
3. reconnect;
4. resubscribe;
5. perform authoritative reconciliation;
6. restore stream health;
7. only then restore affected execution authority.

## 26. Sequence and Ordering

Where the venue supplies sequence/order information, the adapter validates continuity.

If continuity cannot be proven:

SEQUENCE_UNKNOWN

The adapter must not invent ordering from local receive time.

## 27. REST/API Recovery

For mutation timeout:

UNKNOWN

The adapter queries authoritative venue state.

Required checks depend on operation:

Order:
- order status;
- open orders;
- recent fills;
- position.

Cancel:
- order;
- fills;
- position.

Protection:
- protective order;
- fills;
- position;
- remaining required quantity.

## 28. Rate Limit Handling

The adapter maintains a local rate-limit state.

On venue rate-limit response:

1. classify;
2. apply bounded backoff;
3. preserve operation identity;
4. avoid uncontrolled retry;
5. report health degradation.

Risk/Protection operations have policy-defined priority.

## 29. Exchange Time

The adapter should expose venue time where available.

Clock drift affecting signed/authenticated operations is treated as an execution safety issue.

If required synchronization cannot be established:

affected execution = DENIED

## 37. Startup

BOOT
→ LOAD_CONFIGURATION
→ LOAD_CREDENTIAL_REFERENCE
→ LOAD_METADATA
→ CONNECT_API
→ CONNECT_WS

READY is not granted when required reconciliation fails.

## 38. Shutdown

Graceful shutdown:

1. stop new strategy intents;
2. preserve protection;
3. finish/cancel according to policy;
4. reconcile;
5. release execution lease;
6. close connections;
7. persist final state.

The adapter must never treat process shutdown as equivalent to position closure.

## 40. Hummingbot Failure Isolation

If Hummingbot becomes unavailable:

- new exposure is denied;
- existing protection follows v4.4.6/v4.4.7;
- direct native adapter may be activated only if explicitly certified;
- automatic fallback between execution implementations is forbidden unless the transition policy is certified.

This prevents an untested failover path from becoming a hidden risk.

## 45. Security

I1 — Credentials never enter strategy state.
I2 — Signing remains isolated.
I3 — Adapter cannot bypass permission.
I4 — Adapter cannot increase capital policy.
I5 — Unknown mutation cannot be blindly retried.
I6 — Stale runtime cannot execute without lease.
I7 — Raw exchange evidence is preserved.
I8 — Protection semantics cannot be weakened by mapping.
I9 — Metadata drift blocks unsafe new orders.
I10 — All production mutations are auditable.
