# v4.4.12 — Hyperliquid Adapter Implementation Architecture

## 1. Objective

v4.4.12 converts the v4.4.10 production adapter specification and v4.4.11 verification matrix into an implementation architecture.

The objective is to define:
- repository layout;
- module boundaries;
- interfaces;
- dependency direction;
- data flow;
- lifecycle;
- state ownership;
- concurrency boundaries;
- failure handling;
- testing boundaries;
- Hummingbot integration boundary.

This specification does not change ChanLun semantics.

## 2. Architectural Rule

The implementation MUST preserve:

ChanLun Core
→ Execution Contract
→ Hyperliquid Adapter
→ Venue Infrastructure

The following MUST NOT import Hyperliquid SDK objects:
- ChanLun Engine;
- Fractal Engine;
- Bi Engine;
- Segment Engine;
- Center Engine;
- Decision Engine;
- Risk Engine;
- Capital Engine;
- Protection Engine;
- Replay Engine.

Only the adapter/infrastructure layer may depend on Hyperliquid-specific libraries.

## 7. Hyperliquid SDK Boundary

The official Hyperliquid Python SDK already separates Info/query functionality and Exchange/action functionality, and provides WebSocket support. The current SDK source exposes Info methods such as user state, open orders, fills, metadata and order status, while Exchange handles signed order/cancel actions.

Our adapter MUST wrap these APIs rather than expose them directly to core code.

Example:
    HyperliquidInfoClient
          ↓
    HyperliquidMapper
          ↓
    Canonical Position / Order / Account

and:
    Canonical OrderIntent
          ↓
    HyperliquidOrderMapper
          ↓
    HyperliquidExchangeClient
          ↓
    Venue

## 8. REST Client

rest.py owns transport-level communication.

Responsibilities:
- endpoint calls;
- timeout;
- HTTP errors;
- serialization;
- response capture;
- transport metrics;
- retry policy hooks.

It MUST NOT decide whether a trade is allowed.

## 9. Info Client

A dedicated read-only client is recommended:

info_client.py

Responsibilities:
- meta;
- metaAndAssetCtxs;
- clearinghouseState;
- openOrders;
- orderStatus;
- userFills;
- historical orders;
- allMids;
- candle snapshots;
- other required read APIs.

This mirrors the official SDK's separation of Info operations.

## 10. Exchange Client

exchange_client.py owns mutation calls:
- order;
- cancel;
- modify where supported;
- leverage/configuration mutations where certified.

It MUST receive already-authorized commands.

It MUST NOT calculate:
- position size;
- stop distance;
- risk;
- strategy signals.

## 11. WebSocket Manager

websocket.py owns:
- connection;
- authentication/subscription setup;
- subscription registry;
- heartbeat;
- reconnect;
- snapshot detection;
- raw message capture;
- stream health.

The official SDK examples show subscriptions for l2Book, trades, user events, fills, candles, order updates, funding, ledger updates and active asset data.

## 12. WebSocket Event Router

Raw WebSocket events flow:

    Raw Message
       ↓
    Envelope Parser
       ↓
    Subscription Router
       ↓
    Event Normalizer
       ↓
    Canonical Event Bus

No strategy callback should be attached directly to the raw WebSocket client.

## 13. Stream Workers

Recommended logical workers:
    MarketStreamWorker
    OrderStreamWorker
    FillStreamWorker
    PositionStreamWorker
    AccountStreamWorker

Workers may share a physical WebSocket connection but retain independent logical state.

## 14. Snapshot State

Each stream tracks:
    stream_id
    connection_id
    subscribed
    snapshot_received
    last_event_time
    last_sequence
    health

A stream cannot be considered synchronized until its required initial state has been established.

## 15. Connection Supervisor

connection_supervisor.py owns:
    CONNECTING
    CONNECTED
    DEGRADED
    RECONNECTING
    RESYNCING
    READY
    STOPPED

A reconnect MUST enter RESYNCING before returning to READY.

## 16. Market Data Normalizer

market_data.py converts:
- order book;
- trades;
- candle;
- allMids;
- mark/reference context

into canonical domain events.

It also performs:
- timestamp normalization;
- symbol normalization;
- decimal normalization;
- duplicate detection;
- stale detection.

## 17. Candle Normalizer

Canonical output:
    CanonicalCandle {
      instrument_id
      timeframe
      open_time
      close_time
      open
      high
      low
      close
      volume
      final
      source
    }

For the ChanLun structural path:
    timeframe = 1m
    final = true

is the only certified structural input.

## 18. Order Mapper

orders.py translates:
    OrderIntent
       ↓
    VenueOrderRequest

and:
    VenueOrderResponse
       ↓
    Canonical OrderResult

It validates:
- instrument;
- side;
- quantity;
- price;
- order type;
- TIF;
- reduce-only;
- post-only;
- trigger semantics.

## 19. Order Mapper Safety

The mapper MUST fail closed.

Example:
    reduce_only = REQUIRED

If venue representation cannot prove reduce-only:
    MappingError
    →
    PROTECTION_FAILED

Never:
    REQUIRED
    →
    omitted

## 20. Client Order ID

The adapter creates a durable correlation:
    intent_id
       ↕
    client_order_id
       ↕
    venue_order_id

Hyperliquid's official SDK supports client order IDs through cloid; the adapter should preserve this identity where the current venue contract permits it.

## 21. Order Lifecycle Store

mutation_tracker.py tracks:
    CREATED
    AUTHORIZED
    SUBMITTING
    ACCEPTED
    UNKNOWN
    OPEN
    PARTIALLY_FILLED
    FILLED
    CANCEL_REQUESTED
    CANCELLED
    REJECTED
    EXPIRED

The lifecycle store is separate from the exchange transport client.

## 22. Unknown Mutation Handler

Any mutation that reaches the transport boundary but lacks authoritative outcome becomes:
    UNKNOWN

The handler must execute:
    Query Order
    +
    Query Open Orders
    +
    Query Recent Fills
    +
    Query Position

Only then may the lifecycle transition to a terminal state.

## 23. Fill Mapper

fills.py maps venue fills into canonical Fill events.

Required protections:
- duplicate fill detection;
- idempotent persistence;
- timestamp normalization;
- order correlation;
- position correlation.

A fill must never be applied twice.

## 24. Position Mapper

positions.py maps authoritative venue state.

For Hyperliquid, the official SDK exposes clearinghouseState with asset positions, entry price, leverage, liquidation price, margin used, position size and unrealized PnL.

The mapper must preserve:
- leverage type;
- liquidation price;
- position size;
- margin;
- PnL.

Missing fields remain UNKNOWN.

## 25. Account Mapper

account.py maps:
- account value;
- margin;
- withdrawable/available capital;
- cross margin summary;
- relevant account state.

The mapper must distinguish:
    0
    null
    unavailable
    unknown

These are not interchangeable.

## 26. Instrument Registry

instruments.py owns:
    CanonicalInstrumentId
          ↕
    Hyperliquid Instrument

It loads current venue metadata instead of hard-coding asset indexes.

The official SDK currently builds coin/asset mappings from perpetual metadata and size decimals.

## 27. ETH Mapping

The implementation MUST provide:
    resolve("ETH-USD")
→ current Hyperliquid perpetual instrument

The result is cached with:
    metadata_version
    fetched_at
    adapter_version

A stale registry cannot authorize new orders.

## 28. Capability Provider

capabilities.py determines:
- supported order types;
- reduce-only;
- post-only;
- amend;
- leverage;
- margin;
- streaming;
- client order IDs;
- reconciliation queries.

Capability state:
    SUPPORTED
    UNSUPPORTED
    CONDITIONAL
    UNKNOWN

UNKNOWN is never promoted to SUPPORTED.

## 29. Error Mapper

errors.py maps venue errors into canonical:
    InvalidRequest
    InvalidSymbol
    InvalidQuantity
    InvalidPrice
    InsufficientMargin
    ReduceOnlyRejected
    RateLimited
    AuthenticationFailed
    PermissionDenied
    Timeout
    NetworkError
    Maintenance
    Unsupported
    Unknown

Raw error payload remains attached to the adapter evidence record.

## 30. Rate Limit Controller

rate_limit.py owns:
- request weight;
- endpoint budget;
- backoff;
- retry;
- burst control;
- metrics.

It must be transport-aware but policy-neutral.

Protection requests may receive higher scheduling priority, but the controller must never bypass authorization.

## 31. Authentication Boundary

auth.py owns:
- signer reference;
- account address;
- API wallet configuration;
- signature creation;
- nonce/timestamp requirements.

Private keys must never be passed into:
- OrderIntent;
- Strategy;
- Risk;
- Replay fixtures.

The official SDK supports a separate API wallet configuration while retaining the main wallet/account address as the account identity; this distinction must remain explicit in our configuration model.

## 32. Signing Gateway

The preferred path:
    AuthorizedExecutionCommand
          ↓
    SigningGateway
          ↓
    HyperliquidExchangeClient
          ↓
    Venue

Signing MUST occur as late as practical.

No unsigned raw action should escape the adapter boundary.

## 33. Reconciliation Engine

reconciliation.py compares:

Local:
- orders;
- fills;
- positions;
- account;
- protection.

Venue:
- authoritative queries.

Outputs:
    MATCH
    DRIFT
    INCOMPLETE
    FAILED

## 34. Reconciliation Priority

Priority order:
1. position;
2. protection;
3. open orders;
4. fills;
5. account;
6. metadata.

This is an operational priority, not a statement that lower layers are unimportant.

## 35. Position Drift

If:
    local_position != venue_position

then:
    POSITION_DRIFT

The execution policy decides whether:
- restrict;
- freeze;
- reconcile;
- flatten.

The adapter does not independently invent the recovery trade.

## 36. Protection Reconciler

Dedicated protection verification:
    required_protection
       vs
    actual_protection_orders

Cases:
- missing;
- duplicate;
- oversized;
- undersized;
- wrong direction;
- non-reduce-only;
- stale;
- unknown.

Any material protection mismatch escalates to v4.4.6.

## 42. Raw Evidence Store

Raw Hyperliquid messages are stored separately from canonical state.

Structure:
    raw/
      hyperliquid/
        <date>/
          websocket/
          rest/
          errors/

Canonical events reference:
    raw_evidence_ref

This permits forensic reconstruction without leaking raw venue objects into the core.

## 43. Hummingbot Adapter

If Hummingbot remains in the stack:
    HyperliquidAdapter
        ↓
    HummingbotBridge
        ↓
    hyperliquid_perpetual

The bridge implements the same transport-facing interfaces as the native client.

The core cannot know whether the underlying transport is:
- native SDK;
- Hummingbot;
- another certified implementation.

## 44. Native vs Hummingbot

Initial implementation should support one certified path first.

Recommended abstraction:
    ExecutionBackend
       ├── HyperliquidNativeBackend
       └── HummingbotBackend

Automatic runtime switching is forbidden until both paths independently pass certification.

## 45. Concurrency Model

Recommended:
- one connection supervisor;
- one WebSocket reader;
- logical stream routers;
- bounded REST worker pool;
- serialized mutation coordinator per account/instrument;
- asynchronous reconciliation worker.

Critical order mutations must preserve ordering where required.

## 46. Mutation Coordinator

For each:
    account + instrument

maintain a serialized mutation lane.

This prevents races such as:
    submit
    cancel
    replace

from executing concurrently without lifecycle awareness.

## 47. Protection Priority Lane

Protection may have a dedicated priority queue.

Priority:
    emergency protection
    >
    position reconciliation
    >
    cancel risk-reduction
    >
    ordinary order
    >
    metadata/non-critical reads

This does not bypass permission or risk policy.

## 48. Time Model

Every event records:
- exchange time;
- local receive time;
- processing time.

Never replace exchange time with local time.

Latency metrics derive from explicit timestamps.

## 49. Persistence

Minimum durable state:
- order correlation;
- mutation status;
- fill ledger;
- position snapshot;
- adapter metadata;
- capability snapshot;
- reconciliation status;
- protection status;
- lease state.

Transient WebSocket buffers do not constitute durable truth.

## 50. Restart Sequence

After process restart:
    LOAD DURABLE STATE

        ↓
    LOAD METADATA
        ↓
    QUERY ORDERS
        ↓
    QUERY FILLS
        ↓
    QUERY POSITION
        ↓
    QUERY ACCOUNT
        ↓
    RECONCILE
        ↓
    VERIFY PROTECTION
        ↓
    RESTORE LEASE
        ↓
    READY

No new exposure before READY.

## 54. Static Architecture Test

CI should fail if forbidden imports appear.

Any import such as:
    from hyperliquid import ...

is forbidden outside:
    adapters/hyperliquid/

This can be enforced through import-lint tests.

## 60. Implementation Rules

R1 — No exchange logic in ChanLun Core.
R2 — No SDK object outside adapter.
R3 — No blind retry after UNKNOWN.
R4 — No silent reduce-only downgrade.
R5 — No new exposure before reconciliation-ready.
R6 — No duplicate fill application.
R7 — No metadata assumption without current registry.
R8 — No automatic backend failover before dual certification.
R9 — No secrets in event/log/replay payloads.
R10 — Every mutation is traceable.

## 62. Scope Boundary

v4.4.12 defines implementation architecture.

It does not claim that the resulting code is production-certified.

Production readiness still requires execution of v4.4.11 and completion of the project's existing v4.4.4/v4.4.5 certification and capital-promotion gates.
