# v4.4.13 — Hyperliquid Adapter Code Skeleton & Interface Package

## 1. Status

This release creates the first executable code boundary for the Hyperliquid adapter.

It is a code skeleton, not a production trading implementation.

## 2. Implemented Components

### Domain
Path:
src/chantrading/domain/execution.py

Provides venue-neutral:
- Side
- OrderType
- TimeInForce
- OrderStatus
- OrderIntent
- Fill
- Position
- ExecutionResult
- ReconciliationResult

No Hyperliquid SDK dependency is permitted.

### Execution Contract
Path:
src/chantrading/execution/contracts.py

Defines the adapter-facing protocols:
- ExecutionBackend
- MarketDataBackend
- CapabilityProvider
- Signer

These protocols are the dependency inversion boundary.

### Hyperliquid Adapter
Path:
src/chantrading/adapters/hyperliquid/

Current files:
- __init__.py
- config.py
- capabilities.py
- adapter.py

The top-level adapter delegates transport work to a backend and exposes canonical domain objects.

## 3. Deliberate Limitation

The current Hyperliquid adapter does NOT yet call the real Hyperliquid API.

This is intentional.

The implementation sequence is:

1. stabilize canonical models;
2. stabilize contracts;
3. stabilize fake backend;
4. implement real REST client;
5. implement real WebSocket client;
6. implement normalization;
7. implement mutation lifecycle;
8. implement reconciliation;
9. run v4.4.11 certification tests.

## 4. Official SDK Boundary

Current official Hyperliquid Python SDK code exposes Info methods for user state, metadata, fills, open orders and WebSocket subscriptions, while Exchange contains signed mutations such as order and cancel. The adapter therefore treats the SDK as an infrastructure dependency rather than a domain dependency.

Official SDK reference:
https://github.com/hyperliquid-dex/hyperliquid-python-sdk

## 5. Canonical Instrument

The project-facing identifier remains:

ETH-USD

The adapter is responsible for resolving this to the current venue-native representation.

No asset index is hard-coded into ChanLun Core.

## 6. Security Boundary

Private keys and signing credentials are intentionally absent from:
- OrderIntent;
- domain models;
- tests;
- replay fixtures;
- logs.

Signing will be added behind a dedicated SigningGateway.

## 7. Reduce-Only Boundary

reduce_only is represented explicitly in OrderIntent.

The adapter capability registry explicitly declares whether reduce-only is supported.

If a future backend cannot guarantee the requested reduce-only semantics, the request must fail closed.

## 8. Architecture Test

tests/unit/test_architecture_boundary.py prevents Hyperliquid SDK imports from leaking into core/execution code.

This is a CI-enforceable architecture rule.

## 9. Unit Tests

tests/unit/test_hyperliquid_adapter.py currently verifies:
- canonical execution result;
- backend delegation;
- venue order ID isolation;
- client order ID preservation;
- explicit reduce-only capability.
