# v4.4.15 — Hyperliquid WebSocket Read Path

## 1. Objective

v4.4.15 establishes the real-time event architecture for Hyperliquid.

The implementation separates:
- WebSocket transport;
- subscription definitions;
- lifecycle state;
- canonical event envelope;
- ChanTrading consumers.

The current release intentionally does not perform signed trading mutations.

## 2. Verified Venue Surface

The current official Hyperliquid Python SDK exposes WebSocket subscriptions for:
- allMids;
- l2Book;
- trades;
- userEvents;
- userFills;
- candle;
- orderUpdates;
- userFundings;
- userNonFundingLedgerUpdates;
- webData2;
- bbo;

- activeAssetData.

The first certified streams are:

1. candle / 1m;

3. userFills;
4. orderUpdates.

The 1m candle stream is the structural market-data input for the ChanLun engine.

## 5. Lifecycle Manager

Implemented:
src/chantrading/adapters/hyperliquid/websocket.py

States:

    DISCONNECTED
    CONNECTING
    CONNECTED
    RESYNCING
    READY
    STOPPED

The state machine is deliberately stricter than simply checking whether a TCP/WebSocket connection exists.

## 6. Ready Rule

A WebSocket connection is NOT READY merely because the socket is open.

READY requires every registered snapshot-required subscription to have received its required synchronization state.

This prevents a reconnect from immediately exposing incomplete data to ChanLun.

## 7. Reconnect Rule

After a disconnect/reconnect:

    CONNECTED
        ↓
    RESYNCING
        ↓
    snapshot recovery
        ↓
    READY

No structural signal or new execution authorization should rely on the adapter during RESYNCING.

## 8. Canonical Event Envelope

Implemented:
src/chantrading/adapters/hyperliquid/events.py

Each event carries:
- event_id;
- channel;
- exchange/event timestamp;
- local receive timestamp;
- normalized data;
- optional raw evidence.

This allows latency measurement and deterministic replay without forcing the core to understand venue-specific message envelopes.

## 9. 1M Candle Semantics

The official API documents candle messages with:
- start timestamp;
- end timestamp;
- open;
- high;
- low;
- close;
- volume;
- interval;
- symbol.

The official REST candle snapshot likewise exposes 1m as a valid interval. citeturn0search6

The adapter must preserve both the beginning and end timestamps.

A candle is considered structurally usable only after the project-level final-candle policy marks it complete.

## 10. User Event Streams

The official SDK provides userEvents, userFills and orderUpdates subscriptions. citeturn0search0turn0search5

These streams will feed:
- order lifecycle;
- fill ledger;
- position reconciliation;
- protection verification.

They must not directly mutate ChanLun state.

## 11. Snapshot vs Live Update

A subscription may:
- provide an initial snapshot;
- provide only future events;
- require a REST snapshot before live events are trusted.

The adapter therefore treats synchronization as an explicit state transition rather than assuming every WebSocket subscription is self-synchronizing.

## 12. REST + WebSocket Recovery

The certified recovery model is:

    WebSocket disconnect
           ↓
    stop accepting structural events
           ↓
    reconnect
           ↓
    REST authoritative snapshot
           ↓
    replay/consume queued live events where safe
           ↓
    consistency check
           ↓
    READY

This avoids treating a WebSocket reconnect as an authoritative state reconstruction.

## 13. Heartbeat

The current official SDK sends WebSocket ping messages periodically and handles pong messages. citeturn0search0

The ChanTrading transport implementation must expose heartbeat health separately from application-data health.

A live socket with no usable market/user events is not automatically HEALTHY.

## 14. Event Ordering

Each event records:
- venue event time;
- receive time.

Later state-store integration must add:
- monotonic ingestion sequence;
- duplicate key;
- stream sequence where the venue provides one.

The current WebSocket layer does not invent a sequence number.

## 15. Duplicate Events

Duplicate suppression belongs above raw transport.

The event/state layer will use:
    event_id
    + channel
    + venue identifiers
    + timestamp
    + payload fingerprint

where required.

The WebSocket transport itself should remain lossless.

## 16. Out-of-Order Events

The adapter must not silently reorder raw messages.

Ordering-sensitive consumers will use:
- event timestamps;
- lifecycle version;
- reconciliation;
- authoritative REST state.

## 17. Backpressure

The eventual implementation must use bounded queues.

If consumers cannot keep up:
    queue pressure
        ↓
    DEGRADED

It must not silently drop fills, order updates, or protection events.

## 18. Stream Health

Health must be tracked independently for:
- socket connection;
- heartbeat;
- 1m candle;
- user events;
- fills;
- order updates.

A failure in one stream must not be hidden by another healthy stream.

## 19. Tests Added

Current unit tests verify:
- reconnect enters RESYNCING;
- READY requires all registered snapshots;
- 1m subscription payload is explicit.

## 20. Next Layer

v4.4.16 should implement the real WebSocket transport and event normalizers:

    websocket-client
        ↓
    HyperliquidWebSocketTransport
        ↓
    SubscriptionManager
        ↓
    RawEventRouter
        ↓
    CandleNormalizer / OrderNormalizer / FillNormalizer
        ↓

The implementation should remain read-only until those normalized events pass deterministic fixture tests.

## 21. Production Boundary

v4.4.15 does not certify:
- live trading;
- execution;
- stop protection;
- liquidation protection;
- production capital.

Those remain downstream certification gates.
