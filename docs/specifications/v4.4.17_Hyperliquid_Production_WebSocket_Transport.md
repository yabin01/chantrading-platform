# v4.4.17 — Hyperliquid Production WebSocket Transport

## Objective

Bind the v4.4.15 lifecycle manager to a real WebSocket transport while keeping event parsing and trading policy outside the transport.

## Implementation

Added:
- WebSocketAppTransport using websocket-client with lazy import;
- deterministic InMemoryWebSocketTransport;
- lifecycle manager connection binding;
- subscription replay on open;
- pong timestamp tracking;
- disconnect → RESYNCING transition.

## Venue Verification

The official Hyperliquid Python SDK currently constructs its WebSocket URL from the API base URL, sends a JSON ping periodically, recognizes a pong channel, and replays queued subscriptions when the socket opens. citeturn0search0

The official SDK examples subscribe to ETH 1m candles and user event/fill/order-update streams. citeturn0search5

## Important Design Choice

This project does not simply adopt the SDK's WebSocketManager as the ChanTrading runtime.

The SDK remains a venue transport dependency. ChanTrading owns:
- lifecycle state;
- RESYNCING semantics;
- canonical event normalization;
- deterministic replay;
- reconciliation;
- trading authorization.

This prevents an exchange SDK lifecycle detail from becoming a core trading invariant.

## Connection State

Normal operation:

DISCONNECTED
→ CONNECTING
→ CONNECTED
→ RESYNCING
→ READY

A socket being physically connected is not sufficient for READY.

READY requires required synchronization snapshots.

## Subscription Replay

After on_open, registered subscriptions are re-sent.

This is required because a reconnect invalidates the previous WebSocket session.

Single-subscription constraints and venue-specific subscription identifiers remain adapter concerns.

## Heartbeat

The manager records the timestamp of the most recent pong.

The transport itself does not declare the application healthy merely because the socket remains open.

A later health supervisor should combine:
- pong freshness;
- candle freshness;
- user-event freshness;
- fill freshness;
- order-update freshness.

## Failure Semantics

Unexpected close:
→ RESYNCING
→ clear synchronization markers
→ reconnect externally
→ replay subscriptions
→ obtain authoritative REST snapshots
→ mark required snapshots complete
→ READY

No trading decision should be authorized during RESYNCING.

## Security

No secret key, signing operation, or order mutation is introduced.

The transport only carries public subscription messages and read-side user streams.

## Testing Boundary

InMemoryWebSocketTransport allows lifecycle tests without a network connection.

Production websocket-client is imported lazily so unit tests and domain modules do not require the external package merely to import the project.

## Current Limitation

The current WebSocketAppTransport is a transport binding, not the complete reconnect supervisor.

Exponential backoff, jitter, maximum retry policy, circuit breaker, and automatic reconnect scheduling belong in the runtime supervisor.

This separation is intentional.
