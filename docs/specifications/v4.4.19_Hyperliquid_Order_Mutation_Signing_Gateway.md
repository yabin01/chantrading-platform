# v4.4.19 — Hyperliquid Order Mutation & Signing Gateway

## 1. Objective

v4.4.19 introduces the first signed execution boundary without exposing private keys to the ChanTrading domain.

The implementation separates:
- canonical order requests;
- venue action mapping;
- signing;
- signed transport;
- mutation result.

## 2. Official API Evidence

The current official Hyperliquid Python SDK constructs an order action, obtains a millisecond timestamp, signs the L1 action with the wallet, and POSTs the signed payload to /exchange. It also supports reduce_only, client order IDs, and expires_after. citeturn0search3

The official SDK's basic testnet example demonstrates order submission followed by querying the resulting order status and cancelling a resting order. citeturn0search1

The SDK also documents an agent-account pattern for placing testnet orders. citeturn0search2

## 3. Architecture

    ChanTrading Domain
            ↓
    LimitOrderRequest / CancelOrderRequest
            ↓
    Hyperliquid Order Mapper
            ↓
    SigningGateway
            ↓
    SignedAction
            ↓
    ExchangeTransport
            ↓
    /exchange

The domain never receives or stores a private key.

## 4. Signing Boundary

Implemented:
src/chantrading/adapters/hyperliquid/signing.py

ActionSigner is an injected protocol.

Production implementations may be:
- isolated local signer;
- API-wallet process;
- MPC gateway;
- HSM-backed signer.

The ChanLun engine must never call a wallet library directly.

## 5. Canonical Limit Order

Implemented:
src/chantrading/adapters/hyperliquid/order_requests.py

Fields:
- instrument;
- buy/sell;
- quantity;
- limit price;
- time in force;
- reduce-only;
- client order ID.

Decimal is used for quantity and price at the domain boundary.

## 6. Supported TIF

Current canonical enum:
- GTC;
- IOC;
- ALO.

The mapper converts these to Hyperliquid wire values.

Venue-specific acceptance must still be certified before production enablement.

## 7. Reduce-Only

reduce_only is carried explicitly into the signed order action.

It is not inferred from ChanLun intent.

This is important because a close/reduction must remain distinguishable from an opening order throughout the execution chain.

## 8. Client Order Identity

client_order_id is preserved as the canonical idempotency/tracing handle.

The venue's native order ID is still authoritative after submission.

The client ID is not treated as proof that an order was accepted.

## 9. Cancel

v4.4.19 currently supports cancel-by-native-order-ID.

Client-ID cancellation remains a later extension because it requires explicit venue capability verification and canonical error semantics.

## 10. expiresAfter

The signing gateway accepts expires_after as an explicit parameter.

The official SDK sends expiresAfter together with the signed exchange action and documents that expiration causes actions to be rejected after the timestamp. citeturn0search3

The runtime must calculate this from a synchronized clock rather than an arbitrary local clock.

## 11. Nonce

The current signing gateway requires a positive nonce.

Nonce allocation and collision prevention are deliberately not embedded inside the signer.

A dedicated nonce/clock authority must own:
- timestamp generation;
- monotonicity;
- clock drift checks;
- concurrent request serialization.

## 12. Mutation Result

The gateway returns MutationResult.

Current statuses:
- SUBMITTED;
- CANCEL_SUBMITTED.

These are transport submission states, NOT final exchange states.

The order lifecycle layer must later resolve:
- resting;
- filled;
- partially filled;
- canceled;
- rejected;
- expired;
- UNKNOWN.

## 13. UNKNOWN Rule

A timeout after signing must never be interpreted as rejection.

It creates an UNKNOWN execution state.

The system must query authoritative order state before retrying.

Blind retry of a signed order is prohibited.

This rule is mandatory for avoiding duplicate execution.

## 14. Mainnet Boundary

SigningGateway has an explicit mainnet flag.

v4.4.19 does not automatically permit mainnet execution.

Production configuration must require a separate certification gate before the mainnet signer is enabled.

## 15. Test Boundary

Unit tests use a fake signer.

No real private key is stored in the repository.

No live order is sent by the tests.

## 16. Security Boundary

The repository must never contain:
- private keys;
- seed phrases;
- API wallet secrets;
- raw production signatures;
- production wallet configuration.

Only interfaces and deterministic test doubles belong here.

## 17. Next Step

v4.4.20 should implement the canonical order lifecycle and UNKNOWN recovery:

    SUBMITTING
       ↓
    SUBMITTED
       ↓
    ACKNOWLEDGED
       ↓
    RESTING / PARTIAL / FILLED
       ↓
    CLOSED

with failure branches:

    REJECTED
    CANCELED
    EXPIRED
    UNKNOWN
       ↓
    QUERY
       ↓
    RESOLVED

No signed retry is permitted while UNKNOWN remains unresolved.

## 18. Production Boundary

v4.4.19 establishes the signed mutation architecture but does not authorize autonomous production execution.
