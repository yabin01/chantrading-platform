# v4.4.1 — Canary Operations, Monitoring & Incident Runbook

## 1. Objective

v4.4.1 turns the v4.4.0 Canary Runtime architecture into an executable operating procedure.

It defines:
- monitoring;
- alert severity;
- SLO/SLA-style runtime targets;
- operator roles;
- deployment and promotion checklist;
- incident classification;
- kill-switch procedure;
- rollback procedure;
- recovery verification;
- evidence collection;
- post-incident review.

The objective is operational safety, not strategy optimization.

## 2. Operating Principle

A canary must be easy to observe and easy to stop.

Monitoring must compare the canary against explicit safety thresholds rather than rely only on manual inspection. Production canary systems commonly use health metrics, alarms, evaluation windows and rollback mechanisms to limit exposure. citeturn0search1turn0search2

For this trading system, the unit of exposure is financial risk rather than request traffic.

## 3. Operator Roles

### Operator
Can:
- inspect dashboards;
- acknowledge alerts;
- execute approved freeze procedures;
- collect evidence.

Cannot:
- change risk limits;
- change signing policy;
- authorize treasury withdrawal;
- clear FROZEN independently.

### Risk Operator
Can:
- review risk state;
- approve defined operational changes;
- initiate risk freeze.

Cannot:
- bypass MPC;
- authorize treasury withdrawals.

### Security Operator
Can:
- disable signer;
- initiate key rotation;
- execute security incident procedures.

### Release Approver
Can:
- approve promotion between canary levels.

No single operational role should control strategy, signing and treasury authority simultaneously.

## 5. Health States

Every critical subsystem reports:

HEALTHY
DEGRADED
STALE
FAILED
UNKNOWN

UNKNOWN must not be treated as HEALTHY.

Examples:
- stale market data -> STALE;
- uncertain exchange acknowledgement -> UNKNOWN;
- missing protection -> UNKNOWN;
- unavailable signer quorum -> FAILED;
- state mismatch -> DEGRADED or FAILED according to policy.

## 6. Severity Levels

### SEV-0 — Critical Security / Capital Threat
Examples:
- unauthorized signed action;
- treasury boundary violation;
- unexplained withdrawal-capable action;
- confirmed signer compromise;
- unexplained capital movement.

Action:
- immediate FROZEN;
- disable affected signer;
- preserve evidence;
- initiate security incident.

### SEV-1 — Trading Safety Failure
Examples:
- unexpected position;
- protection missing;
- material reconciliation divergence;
- nonce uncertainty;
- duplicate exposure.

Action:
- stop new exposure;
- REDUCE_ONLY or FROZEN;
- reconcile.

### SEV-2 — Runtime Degradation
Examples:
- stale feed;
- repeated exchange errors;
- elevated latency;
- event lag;
- resource pressure.

Action:
- THROTTLE or RESTRICTED;
- investigate.

### SEV-3 — Operational Warning
Examples:
- approaching limits;
- elevated reconnect count;
- non-critical resource warning.

Action:
- monitor and investigate.

## 7. Hard Stop Conditions

The system must automatically freeze or disable new exposure for:

- unauthorized order;
- unauthorized transfer request;
- signer mismatch;
- keyset mismatch;
- configuration checksum mismatch;
- daily hard-loss breach;
- capital limit breach;
- protection UNKNOWN/FAILED beyond configured tolerance;
- material position divergence;
- nonce uncertainty;
- corrupted state store;
- unrecoverable event-store failure;
- treasury permission violation.

Automatic rollback is appropriate only when the rollback action itself is safe; otherwise the system must remain frozen and require controlled recovery. Canary rollback is a standard safety mechanism, but trading rollback cannot reverse financial state automatically. citeturn0search0turn0search1

## 8. Alert Rules

Every alert must contain:
- alert_id;
- severity;
- subsystem;
- first_seen;
- last_seen;
- current_state;
- threshold;
- observed_value;
- affected account;
- affected symbol if applicable;
- recommended runbook;
- correlation_id.

Alerts must be deduplicated while preserving occurrence counts.

## 9. Alert Philosophy

Avoid alerting on isolated noise where possible.

Prefer:
- sustained breach;
- repeated failure;
- state transition;
- safety invariant violation.

But security and capital-boundary violations are immediate alerts and must not wait for aggregation.

## 10. Runtime SLO Targets

Exact numeric thresholds are deployment parameters, but the runtime must define targets for:

- market-data freshness;
- event-processing lag;
- decision latency;
- signing latency;
- exchange acknowledgement latency;
- reconciliation freshness;
- protection verification latency;
- alert delivery latency;
- recovery time.

The production configuration must store the target and actual measurement separately.

## 11. Pre-Canary Checklist

Before starting:

### Software
- approved git commit;
- dependency lock verified;
- build artifact verified;
- schema compatibility verified.

### Configuration
- configuration hash verified;
- environment = CANARY;
- production/testnet identities separated;
- risk limits loaded;
- canary capital limit loaded.

### Security
- correct signer/keyset;
- correct epoch;
- treasury keyset inaccessible;
- emergency operator credentials tested;
- kill switch available.

### Trading
- approved symbol list;
- leverage limit;
- order-size limit;
- daily-loss limit;
- protection configuration.

### Infrastructure
- monitoring healthy;
- event store healthy;
- state store healthy;
- clock synchronized;
- exchange connectivity healthy.

## 12. Startup Procedure

1. Start runtime in FROZEN.
2. Verify configuration hash.
3. Verify exchange identity.
4. Verify signer/keyset.
5. Load canonical state.
6. Reconcile account.
7. Reconcile open orders.
8. Reconcile positions.
9. Verify protection.
10. Verify Capital Guard.
11. Verify Permission Guard.
12. Verify monitoring.
13. Run canary self-tests.
14. Enter MICRO_CANARY only after operator approval.

No startup path may directly enable unrestricted production exposure.

## 13. Normal Operating Procedure

During operation:

1. Monitor market-data freshness.
2. Monitor ChanLun state continuity.
3. Monitor decision/event latency.
4. Monitor risk and capital state.
5. Monitor protection.
6. Monitor exchange acknowledgements.
7. Monitor reconciliation.
8. Review alerts.
9. Preserve event evidence.

Operators must not manually alter local position state to hide divergence.

## 14. Kill-Switch Procedure

When a hard-stop condition occurs:

1. Activate independent kill switch.
2. Block new opening OrderIntent.
3. Disable new opening signatures.
4. Cancel permitted opening orders where safe.
5. Preserve reduce-only emergency capability.
6. Verify current position.
7. Verify protection.
8. Snapshot runtime state.
9. Record incident ID.
10. Escalate according to severity.

The strategy process must not be able to clear its own kill switch.

## 15. Incident Procedure

### Phase 1 — Contain
- freeze;
- disable affected capability;
- prevent new exposure.

### Phase 2 — Observe
- snapshot state;
- preserve logs;
- preserve events;
- identify last known-good state.

### Phase 3 — Reconcile
Compare:
- balance;
- position;
- orders;
- fills;
- protection;
- capital reservations;
- nonce.

### Phase 4 — Classify
Determine:
- security;
- execution;
- data;
- risk;
- infrastructure;
- exchange;
- operator error.

### Phase 5 — Recover
Only use the corresponding approved runbook.

### Phase 6 — Verify
Return through:
FROZEN -> RECOVERY -> RECONCILIATION -> VERIFIED -> MICRO_CANARY

## 16. Unknown Order Procedure

If an order submission receives UNKNOWN acknowledgement:

1. Do not blind retry.
2. Query exchange order state.
3. Query fills.
4. Query position.
5. Compare local ledger.
6. Determine whether order exists.
7. Reconcile capital reservation.
8. Emit final outcome.
9. Only then permit subsequent exposure.

## 17. Position Divergence Procedure

If exchange position != canonical local position:

1. Stop new exposure.
2. Verify exchange state.
3. Verify fills.
4. Verify pending orders.
5. Verify protection.
6. Rebuild deterministic local state from authoritative events.
7. Reconcile again.
8. Remain REDUCE_ONLY/FROZEN until verified.

Never manufacture a local fill or position to force equality.

## 18. Protection-Loss Procedure

If protection becomes UNKNOWN or FAILED:

1. Stop opening exposure.
2. Attempt only explicitly authorized protection restoration.
3. If restoration fails, enter REDUCE_ONLY.
4. If exposure cannot be safely protected, enter FROZEN and escalate.
5. Reconcile.
6. Require verification before reopening.

## 19. Signer Failure Procedure

If signer fails:

1. stop new signatures;
2. preserve existing protection;
3. check MPC quorum;
4. determine whether failure is availability or compromise;
5. rotate/recover according to v4.3.3 when necessary;
6. verify signer identity and epoch;
7. run constrained canary;
8. resume only after approval.

## 20. Deployment / Promotion Procedure

Promotion requires:

1. Evidence bundle complete.
2. No unresolved SEV-0/SEV-1 incident.
3. Reconciliation healthy.
4. Protection healthy.
5. Risk state healthy.
6. Signing state healthy.
7. Monitoring healthy.
8. Recovery test passed.
9. Operator review completed.
10. Release approval recorded.

Capital increase occurs only after promotion approval.

## 21. Rollback Procedure

If a release is defective:

1. Freeze new exposure.
2. Preserve current positions/protection.
3. Stop candidate runtime.
4. Restore last known-good software/configuration.
5. Reconcile against exchange.
6. Verify state.
7. Restart in MICRO_CANARY.
8. Observe.
9. Re-qualify before promotion.

Rollback does not reverse already executed trades.

## 22. Evidence Bundle

Every incident and promotion must preserve:

- git commit;
- build ID;
- configuration hash;
- strategy version;
- event schema;
- state schema;
- risk policy;
- signing policy;
- keyset ID/epoch;
- runtime logs;
- event archive;
- order/fill ledger;
- reconciliation report;
- alert history;
- operator actions;
- incident timeline.

## 23. Post-Incident Review

Every SEV-0/SEV-1 incident requires:

- timeline;
- detection method;
- affected state;
- root cause;
- contributing factors;
- containment;
- financial impact;
- security impact;
- recovery;
- missing controls;
- corrective actions;
- regression test;
- runbook update.

Do not close the incident until the corrective action has an owner and verification method.

## 24. Operational Invariants

I1 — Unknown is never treated as healthy.

I2 — FROZEN cannot self-clear.

I3 — Operators cannot bypass Capital Guard.

I4 — Operators cannot bypass Signing Policy.

I5 — Trading operators cannot authorize treasury withdrawal.

I6 — Rollback cannot reverse financial state automatically.

I7 — Local state cannot be edited to hide exchange divergence.

I8 — Every production action has a correlation chain.

I9 — Every promotion has evidence.

I10 — Every SEV-0/SEV-1 incident has a regression test or explicit risk acceptance.

## 25. Exit Criteria

v4.4.1 is complete only when:

1. Dashboards cover all critical subsystems.
2. Severity and alert rules are implemented.
3. Hard-stop conditions are executable.
4. Startup checklist is executable.
5. Kill-switch procedure is tested.
6. Unknown-order procedure is tested.
7. Position-divergence procedure is tested.
8. Protection-loss procedure is tested.
9. Signer-failure procedure is tested.
10. Promotion/rollback procedure is tested.
11. Evidence bundles are reproducible.
12. SEV-0/SEV-1 incident drills are completed.

## 26. Scope Boundary

v4.4.1 does not change:
- ChanLun geometry;
- Decision Engine logic;
- position-sizing formulas;
- stop-anchor rules;
- exchange trading strategy.

It operationalizes v4.4.0.
