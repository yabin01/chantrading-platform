# v4.4.20 — Order Lifecycle & UNKNOWN Recovery

## 1. Objective
v4.4.20 converts exchange order responses into a canonical lifecycle and defines the mandatory recovery path for uncertain execution.

## 2. Official Status Evidence
The official Hyperliquid SDK exposes orderStatus queries by OID and Cloid. citeturn0search1
The documented order-status vocabulary includes open, filled, canceled, triggered, rejected, marginCanceled, reduceOnlyCanceled and other explicit cancellation/rejection reasons. A missing OID can return unknownOid. citeturn0search4

## 3. Canonical Lifecycle
CREATED → SUBMITTING → SUBMITTED → ACKNOWLEDGED → RESTING → PARTIAL → FILLED
Terminal branches: CANCELED, REJECTED, EXPIRED.
Uncertain branch: UNKNOWN → QUERY → RESOLVED.

## 4. Core Rule
UNKNOWN is not REJECTED. UNKNOWN means the system does not yet know whether the exchange accepted, rejected, rested, partially filled, or filled the order.
Therefore: UNKNOWN → no blind retry → authoritative query → resolve state.

## 5. Retry Policy
Retry is allowed only when the canonical state explicitly permits it. UNKNOWN is never retryable by itself.

## 6. Terminal State Protection
Once an order is FILLED, CANCELED, REJECTED, or EXPIRED, the lifecycle cannot be moved to another terminal state.

## 7. OID and Client ID
The native OID is authoritative after exchange acknowledgement. The client order ID remains a tracing/idempotency identity. OrderStatusResolver supports both query paths.

## 8. Partial Fills
PARTIAL is non-terminal. The order remains observable until fully filled, canceled, rejected, or expired. Future fill reconciliation must accumulate fills rather than infer filled quantity only from order status.

## 9. Triggered
Hyperliquid can report a triggered order state. The canonical lifecycle maps triggered to ACKNOWLEDGED pending subsequent resting/fill state. Detailed trigger/child-order semantics remain part of later order-type implementation.

## 10. Rejection Semantics
Venue-specific rejection reasons should remain available for risk and diagnostics, including insufficient margin, reduce-only rejection, post-only immediate match, IOC unable to match, invalid tick price, minimum trade notional and oracle rejection. citeturn0search4

## 11. UNKNOWN Recovery
Mutation timeout/error → UNKNOWN → query by OID/Cloid → resolve to open/resting, filled, canceled or rejected.
If the query itself fails, UNKNOWN remains UNKNOWN. No order retry occurs until uncertainty is resolved.

## 12. WebSocket Interaction
WebSocket order updates can accelerate resolution. REST orderStatus remains the authoritative recovery query after execution uncertainty.

## 13. Tests
Added tests for UNKNOWN non-retryability, terminal FILLED behavior, OID retention, and status mapping for open, filled, rejected and unknownOid.

## 14. Next Step
v4.4.21 should implement full order/position reconciliation across local lifecycle, WebSocket events, openOrders, orderStatus, userFills and clearinghouseState.
The reconciliation output must identify missing local orders, missing venue orders, unprocessed fills, duplicate fills, position drift and impossible lifecycle transitions.

## 15. Production Boundary
v4.4.20 does not authorize autonomous retry or live trading. It establishes the canonical execution-state machine required before reconciliation and production certification.
