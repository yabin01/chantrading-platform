# v4.4.21 — Hyperliquid Order & Position Reconciliation

## 1. Objective

v4.4.21 introduces deterministic reconciliation between local execution state and Hyperliquid authoritative state.

## 2. Venue Data Sources

The Hyperliquid WebSocket API provides clearinghouseState, openOrders, orderUpdates, userFills and userEvents subscriptions. Streaming user fills begin with a snapshot and then continue with incremental updates. citeturn0search0

The official Python SDK exposes user_state/clearinghouseState, open_orders, user_fills and orderStatus through the Info API. citeturn0search3

Hyperliquid explicitly states that data missed during a WebSocket reconnect can be recovered from reconnect snapshots or corresponding Info requests. citeturn0search1

## 3. Reconciliation Domains

The engine compares three primary domains:

1. Orders
2. Fills
3. Position

A later extension may add:
- margin;
- funding;
- ledger;
- liquidation;
- balances.

## 4. Order Reconciliation

The engine compares local order IDs against venue open orders.

Detected drift:
- MISSING_VENUE_ORDER: local order is absent from venue open orders;
- MISSING_LOCAL_ORDER: venue has an open order unknown locally.

A missing venue order is not automatically considered canceled because it may already be filled, rejected, expired, or otherwise terminal. It requires orderStatus/history resolution.

## 5. Fill Reconciliation

Fill identity uses:
1. tid when available;
2. hash + oid + time fallback.

The engine detects:
- UNPROCESSED_FILL;
- DUPLICATE_FILL.

A fill must be applied exactly once to the local execution ledger.

## 6. Position Reconciliation

Local and venue position sizes are compared using Decimal.

Any difference beyond the configured tolerance produces POSITION_DRIFT.

Position drift blocks autonomous trading until resolved.

## 7. Report

ReconciliationReport contains:
- consistent boolean;
- immutable tuple of ReconciliationDrift records.

The report does not mutate local state.

This is intentional: detection and repair remain separate operations.

## 8. Repair Principle

The reconciliation engine must never silently overwrite local state.

The required sequence is:

detect drift
→ classify
→ obtain authoritative evidence
→ generate repair event
→ apply through State Store
→ re-run reconciliation
→ certify consistency.

## 9. Safety Gate

If any critical drift exists:
- no new production order authorization;
- no blind order retry;
- no position-changing action.

The system enters a reconciliation-required condition.

## 10. Order/Fills Interaction

An order absent from openOrders may still have a fill.

Therefore order reconciliation must not conclude CANCELED merely from absence in openOrders.

Resolution should use:
- orderStatus;
- historicalOrders when needed;
- userFills.

## 11. Position Interaction

A position discrepancy is stronger evidence than an order-status discrepancy for execution safety.

If local position differs from authoritative clearinghouseState, the local execution state must be treated as unsafe for autonomous position changes.

## 12. Rate-Limit Consideration

Hyperliquid documents that clearinghouseState and orderStatus have lower Info request weights than many user-history endpoints, while userFills can carry additional weight based on returned items. citeturn0search4

The production reconciliation scheduler must therefore avoid repeatedly pulling large fill histories when a smaller authoritative query is sufficient.

## 13. Tests

Added tests for:
- missing venue/local orders;
- duplicate fills;
- unprocessed fills;
- position drift;
- fully consistent state.

## 14. Current Limitation

v4.4.21 implements drift detection but not automatic repair.

It does not:
- cancel unknown orders;
- recreate orders;
- alter positions;
- mark fills as processed;
- overwrite State Store data.

Repair will be event-driven and auditable.

## 15. Next Step

v4.4.22 should implement failure injection and recovery certification.

It should simulate:
- WebSocket disconnect;
- missed order update;
- missed fill;
- duplicate fill;
- delayed REST response;
- stale snapshot;
- timeout after signed order;
- UNKNOWN order;
- position drift;
- reconnect during order submission.

The objective is to prove that the execution layer fails safe rather than merely functioning in the happy path.

## 16. Production Boundary

v4.4.21 remains a read/compare layer.

It does not autonomously repair or mutate production trading state.
