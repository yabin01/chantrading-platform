# v4.4.22 — Failure Injection & Recovery Certification

## 1. Objective

v4.4.22 establishes an explicit failure-injection matrix for the Hyperliquid execution boundary. The objective is not to prove that the happy path works; it is to prove that failure causes the system to fail safe.

## 2. Failure Matrix

| Scenario | Expected behavior | Trading |
|---|---|---|
| WS_DISCONNECT | enter RESYNCING | BLOCK |
| MISSED_ORDER_UPDATE | reconcile against REST | BLOCK until resolved |
| MISSED_FILL | recover fill from authoritative source | BLOCK until resolved |
| DUPLICATE_FILL | deduplicate by fill identity | BLOCK if unresolved |
| REST_TIMEOUT | retain prior uncertainty | BLOCK |
| SIGNED_ORDER_TIMEOUT | enter UNKNOWN | BLOCK retry |
| UNKNOWN_ORDER | query authoritative status | BLOCK |
| POSITION_DRIFT | reconcile position | BLOCK |

## 3. Core Safety Invariant

For every critical failure, trading authorization must become false. A failure may not silently fall through to the normal Decision → Order path.

## 4. Signed Order Timeout

Canonical order → signing → exchange request → timeout → UNKNOWN.

The system must not infer rejection, generate a second signed mutation, or retry blindly. It must query authoritative order state.

## 5. WebSocket Failure

READY → RESYNCING → reconnect → subscription replay → authoritative snapshot → reconciliation → READY.

No production mutation is authorized between RESYNCING and READY.

## 6. Missed Fill

A missed fill is execution-state uncertainty. The system must obtain the fill through an authoritative recovery path before restoring autonomous trading. Local order status alone is insufficient to reconstruct all execution quantities.

## 7. Duplicate Fill

Duplicate fills must be detected using a stable fill identity. The current reconciliation implementation uses tid where available and a deterministic fallback when it is absent. A duplicate must not be applied twice to the execution ledger.

## 8. Position Drift

If local_position differs from venue_position, the system enters a reconciliation-required state. It must not attempt to trade its way back to the expected position automatically. The first operation is diagnosis and authoritative reconciliation.

## 9. REST Failure

If REST is required to resolve uncertainty and the request fails, UNKNOWN remains UNKNOWN. The system must not downgrade the uncertainty into a rejection merely because the query failed.

## 10. Failure-Injection Contract

The test harness currently defines WS_DISCONNECT, MISSED_ORDER_UPDATE, MISSED_FILL, DUPLICATE_FILL, REST_TIMEOUT, SIGNED_ORDER_TIMEOUT, UNKNOWN_ORDER and POSITION_DRIFT. Every listed case is marked as trading-blocking.

## 11. Certification Principle

A recovery test passes only if: (1) the failure is detected; (2) the unsafe state is entered; (3) trading authorization is removed; (4) recovery obtains authoritative evidence; (5) state is reconciled; and (6) trading authorization is restored only after consistency.

## 12. Current Scope

v4.4.22 provides the failure matrix and fail-safe assertions. It does not yet execute full end-to-end network simulations. Remaining certification work includes real WebSocket reconnect tests, REST timeout harnesses, signed request timeout simulation, event replay after reconnect, full position reconciliation, exchange testnet integration and crash/restart recovery.

## 13. Next Step

v4.4.23 should be the Production Certification Specification, defining testnet certification, mainnet dry-run, signing isolation, recovery drills, reconciliation certification, kill switch, runtime health gate, deployment checklist, rollback and audit evidence.

## 14. Production Boundary

No failure-injection test enables autonomous mainnet trading. The purpose of v4.4.22 is to establish a measurable fail-safe contract before production certification.
