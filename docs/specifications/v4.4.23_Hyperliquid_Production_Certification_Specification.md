# v4.4.23 — Hyperliquid Production Certification Specification

## 1. Objective

v4.4.23 defines the formal certification gates required before the Hyperliquid adapter can be considered eligible for production authorization.

Certification is a gate, not an execution command. Passing certification does not itself submit an order.

## 2. Network Separation

Hyperliquid exposes separate WebSocket endpoints for Mainnet and Testnet. The adapter must carry the network explicitly and must never infer Mainnet from an absent or default configuration. citeturn0search2

Required rule:

TESTNET != MAINNET

A Testnet certification can validate the runtime but cannot authorize Mainnet production execution.

## 3. Certification Gates

The implementation defines seven mandatory gates:

- TESTS
- RECONCILIATION
- RECOVERY
- SIGNING_ISOLATION
- KILL_SWITCH
- HEALTH
- CONFIGURATION

All gates are required for Mainnet production authorization.

## 4. Test Gate

Must prove:
- unit tests pass;
- state-machine tests pass;
- order mapping tests pass;
- UNKNOWN recovery tests pass;
- reconciliation tests pass;
- failure-injection assertions pass.

## 5. Reconciliation Gate

Must prove that:
- local orders reconcile with venue state;
- fills are processed exactly once;
- position size matches authoritative venue state;
- unresolved drift blocks trading.

The venue provides openOrders, orderStatus, userFills and clearinghouseState data paths suitable for these checks. citeturn0search1turn0search5

## 6. Recovery Gate

Must execute and pass drills for:
- WebSocket disconnect;
- reconnect;
- subscription recovery;
- missed data;
- REST recovery;
- signed-order timeout;
- UNKNOWN order;
- crash/restart.

Hyperliquid explicitly instructs automated users to handle server-side disconnects gracefully and states that missed data can be recovered from reconnect snapshots or corresponding Info requests. citeturn0search2

## 7. Signing Isolation Gate

The production trading process must not contain raw private keys in the ChanTrading domain.

Accepted production boundary:

ChanTrading → SigningGateway → isolated signer → signed action

The signer may be implemented as an API-wallet, isolated signing process, MPC or HSM-backed component.

## 8. Kill Switch Gate

A production deployment must have an independent kill switch capable of preventing new position-changing actions.

Kill switch activation must override normal Decision Engine authorization.

Existing positions are not automatically closed merely because the kill switch is activated.

## 9. Health Gate

Trading authorization requires:
- WebSocket healthy;
- required subscriptions active;
- no unresolved RESYNCING state;
- no stale market/user stream;
- no unresolved reconciliation drift;
- clock within configured bounds.

Hyperliquid documents a 60-second server connection timeout when no messages are sent and supports ping/pong heartbeats. citeturn0search0

## 10. Configuration Gate

The runtime must explicitly validate:
- network;
- account address;
- instrument universe;
- asset IDs;
- leverage/risk configuration;
- signer identity;
- API endpoint;
- emergency controls.

No production startup may rely on silent defaults for these fields.

## 11. Rate-Limit Gate

The runtime must respect venue limits.

Current documented limits include:
- 1200 weighted REST requests per minute per IP;
- maximum 10 WebSocket connections;
- maximum 30 new WebSocket connections per minute;
- maximum 1000 subscriptions;
- maximum 100 simultaneous WebSocket post requests.

The adapter must use bounded reconnects and avoid reconciliation loops that can amplify API load. citeturn0search4

## 12. Mainnet Authorization

Production authorization is represented as:

Network == MAINNET
AND
all certification gates PASS

Anything else results in:

PRODUCTION_AUTHORIZED = false

## 13. Go / No-Go Evidence

A certification package should contain:
- commit SHA;
- test report;
- failure-injection report;
- reconciliation report;
- recovery drill report;
- signer-isolation evidence;
- kill-switch test evidence;
- configuration snapshot with secrets removed;
- runtime health report;
- rollback procedure.

## 14. Rollback

Rollback must be able to:
- stop new orders;
- preserve audit logs;
- preserve fills and position evidence;
- restore a previously certified application version;
- force reconciliation before re-enabling trading.

## 15. Dry-Run Requirement

Before Mainnet authorization, the complete runtime should operate in a no-mutation mode in which Decision Engine signals, risk checks, order mappings, signing intent and reconciliation are exercised without submitting position-changing production actions.

## 16. Certification Result

The code exposes a deterministic certification result containing:
- network;
- passed gates;
- failed gates;
- certified boolean.

Only a fully certified Mainnet result can satisfy the production authorization predicate.

## 17. Important Boundary

v4.4.23 does not enable autonomous Mainnet trading by itself.

It establishes the formal gate required before such authorization can be granted.

## 18. Next Phase

After v4.4.23, the project should move from specification-driven implementation to controlled Testnet Integration:

1. connect real Testnet market data;
2. validate 1m candle continuity;
3. validate ChanLun state replay;
4. validate order lifecycle with testnet orders;
5. validate reconciliation after fills;
6. execute failure drills;
7. run extended paper trading;
8. only then consider a separately approved Mainnet dry-run.
