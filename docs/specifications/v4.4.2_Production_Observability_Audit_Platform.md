# v4.4.2 — Production Observability & Audit Platform

## 1. Objective

v4.4.2 defines the unified observability and audit layer for the production ChanLun Trading Agent.

The objective is to make every material production action observable, attributable, queryable, correlated, replayable and auditable.

The observability layer MUST NOT modify trading decisions or create a second execution path.

## 2. Observability Model

The platform uses four complementary signal classes:

1. Events — canonical business/state transitions.
2. Traces — execution path and latency.
3. Metrics — continuous quantitative health measurements.
4. Logs — structured diagnostic records.

OpenTelemetry provides a vendor-neutral framework for traces, metrics and logs and supports shared context for correlation across these signals. citeturn0search1turn0search8

Events remain the system-of-record for deterministic business state. Observability telemetry is derived from or correlated with those events.

## 3. Core Principle

Event Store = Truth
Observability = Evidence + Navigation
Exchange = External Authority for Execution State

No metric, dashboard, log line or trace span may be treated as the canonical source of trading state.

If observability data conflicts with the event/state store:
- preserve both;
- raise an integrity alert;
- reconcile against the authoritative source.

## 5. Global Correlation Identity

Every runtime action SHOULD carry:
- trace_id;
- span_id;
- event_id;
- correlation_id;
- causation_id;
- aggregate_id;
- runtime_instance_id;
- build_id;
- config_hash;
- schema_version.

causation_id identifies the immediate event that caused the current event.

correlation_id groups the larger business workflow.

This allows both causal traversal and workflow-level investigation.

## 6. Event vs Trace

### Event
Represents a durable business/state transition.

Examples:
- FRACTAL_COMPLETED
- BI_CONFIRMED
- DECISION_CREATED
- ORDER_INTENT_CREATED
- SIGNING_REQUESTED
- ORDER_SUBMITTED
- FILL_CONFIRMED
- POSITION_RECONCILED

### Trace
Represents execution of an operation.

Examples:
- process_candle
- evaluate_decision
- risk_check
- create_order
- sign_payload
- submit_order
- reconcile_position

A trace may contain multiple events. An event may be linked to one or more spans.

## 10. Metric Rules

Metrics MUST be:
- low-cardinality where possible;
- bounded in label values;
- safe from secret leakage;
- stable across software versions.

Do not use raw wallet addresses, arbitrary order IDs, raw error strings, full configuration objects or user-controlled unbounded strings as ordinary time-series labels.

High-cardinality identifiers belong in events/traces/logs.

## 11. Structured Logs

Production logs MUST use structured records.

Required fields:
- timestamp;
- severity;
- service;
- build_id;
- environment;
- event_name;
- event_id;
- trace_id;
- span_id;
- correlation_id;
- causation_id;
- symbol;
- account_id_hash;
- message;
- error_code when applicable.

OpenTelemetry's log model supports timestamp, trace/span context, resource information, attributes and event names, which fits this structured audit approach. citeturn0search3

## 12. Sensitive Data Policy

Never emit:
- private keys;
- MPC shares;
- seed phrases;
- API secrets;
- authentication tokens;
- raw withdrawal credentials.

Avoid unnecessary full wallet addresses, personally identifying information, internal secret material and raw signed payloads.

If a signed payload is required for audit, store a cryptographic hash plus access-controlled evidence rather than exposing sensitive material in ordinary logs.

## 15. Audit Integrity

Audit records MUST support tamper evidence.

Recommended mechanisms:
- append-only storage;
- monotonically increasing sequence;
- event hash;
- previous-event hash;
- periodic Merkle/checkpoint hash;
- immutable archive.

A practical record chain is H_n = SHA256(H_(n-1) || canonical_event_n). The exact hashing algorithm and serialization format are implementation parameters but MUST be versioned.

## 18. Time Model

Store timestamps with:
- UTC wall-clock timestamp;
- monotonic duration measurement where supported;
- source timestamp;
- observed timestamp.

Do not infer event ordering solely from wall-clock time.

For causal ordering, prefer:
1. event sequence;
2. causation_id;
3. durable event cursor;
4. source sequence;
5. timestamps as supporting evidence.

## 19. Trace Sampling

Financially material operations MUST remain traceable.

Do not probabilistically sample away:
- order creation;
- signing;
- order submission;
- fill;
- reconciliation divergence;
- risk denial;
- permission violation;
- kill switch;
- recovery.

High-volume market-data spans may use controlled sampling, while canonical events remain fully retained.

## 20. Retention Classes

### Class A — Financial / Security Audit
Long-term retention according to regulatory, legal and business requirements.

Includes:
- trades;
- fills;
- positions;
- signing;
- treasury;
- key lifecycle;
- security incidents.

### Class B — Operational Evidence
Medium/long retention.

Includes:
- traces;
- structured logs;
- incident evidence.

### Class C — High-Volume Telemetry
Shorter retention.

Includes:
- debug logs;
- high-frequency performance samples;
- verbose market-data diagnostics.

Retention policy must be explicit and versioned.

## 22. Failure Handling

Observability failure MUST NOT silently become trading failure unless explicitly configured by safety policy.

### Audit path failure
For security-critical actions:
- fail closed where durable audit evidence is required before authorization.

### Metrics backend failure
Trading may continue if core safety controls remain healthy.

### Trace backend failure
Trading may continue if canonical events remain durable.

### Event Store failure
Trading must stop or enter the configured safe mode.

### State Store failure
Trading must stop or enter FROZEN according to v4.4.0/v4.4.1.

## 23. Observability Self-Monitoring

The observability system monitors itself:
- telemetry export failures;
- collector queue depth;
- dropped spans;
- dropped logs;
- metric ingestion lag;
- event-store lag;
- clock drift;
- storage capacity;
- archive integrity.

A dashboard showing no alerts is not sufficient if telemetry ingestion itself is broken.

## 24. Audit Query Requirements

Operators must be able to query:

### By order
order_id -> all related events/traces/logs/fills/reconciliation.

### By decision
decision_id -> ChanLun state -> risk -> OrderIntent -> execution.

### By position
position_id -> entry -> fills -> protection -> exit -> reconciliation.

### By incident
incident_id -> alerts -> timeline -> actions -> evidence -> recovery.

### By signer
keyset_epoch -> signatures -> failures -> rotation -> incidents.

### By configuration
config_hash -> deployments -> decisions -> orders -> incidents.

## 25. Deterministic Replay Integration

Observability must integrate with v3.5.2 State Store / Deterministic Replay.

For a selected event range, the platform must be able to produce:
- original event stream;
- reconstructed state;
- decision outputs;
- expected OrderIntent;
- actual OrderIntent;
- execution result;
- divergence report.

Replay must never submit live orders.

## 26. Decision-to-Execution Audit

For every real opening/closing action, the audit view should answer:

1. What market event caused it?
2. What was the ChanLun state?
3. Which fractal/Bi/segment state was active?
4. What Decision was produced?
5. Why was the decision accepted?
6. What risk checks passed?
7. What capital was reserved?
8. What permission checks passed?
9. Which signer/keyset signed it?
10. What exchange order was submitted?
11. What fills occurred?
12. What position resulted?
13. Was protection active?
14. Did reconciliation converge?

If any answer cannot be reconstructed, the observability implementation is incomplete.

## 27. Security Invariants

I1 — Observability cannot create trading authority.
I2 — Telemetry cannot bypass risk or permission controls.
I3 — Sensitive key material never enters ordinary telemetry.
I4 — Financially material actions remain fully traceable.
I5 — Audit records are append-only and tamper-evident.
I6 — Event Store remains the canonical business-state source.
I7 — Exchange remains authoritative for external execution state.
I8 — Unknown states remain explicitly represented.
I9 — Replay never produces live financial side effects.
I10 — Observability failure cannot silently disable safety controls.

## 28. Exit Criteria

v4.4.2 passes when:
1. Every material trading lifecycle has a correlation chain.
2. Events, traces, metrics and logs can be cross-navigated.
3. Structured logs are implemented.
4. Security-sensitive actions have audit records.
5. Audit tamper evidence is implemented.
6. Sensitive credentials are excluded from telemetry.
7. Incident evidence bundles are reproducible.
8. Decision-to-execution reconstruction works.
9. Replay integration works without live side effects.
10. Observability failure modes are tested.
11. Retention classes are configured.
12. Self-monitoring detects telemetry pipeline failure.

## 29. Scope Boundary

v4.4.2 does not change ChanLun rules, Decision Engine semantics, risk formulas, execution strategy or capital allocation policy.

It establishes the production observability and audit layer.
