# v4.4.3 — Production Replay & Forensic Debugging Engine

## 1. Objective

v4.4.3 defines the forensic replay layer that reconstructs historical runtime behavior from authoritative event/state data and identifies the first deterministic divergence between expected and observed behavior.

The engine is designed to answer:

> Given the exact historical inputs and runtime versions, what should the ChanLun Trading Agent have done, what did it actually do, and where did the two paths first diverge?

Replay is diagnostic only. It MUST never create live financial side effects.

## 2. Scope

Replay covers:

Market Data
-> ChanLun State
-> Fractal
-> Bi
-> Segment
-> Center State
-> Decision
-> Risk
-> Capital Reservation
-> Permission
-> OrderIntent
-> Execution Observation
-> Position
-> Reconciliation

It does not alter historical records.

## 3. Authority Hierarchy

For forensic reconstruction:

1. Immutable event store
2. Versioned state snapshots
3. Exchange execution records
4. Reconciliation records
5. Observability telemetry
6. Diagnostic logs

Observability data helps explain behavior but does not silently replace authoritative state.

## 4. Replay Modes

### EXACT_REPLAY

Reconstruct the original runtime state using the original:
- event sequence;
- schema versions;
- strategy build;
- configuration;
- risk policy;
- signing policy metadata.

### WHAT_IF_REPLAY

Replace explicitly selected parameters or components and compare outputs.

This mode MUST be clearly marked as non-historical.

### DIFFERENTIAL_REPLAY

Run two versions against the same immutable input stream.

Example:

Production build A
vs
Candidate build B

### INCIDENT_REPLAY

Replay a bounded incident window with additional diagnostics.

## 5. Replay Isolation

Replay runtime MUST have:
- no exchange trading credentials;
- no signing capability;
- no treasury access;
- no production write authority;
- no order submission path.

Network egress should be disabled by default.

If external reference data is required, it must be immutable, versioned and explicitly declared as an input.

## 6. Replay Package

Every replay requires a manifest:

- replay_id;
- source_event_range;
- source_snapshot_ids;
- event_schema_version;
- state_schema_version;
- strategy_version;
- build_id;
- config_hash;
- risk_policy_version;
- exchange_adapter_version;
- replay_engine_version;
- input_data_hashes;
- created_at;
- mode.

The manifest is immutable after replay creation.

## 7. Deterministic Input

The replay engine must consume the exact historical event stream.

For 1M ChanLun processing this includes, where available:
- candle timestamp;
- OHLCV;
- market-data sequence;
- source/exchange timestamp;
- normalization result;
- data-quality state.

No future candle may be visible to a replay step.

## 8. Causal Ordering

Replay ordering follows:

1. durable event sequence;
2. causation relationship;
3. source sequence;
4. deterministic tie-breaker.

Wall-clock timestamps are evidence, not the sole ordering mechanism.

## 9. State Reconstruction

At replay start:

Snapshot
+
Event Range
=
Reconstructed State

The engine must validate:
- snapshot schema compatibility;
- event schema compatibility;
- sequence continuity;
- checksum/hash integrity.

If continuity cannot be proven, replay is marked INCOMPLETE rather than silently continuing.

## 10. ChanLun Reconstruction

The replay engine must reproduce the same state transitions used by the production ChanLun engine.

Required observables include:
- normalized K-line state;
- completed fractals;
- invalid/intermediate fractals;
- Bi state;
- Segment state;
- Center state;
- current Ai state;
- divergence-related state;
- completed decision trigger.

The replay report must identify the first ChanLun state transition that differs between two builds.

## 11. Decision Reconstruction

For every decision point record:

- decision_id;
- input state hash;
- ChanLun state version;
- Decision Engine version;
- decision type;
- decision reason code;
- relevant state references;
- risk result;
- final action.

A HOLD decision is a first-class result and must not be treated as missing output.

## 12. Risk Reconstruction

Replay must reproduce:
- position state;
- capital state;
- exposure;
- leverage;
- limits;
- reservation;
- risk decision.

If a risk calculation depends on external state, that dependency must be captured as a versioned replay input.

## 13. Execution Reconstruction

Replay distinguishes:

EXPECTED:
What the deterministic decision/risk pipeline produced.

OBSERVED:
What the live execution and exchange records show.

The replay engine must never pretend that an observed fill was generated by replay.

## 14. First-Divergence Algorithm

Given expected sequence E and observed sequence O:

1. Normalize both into comparable canonical records.
2. Compare event type.
3. Compare causal parent.
4. Compare state hash.
5. Compare decision output.
6. Compare risk output.
7. Compare OrderIntent.
8. Compare execution result.
9. Stop at the earliest material mismatch.
10. Classify the divergence.

The first divergence is the primary forensic finding.

Later differences are downstream consequences until proven otherwise.

## 15. Divergence Classes

### DATA_DIVERGENCE
Input candle/market state differs.

### STATE_DIVERGENCE
Same input but internal state differs.

### DECISION_DIVERGENCE
Same state but Decision output differs.

### RISK_DIVERGENCE
Same decision but risk result differs.

### EXECUTION_DIVERGENCE
Same OrderIntent but exchange outcome differs.

### RECONCILIATION_DIVERGENCE
Execution agrees but local/external state reconciliation differs.

### OBSERVABILITY_DIVERGENCE
System behavior is consistent but telemetry is incomplete/inconsistent.

## 16. Divergence Severity

CRITICAL:
- unauthorized financial action;
- incorrect position reconstruction;
- incorrect risk boundary;
- signing/execution mismatch.

HIGH:
- incorrect Decision;
- incorrect ChanLun state;
- protection mismatch.

MEDIUM:
- telemetry inconsistency;
- latency classification issue.

LOW:
- diagnostic metadata mismatch with no behavioral effect.

Severity does not replace incident severity rules in v4.4.1.

## 17. State Hashing

Canonical state objects should produce versioned hashes.

Example:

state_hash =
HASH(
  schema_version
  + canonical_serialization(state)
)

The serialization rules MUST be deterministic:
- stable field ordering;
- explicit numeric representation;
- explicit null handling;
- explicit enum representation;
- no environment-dependent fields.

## 18. Differential Replay

For build A and build B:

Same Event Stream
       |
       +--> Engine A
       |
       +--> Engine B
       |
       v
Compare State / Decision / Risk / Intent

The report must identify:
- first divergent event;
- first divergent state;
- changed fields;
- old value;
- new value;
- downstream effects.

## 19. ChanLun-Specific Forensics

For each divergence involving ChanLun, expose:

- candle index;
- candle timestamp;
- local fractal candidates;
- completed fractal;
- invalidated fractal;
- Bi state before/after;
- Segment state before/after;
- Center membership;
- Ai state;
- MACD input where used;
- optional EMA input where configured;
- Decision trigger.

The forensic view must preserve the project's 1M-only operating scope.

It must not silently introduce higher-timeframe interpretation.

## 20. No-Lookahead Verification

Replay must verify that every decision at time T only consumed data available at or before T.

For each decision:

max_input_timestamp <= decision_timestamp

Any violation is classified as:

LOOKAHEAD_BIAS

and the replay is failed.

## 21. Same-Candle Verification

Where stop/execution logic depends on 1M OHLC, replay must preserve the exact configured same-candle interpretation.

The engine must not invent intra-candle ordering that is unavailable in the recorded data.

If multiple intra-candle outcomes are possible from OHLC alone, mark the result AMBIGUOUS rather than selecting one without a declared rule.

## 26. Incident Integration

For SEV-0/SEV-1 incidents:

Incident
-> Evidence Bundle
-> Replay Manifest
-> EXACT_REPLAY
-> First Divergence
-> Root Cause
-> Regression Test
-> Runbook Update

Replay output becomes part of the incident evidence bundle.

## 27. Regression Corpus

Every confirmed production bug should generate a deterministic replay case containing:

- minimal source event range;
- expected result;
- failure result;
- fixed result;
- regression-test identifier.

The corpus becomes a permanent protection against recurrence.

## 28. Security Invariants

I1 — Replay has no trading authority.
I2 — Replay has no signing authority.
I3 — Replay has no treasury authority.
I4 — Replay cannot mutate authoritative production events.
I5 — Replay cannot consume future inputs.
I6 — EXACT_REPLAY preserves historical versions.
I7 — WHAT_IF_REPLAY is clearly separated from historical truth.
I8 — Ambiguous OHLC-only outcomes remain explicitly ambiguous.
I9 — First divergence is distinguished from downstream consequences.
I10 — Replay results are themselves versioned and hashable.

## 29. Exit Criteria

v4.4.3 passes when:

1. EXACT_REPLAY reconstructs a known historical window.
2. No-lookahead validation works.
3. State hashes are deterministic.
4. Differential replay identifies a known injected divergence.
5. ChanLun-specific state differences are inspectable.
6. Decision and risk differences are traceable.
7. Execution differences are separated from strategy differences.
8. Ambiguous same-candle cases are not silently resolved.
9. Incident replay integrates with evidence bundles.
10. Confirmed bugs can become permanent regression cases.
11. Replay has no live financial side effects.
12. Replay results are reproducible from the manifest.

## 30. Scope Boundary

v4.4.3 does not change ChanLun geometry, Decision Engine semantics, risk formulas, stop rules or execution policy.

It provides the forensic reconstruction and differential-debugging infrastructure required to validate those components.
