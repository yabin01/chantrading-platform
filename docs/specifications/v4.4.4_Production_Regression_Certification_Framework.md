# v4.4.4 — Production Regression & Certification Framework

## 1. Objective

v4.4.4 defines the automated regression, certification and release-gating framework for the ChanLun Trading Agent.

Its purpose is to ensure that a code, configuration, schema or policy change cannot silently alter certified behavior and then enter Canary.

The framework combines:
- deterministic replay;
- regression corpus;
- invariant testing;
- differential testing;
- security testing;
- execution-contract testing;
- certification evidence;
- release gates.

## 2. Certification Principle

A build is not production-certified because it compiles, unit tests pass, backtests are profitable, or a small canary succeeds.

A build is certified only when all mandatory correctness, safety, reproducibility and security gates pass.

Profitability is a separate performance dimension and MUST NOT override a failed safety gate.

## 3. Certification Pipeline

Source Change
-> Static Validation
-> Unit Tests
-> Deterministic Replay
-> Regression Corpus
-> Differential Replay
-> Risk / Execution Contract Tests
-> Security Invariant Tests
-> Integration Tests
-> Certification Evidence
-> Canary Approval

Any mandatory gate failure => NOT_CERTIFIED.

## 4. Certification States

DRAFT -> TESTING -> PASSED -> CERTIFIED -> CANARY_APPROVED -> PRODUCTION_APPROVED

Failure transitions to FAILED or BLOCKED.

A build cannot skip CERTIFIED.

## 5. Change Classification

### CLASS_A — Documentation / Non-Executable
Examples:
- documentation;
- comments;
- non-runtime metadata.

May require documentation validation only.

### CLASS_B — Observability
Examples:
- dashboards;
- telemetry;
- log fields.

Must pass telemetry compatibility tests.

### CLASS_C — Runtime Non-Strategy
Examples:
- infrastructure;
- queue;
- state persistence;
- exchange adapter.

Requires runtime and replay compatibility tests.

### CLASS_D — Strategy / ChanLun
Examples:
- fractal;
- Bi;
- Segment;
- Center;
- divergence;
- Decision Engine.

Requires full ChanLun regression and differential replay.

### CLASS_E — Risk / Security / Execution
Examples:
- risk limits;
- stop logic;
- signing;
- capital guard;
- permission;
- order manager.

Requires full safety certification and cannot bypass mandatory gates.

## 6. Regression Corpus

The Regression Corpus is the permanent set of certified historical and synthetic cases.

Each case contains:
- case_id;
- category;
- source event range;
- expected state;
- expected decision;
- expected risk result;
- expected OrderIntent;
- expected safety invariants;
- build that certified it;
- corpus version.

The corpus itself is versioned.

## 8. Human-Validated Cases

Human-labeled canonical examples are supported as a dedicated corpus layer.

They MUST contain:
- case_id;
- chart/event window;
- human annotation;
- annotation version;
- rationale;
- expected structural state;
- reviewer identity;
- review status.

Human annotations do not replace deterministic rules.

They provide explicit reference cases for validating implementation against the project's intended interpretation.

## 9. Standard Case Lifecycle

PROPOSED -> ANNOTATED -> REVIEWED -> CERTIFIED -> REGRESSION -> RETIRED

A retired case remains historically queryable.

## 10. Golden Outputs

Every certified regression case has a Golden Output.

Golden Output may include:
- state hash;
- state transition sequence;
- Decision;
- reason code;
- risk result;
- OrderIntent;
- invariant results.

Golden outputs are immutable once certified.

Changing a Golden Output requires:
- new corpus version;
- explicit rationale;
- review;
- migration evidence.

A code change MUST NOT silently rewrite Golden Outputs.

## 11. Determinism Gate

For each deterministic replay case:

Run A
Run B
Run C

Expected:

A == B == C

If outputs differ without an explicitly declared nondeterministic component:

NON_DETERMINISTIC

The build fails certification.

## 12. No-Lookahead Gate

Every Decision must satisfy:

max(input_timestamp) <= decision_timestamp

Any violation:
- FAIL;
- classify as LOOKAHEAD_BIAS;
- block certification.

## 13. State Invariant Gate

Mandatory invariants include:

I1 — State transitions are legal.
I2 — Completed fractals satisfy the defined fractal rules.
I3 — Invalid immediate top-bottom pairs cannot become a Bi.
I4 — Bi state-machine transitions are legal.
I5 — Segment construction respects minimum structural requirements.
I6 — Center state transitions are deterministic.
I7 — Decision cannot reference future state.
I8 — HOLD is an explicit valid result.
I9 — Replay cannot mutate production state.
I10 — State hashes are deterministic.

## 14. Decision Regression Gate

For certified cases:

expected Decision == actual Decision

Where differences are intentional, old behavior, new behavior, rationale, affected corpus, approval and migration version must all be recorded.

No silent behavioral change is accepted.

## 15. Risk Regression Gate

For certified cases:

expected Risk Result == actual Risk Result

The gate must test:
- maximum exposure;
- leverage;
- capital reservation;
- daily loss;
- drawdown;
- protection;
- position sizing;
- stop validity.

Risk regressions are blocking failures.

## 16. Execution Contract Gate

Test the full order lifecycle without real funds:

OrderIntent
-> Permission
-> Signing Request
-> Exchange Adapter
-> Acknowledgement
-> Fill
-> Position
-> Reconciliation

Required cases:
- accepted;
- rejected;
- partial;
- duplicate;
- timeout;
- unknown acknowledgement;
- retry;
- cancel;
- restart.

No test may require production signing credentials.

## 17. Security Invariant Gate

At minimum:

S1 — Trading runtime cannot access treasury authority.
S2 — Replay cannot submit orders.
S3 — Strategy cannot bypass Risk.
S4 — Strategy cannot bypass Permission Guard.
S5 — Strategy cannot bypass Signing Policy.
S6 — FROZEN cannot self-clear.
S7 — Unknown execution state cannot trigger blind retry.
S8 — Secret material cannot enter ordinary telemetry.
S9 — Capital increase requires promotion evidence.
S10 — Only approved execution authority may submit live orders.

Any violation is an immediate certification blocker.

## 18. Differential Certification

For changes classified CLASS_C–E:

Old certified build
vs
Candidate build

must be executed against:
- regression corpus;
- representative live-history windows;
- edge cases;
- incident cases.

Output:
- identical;
- intentional divergence;
- unintentional divergence.

Only intentional divergence with approved migration evidence may pass.

## 19. First-Divergence Requirement

When differential testing fails, the certification system must report:
- first divergent event;
- first divergent state;
- changed field;
- old value;
- new value;
- causation chain;
- affected decisions;
- affected OrderIntents;
- downstream execution impact.

A final PnL difference alone is not an acceptable regression diagnosis.

## 20. Canary Certification

A build cannot enter Canary merely because regression tests pass.

Canary prerequisites:
1. Certification state = CERTIFIED.
2. No unresolved blocking regression.
3. Evidence bundle generated.
4. Configuration hash fixed.
5. Risk policy hash fixed.
6. Signing policy verified.
7. Replay baseline available.
8. Rollback artifact available.
9. Monitoring healthy.
10. Promotion approval recorded.

Capital exposure remains governed by v4.4.0.

## 21. Production Promotion Gate

Promotion from Canary requires:
- Canary evidence;
- no unresolved SEV-0/SEV-1 incident;
- reconciliation healthy;
- protection healthy;
- security invariants intact;
- deterministic replay baseline unchanged or approved;
- resource stability;
- rollback verified.

Profitability cannot substitute for a failed mandatory gate.

## 22. Regression Failure Classes

### BLOCKER
Must prevent certification.

Examples:
- lookahead;
- risk bypass;
- security invariant violation;
- unauthorized order;
- state corruption;
- nondeterminism in deterministic path.

### CRITICAL
Requires explicit remediation before Canary.

Examples:
- ChanLun state divergence;
- incorrect Decision;
- incorrect position reconstruction;
- protection regression.

### MAJOR
Requires review and explicit disposition.

Examples:
- execution edge-case mismatch;
- telemetry loss affecting forensic capability.

### MINOR
Does not affect certified behavior or safety.

Examples:
- diagnostic formatting.

## 23. Test Isolation

Tests must distinguish:
- UNIT;
- PROPERTY;
- REPLAY;
- INTEGRATION;
- CONTRACT;
- SECURITY;
- CHAOS;
- CANARY.

Passing one class does not imply passing another.

## 24. Property-Based Testing

Where appropriate, generate adversarial sequences for:
- candles;
- fractal candidates;
- Bi transitions;
- event ordering;
- duplicate events;
- restarts;
- partial fills;
- exchange errors.

Properties, rather than exact outputs, are used where multiple valid outputs exist.

The generated seed must be preserved for reproducibility.

## 25. Chaos / Failure Certification

Mandatory failure scenarios:
- market-data disconnect;
- stale data;
- event-store unavailable;
- state-store unavailable;
- exchange timeout;
- unknown order acknowledgement;
- duplicate fill;
- signer unavailable;
- signer mismatch;
- nonce conflict;
- process restart;
- partial state recovery;
- observability backend unavailable.

The expected result must always be explicitly defined.

## 26. Build Identity

Every certification result is bound to:
- git_commit;
- build_id;
- artifact_hash;
- dependency_lock_hash;
- config_hash;
- schema versions;
- policy versions;
- replay engine version;
- corpus version.

If any identity changes, certification validity must be re-evaluated.

## 27. Certification Evidence Bundle

Every certified build produces:
- certification_id;
- build metadata;
- test summary;
- replay summary;
- differential results;
- security results;
- invariant results;
- failed tests;
- accepted deviations;
- corpus version;
- evidence hashes;
- approvers;
- timestamp.

The evidence bundle is immutable.

## 32. Certification State Machine

DRAFT
-> TESTING
-> PASSED
-> CERTIFIED
-> CANARY_APPROVED
-> PRODUCTION_APPROVED

Failure:
TESTING -> FAILED
CERTIFIED -> BLOCKED
CANARY_APPROVED -> BLOCKED

No automatic promotion from BLOCKED.

## 33. Golden Corpus Governance

The corpus is itself production-critical.

Rules:
- every case has provenance;
- every expected output is versioned;
- changes require review;
- retired cases remain immutable;
- incident-derived cases are mandatory candidates;
- production bugs must feed back into the corpus.

## 34. Regression Feedback Loop

      v

This makes production incidents permanent improvements to the system's test boundary.

## 35. Security Invariants

I1 — Certification cannot grant trading authority.
I2 — Passing tests cannot bypass production risk gates.
I3 — Golden Outputs cannot be silently modified.
I4 — Failed mandatory tests block Canary.
I5 — Certification identity is immutable.
I6 — Replay tests have no live financial side effects.
I7 — Security tests run without production secrets.
I8 — A build cannot self-approve its own production promotion.
I9 — Corpus changes are auditable.
I10 — Regression evidence is reproducible.

## 36. Exit Criteria

v4.4.4 passes when:
1. Regression Corpus is versioned.
2. Golden Outputs are immutable.
3. Determinism gate works.
4. No-lookahead gate works.
5. ChanLun regression suites work.
6. Decision regression works.
7. Risk regression works.
8. Execution contract tests work.
9. Security invariant tests work.
10. Differential replay works.
11. Failure/chaos tests work.
12. Certification evidence is generated.
13. Canary promotion requires certification.
14. Production promotion requires Canary evidence.
15. Production incidents can become regression cases.
16. Certification is reproducible from build/corpus/config identity.

## 37. Scope Boundary

v4.4.4 does not redefine ChanLun geometry, Decision Engine semantics, risk formulas, stop rules or exchange execution semantics.

It defines the quality, regression and certification gate protecting those components from uncontrolled behavioral change.
