# v4.4.5 — Canary Certification & Progressive Capital Ramp

## 1. Objective

v4.4.5 defines the controlled transition from a fully certified software build to limited real-market execution and progressive capital exposure.

The objective is to ensure that software correctness, operational health, execution reliability and capital exposure are promoted independently and only converge when all safety gates pass.

This specification does not define a profit target.

## 2. Core Principle

Software certification does NOT automatically grant capital authority.

The system separates:

CERTIFICATION
-> "The software passed required correctness and safety tests."

CANARY AUTHORITY
-> "The software may execute within a strictly bounded live environment."

CAPITAL AUTHORITY
-> "The software may control up to a specified capital ceiling."

These are separate permissions.

## 3. Promotion Ladder

Recommended lifecycle:

DRAFT
  ↓
TESTING
  ↓
CERTIFIED
  ↓
SHADOW
  ↓
TESTNET
  ↓
MICRO_CANARY
  ↓
RAMP_L1
  ↓
RAMP_L2
  ↓
CONTROLLED_CANARY
  ↓
PRODUCTION

A deployment may stop or move backward at any stage.

No stage may automatically skip mandatory safety gates.

## 4. Stage Definitions

### SHADOW

No real order submission.

The production build consumes live market data and produces:
- ChanLun state;
- Decision;
- Risk result;
- expected OrderIntent.

Expected execution is recorded but not submitted.

Purpose:
- detect data drift;
- detect runtime divergence;
- validate latency;
- validate observability.

### TESTNET

Orders may be submitted only to an isolated test environment.

Purpose:
- validate order lifecycle;
- validate exchange adapter;
- validate acknowledgement;
- validate fills;
- validate reconciliation.

### MICRO_CANARY

Real market execution with the minimum approved capital ceiling.

Requirements:
- certified build;
- production configuration;
- production risk policy;
- production signing path;
- strict symbol scope;
- strict order/risk limits.

### RAMP_L1 / RAMP_L2

Controlled increases in capital authority after evidence-based promotion.

Each level has an explicit:
- capital ceiling;
- exposure ceiling;
- leverage ceiling;
- order-rate ceiling;
- loss ceiling;
- position count ceiling.

### CONTROLLED_CANARY

Broader but still bounded production operation.

### PRODUCTION

Normal approved operating envelope.

## 5. Capital Authority Model

Capital authority is represented as a signed policy:

CapitalPolicy {
  policy_id
  policy_version
  environment
  account_scope
  symbol_scope
  max_notional
  max_margin
  max_leverage
  max_position_count
  max_order_rate
  max_daily_loss
  max_drawdown
  max_open_positions
  expires_at
  emergency_policy
}

The policy is immutable after activation.

Changes create a new policy version.

## 6. Separation of Authority

The following must remain separate:

Strategy Authority
Risk Authority
Capital Authority
Permission Authority
Signing Authority
Treasury Authority

Strategy code MUST NOT be able to increase its own CapitalPolicy.

## 7. Promotion Evidence

Every promotion requires:

- certification_id;
- build_id;
- artifact_hash;
- config_hash;
- policy_hash;
- replay baseline;
- regression corpus version;
- observability health;
- reconciliation health;
- execution health;
- security invariant result;
- current incident state;
- rollback artifact;
- approval record.

## 8. Shadow Exit Criteria

SHADOW -> TESTNET requires:

1. no unresolved blocking regression;
2. deterministic replay remains valid;
3. no lookahead violation;
4. event ingestion stable;
5. ChanLun state generation stable;
6. Decision output stable;
7. risk output stable;
8. telemetry complete enough for forensic analysis;
9. state/replay hashes reproducible;
10. no unresolved critical incident.

## 9. Testnet Exit Criteria

TESTNET -> MICRO_CANARY requires:

1. order lifecycle contract passes;
2. acknowledgement handling passes;
3. partial-fill handling passes;
4. cancellation handling passes;
5. timeout handling passes;
6. unknown acknowledgement handling passes;
7. reconciliation converges;
8. restart recovery passes;
9. signing path passes without production treasury access;
10. kill switch test passes;
11. rollback test passes.

## 10. Micro-Canary Entry Conditions

Before enabling real trading:

- stage = MICRO_CANARY;
- capital policy explicitly approved;
- symbol allowlist fixed;
- maximum leverage fixed;
- order types allowlisted;
- maximum order notional fixed;
- maximum daily loss fixed;
- maximum position count fixed;
- stop/protection policy active;
- kill switch verified;
- reconciliation healthy;
- observability healthy;
- incident state clear.

## 11. Progressive Capital Ramp

Capital must increase in discrete policy versions.

Example:

RAMP_L1
-> approved ceiling C1

RAMP_L2
-> approved ceiling C2

CONTROLLED_CANARY
-> approved ceiling C3

The actual numerical values are deployment parameters and must NOT be hard-coded into the architecture specification.

## 12. Ramp Conditions

A stage may be promoted only if all mandatory conditions are true:

### Correctness
- certification remains valid;
- no new regression;
- replay baseline consistent.

### Market Data
- no unresolved data-gap incident;
- data freshness within policy;
- sequence integrity healthy.

### ChanLun
- no structural invariant violation;
- state transition rate normal;
- no unexplained divergence.

### Risk
- no risk bypass;
- exposure within policy;
- capital reservation healthy;
- protection healthy.

### Execution
- order rejection rate within policy;
- unknown acknowledgement count = 0 for promotion window;
- reconciliation divergence = 0 for promotion window unless explicitly reviewed;
- no unauthorized order.

### Security
- permission policy unchanged or re-certified;
- signer/keyset healthy;
- no nonce conflict;
- no policy violation.

### Operations
- runtime stable;
- restart/recovery healthy;
- observability pipeline healthy;
- no unresolved blocking incident.

## 13. Promotion Window

Each promotion must define an evidence window.

The window can be measured by:
- elapsed runtime;
- number of processed candles;
- number of decisions;
- number of orders;
- number of fills;
- incident-free observation period.

Promotion should require a minimum evidence threshold appropriate to the stage.

The exact thresholds are deployment parameters, not universal constants.

## 14. Capital Ramp Guard

Capital increase requires a separate authorization event:

CAPITAL_RAMP_REQUESTED
-> CAPITAL_RAMP_VALIDATED
-> CAPITAL_RAMP_APPROVED
-> CAPITAL_POLICY_ACTIVATED

The runtime cannot infer that a successful trading period grants more capital.

## 15. Automatic Downgrade

The system must support automatic stage reduction.

Examples:

CONTROLLED_CANARY
-> RAMP_L2
-> RAMP_L1
-> MICRO_CANARY
-> FROZEN

The downgrade level is determined by incident severity and the affected safety domain.

## 16. Immediate Freeze Conditions

The following are mandatory candidates for immediate FROZEN:

- unauthorized order;
- signing-policy violation;
- capital-policy violation;
- risk bypass;
- position reconstruction failure;
- unknown critical execution state;
- protection failure where required;
- state corruption;
- lookahead detection in live decision path;
- unrecoverable reconciliation divergence;
- compromised signing authority.

## 17. Soft Degradation

Not every problem requires immediate full freeze.

Examples may include:
- telemetry backend degradation while canonical events remain durable;
- non-critical metrics loss;
- elevated but bounded latency;
- isolated market-data reconnect with successful recovery.

The response must follow the incident and runtime policy.

## 18. Kill Switch

Kill switch must be able to:

1. stop new OrderIntent authorization;
2. prevent new live orders;
3. cancel or reduce positions according to policy;
4. transition runtime to FROZEN;
5. create an immutable audit event;
6. preserve evidence.

Kill switch activation must not depend on the ChanLun Decision Engine.

## 19. Rollback

Rollback has two independent dimensions:

### Software Rollback
Return to a previously certified build.

### Capital Rollback
Reduce CapitalPolicy ceiling.

One can occur without the other.

Example:

Build remains valid
but
capital authority is reduced.

## 20. Emergency Capital Reduction

The system must support:

CURRENT_POLICY
-> REDUCED_POLICY

without requiring a software redeployment.

The reduction must be monotonic:

new_max <= old_max

for the affected capital/risk dimensions.

Increasing capital requires the full promotion process.

## 21. Promotion State Machine

DRAFT
-> TESTING
-> CERTIFIED
-> SHADOW
-> TESTNET
-> MICRO_CANARY
-> RAMP_L1
-> RAMP_L2
-> CONTROLLED_CANARY
-> PRODUCTION

Failure transitions:

ANY_LIVE_STAGE
-> DEGRADED
-> RAMP_DOWN

or:

ANY_LIVE_STAGE
-> FROZEN

Recovery:

FROZEN
-> RECOVERY
-> SHADOW
-> TESTNET
-> MICRO_CANARY

Recovery MUST NOT directly jump back to PRODUCTION.

## 24. Canary Traceability

Every real order must be traceable to:

stage
-> capital policy
-> build
-> decision
-> risk
-> permission
-> signing
-> exchange order
-> fill
-> position
-> reconciliation

This extends the v4.4.2 audit chain.

## 25. Capital Utilization

Capital authority and actual capital usage are different.

Track:

capital_policy_ceiling
capital_reserved
capital_in_use
capital_available
capital_utilization_ratio

A high utilization ratio may trigger a risk policy action even if absolute exposure remains below the ceiling.

## 26. Position-Level Guard

Every position must carry:

- position_id;
- stage;
- capital_policy_version;
- build_id;
- entry_decision_id;
- risk_decision_id;
- protection_policy_id.

This allows an individual position to be traced to the exact production authorization under which it was created.

## 27. Stage-Specific Order Controls

Every live stage should have explicit allowlists:

- symbols;
- order types;
- leverage;
- max notional;
- max order count;
- max position count;
- maximum simultaneous exposure.

A stage cannot inherit a broader production policy implicitly.

## 28. Canary Expiration

Every Canary authorization should have an expiration condition.

Possible forms:
- time;
- event count;
- order count;
- explicit promotion.

When expired:

CANARY_EXPIRED
-> RAMP_DOWN or FROZEN

No expired authorization may continue indefinitely.

## 29. Configuration Drift

The runtime must continuously verify:

running_config_hash == approved_config_hash

and:

running_policy_hash == approved_policy_hash

Drift results in:
- alert;
- promotion block;
- possible downgrade/freeze depending on affected control.

## 30. Build Drift

The running artifact must match the certified artifact:

running_artifact_hash == certified_artifact_hash

Unexpected artifact drift is a security and release failure.

## 31. Two-Person Promotion

For high-risk capital increases, the architecture should support independent roles:

Requester
+
Approver

The requester cannot be the sole approver.

The exact organizational approval policy remains deployment-specific.

## 32. Capital Ramp Audit

Every increase must be auditable:

old ceiling
-> requested ceiling
-> evidence
-> approver
-> policy hash
-> activation
-> effective timestamp

Every decrease must also be recorded.

## 33. Promotion Failure Analysis

A rejected promotion must provide:

- failed gate;
- measured value;
- policy threshold;
- evidence references;
- incident references;
- required remediation;
- retry eligibility.

A generic "promotion failed" message is insufficient.

## 34. Shadow-vs-Live Differential

During SHADOW, the system should compare:

shadow expected OrderIntent
vs
actual production OrderIntent

when a separately controlled live deployment exists.

The purpose is to detect:
- code drift;
- configuration drift;
- data normalization differences;
- timing differences.

This comparison must not cause shadow orders to be submitted.

## 35. Certification Expiration

Certification may become invalid when:
- build changes;
- executable dependency changes;
- strategy configuration changes;
- risk policy changes materially;
- signing policy changes;
- schema compatibility breaks;
- critical incident occurs.

The affected certification must return to the appropriate re-certification state.

## 36. Emergency Override

Emergency override may only reduce authority or freeze execution.

It MUST NOT:
- increase capital;
- bypass Risk;
- bypass Permission;
- bypass Signing Policy;
- bypass Certification.

Any override action is audited.

## 37. Security Invariants

I1 — Certification does not grant capital authority.
I2 — Strategy cannot increase capital.
I3 — Runtime cannot activate an unapproved CapitalPolicy.
I4 — Capital increases require explicit authorization.
I5 — Emergency controls can reduce authority but cannot increase it.
I6 — FROZEN cannot self-promote.
I7 — Expired Canary authority cannot remain active.
I8 — Running build/config/policy must match approved identity.
I9 — Kill switch is independent of strategy decisions.
I10 — Every live order has a traceable capital-policy lineage.

## 38. Exit Criteria

v4.4.5 passes when:

1. Promotion state machine is implemented.
2. CapitalPolicy is versioned and immutable.
3. Certification and capital authority are separated.
4. Shadow mode works.
5. Testnet mode works.
6. Micro-canary mode works.
7. Progressive capital ramp works.
8. Automatic downgrade works.
9. Immediate freeze conditions work.
10. Kill switch works independently of strategy.
11. Software rollback and capital rollback are independent.
12. Configuration/artifact drift is detected.
13. Canary expiration works.
14. Promotion evidence is auditable.
15. High-risk capital increases support independent approval.
16. Every live order can be traced to its capital authorization.

## 39. Scope Boundary

v4.4.5 does not define the actual capital amounts for a specific deployment.

It defines the control architecture that makes any approved capital amount bounded, versioned, auditable, reversible and progressively promotable.
