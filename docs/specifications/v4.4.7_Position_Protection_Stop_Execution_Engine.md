# v4.4.7 — Position Protection & Stop Execution Engine

## 1. Objective

v4.4.7 defines the production position-protection subsystem that maintains and executes protective exits for live positions.

It connects the previously defined:
- Stop Anchor;
- Stop Trigger;
- Position Sizing;
- Liquidation Guard;
- Order Manager;
- Reconciliation;
- Live Risk Control;
- Canary Capital Policy

into one authoritative protection lifecycle.

The protection subsystem is defensive infrastructure.

It MUST NOT create a new speculative position.

## 2. Design Principle

After a live position exists:

Position
  ↓
Protection Policy
  ↓
Stop Anchor
  ↓
Trigger Monitor
  ↓
Stop Decision
  ↓
Protective OrderIntent
  ↓
Permission
  ↓
Execution
  ↓
Fill
  ↓
Position Update
  ↓
Protection Reconciliation

The protection path must remain available even when the Strategy/Decision Engine is degraded.

## 3. Authority Boundary

Strategy decides whether to open, hold or close according to Decision Engine semantics.

Protection Engine owns:
- stop-anchor validity;
- trigger evaluation;
- protective exit authorization;
- protection-state tracking;
- emergency reduction when required by policy.

Strategy MUST NOT disable a mandatory protection policy.

## 4. Position Protection Record

Every live position has a ProtectionRecord:

ProtectionRecord {
  protection_id

  anchor_type
  anchor_price
  trigger_policy_version

  source_decision_id
  created_at
  updated_at
  status
  trigger_state
  protective_order_id
  remaining_quantity
}

The record is versioned and auditable.

## 5. Stop Anchor

A Stop Anchor is the immutable reference point from which the configured protective threshold is derived.

For the project's ChanLun 1M operating model, the anchor is based on the latest completed qualifying fractal extreme as defined by the existing stop specification.

The protection engine MUST NOT silently replace a completed anchor with an unconfirmed fractal.

## 6. Anchor Lifecycle

PROPOSED
-> QUALIFIED
-> ACTIVE
-> TRIGGERED
-> EXECUTING
-> PROTECTED_CLOSED

Alternative failure path:

ACTIVE
-> INVALID
-> EMERGENCY_PROTECTION

An anchor becomes active only after its required source state is complete.

## 7. ChanLun Dependency Boundary

The protection engine consumes ChanLun structural facts.

It does not reinterpret ChanLun geometry.

For example, it may consume:
- completed top fractal;
- completed bottom fractal;
- associated timestamp;
- structural extreme.

It must not independently invent:
- a new fractal;
- a new Bi;
- a new Segment;
- a new Center;
- a new divergence interpretation.

This preserves the separation between structural analysis and risk protection.

## 8. Long/Short Symmetry

Protection rules must be directionally symmetric.

For LONG:
- protective stop is normally below the qualifying anchor.

For SHORT:
- protective stop is normally above the qualifying anchor.

The exact offset/slippage rules are controlled by the versioned protection policy.

No directional asymmetry may be introduced accidentally by implementation.

## 9. Stop Trigger Model

A trigger evaluation contains:

TriggerInput {
  position_state
  protection_state
  latest_market_data
  latest_valid_candle
  trigger_policy
  exchange_state
}

Output:

TRIGGERED
NOT_TRIGGERED
UNKNOWN
INVALID

UNKNOWN is not equivalent to NOT_TRIGGERED.

## 10. Trigger Data Sources

Trigger evaluation may use:

### Tick
Highest resolution when authoritative and available.

### 1M OHLC
Used when the project's configured execution mode relies on candle data.

### Exchange Mark/Index
Used only where explicitly configured by policy.

The trigger source is recorded in the ProtectionDecision.

## 11. Tick Trigger

If authoritative tick data is available:

LONG:
trigger when the configured trigger price is reached or crossed according to policy.

SHORT:
trigger when the configured trigger price is reached or crossed according to policy.

The comparison rule must be explicit:
- >= for upward threshold;
- <= for downward threshold;
or another explicitly versioned rule.

## 12. 1M OHLC Trigger

When only completed 1M OHLC is available:

LONG stop candidate:
Low <= stop_price

SHORT stop candidate:
High >= stop_price

This determines that the stop threshold was touched during the candle.

It does NOT by itself establish the exact intra-candle sequence.

## 13. Same-Candle Ambiguity

If multiple relevant triggers can occur within the same 1M candle and OHLC cannot determine their order, the engine MUST NOT invent an order.

Example:

Open
High
Low
Close

Both:
- stop threshold;
- another execution condition

may be touched.

If sequence cannot be proven:

AMBIGUOUS

The result follows the declared same-candle policy.

## 14. Same-Candle Policy

The policy must explicitly define behavior for:

### CONSERVATIVE
Assume the protective condition occurred whenever the OHLC proves it was touched.

### SEQUENCE_REQUIRED
Require higher-resolution evidence.

### AMBIGUOUS_BLOCK
Block any interpretation that depends on unknown intra-candle ordering.

The selected policy is part of the replay/certification identity.

The engine MUST NOT switch policies dynamically.

## 15. Stop Trigger Decision

Every trigger creates:

ProtectionDecision {
  protection_decision_id
  position_id
  anchor_price
  trigger_source
  observed_price
  candle_id
  trigger_result
  ambiguity_state
  policy_hash
  state_hash
  timestamp
}

This becomes part of the forensic chain.

## 16. Triggered State

Once a mandatory stop is triggered:

ACTIVE
-> TRIGGERED

The trigger event is durable.

The system must not repeatedly reinterpret the same trigger as a new independent event.

## 17. Protective OrderIntent

After trigger:

TRIGGERED
-> EXECUTION_PENDING

The engine creates a protective OrderIntent.

The OrderIntent must identify:

- position_id;
- reduce_only = true;
- target quantity;
- protective reason;
- trigger reference;
- protection policy;
- idempotency key.

A normal strategy OrderIntent cannot be substituted for a mandatory protection OrderIntent.

## 18. Reduce-Only Requirement

Protective exits MUST use reduce-only semantics whenever supported by the exchange and execution architecture.

A protective action must not accidentally increase or reverse exposure.

If the exchange does not support the required protection semantics, the position enters the policy-defined emergency path.

## 19. Position Quantity

Protective quantity is based on authoritative current position quantity.

It must account for:
- partial fills;
- prior reductions;
- manual authorized intervention;
- liquidation;
- reconciliation.

The engine must never blindly submit the original position quantity after partial execution.

## 20. Partial Fill

Example:

Position = 10
Protective order = 10
Filled = 4

Remaining protection target:

6

The system transitions:

EXECUTING
-> PARTIALLY_PROTECTED

and creates or maintains protection for the remaining quantity according to policy.

## 21. Duplicate Trigger

A duplicate trigger for the same protection version must be idempotent.

If protection is already:

EXECUTION_PENDING
or
EXECUTING

a second trigger must not create an uncontrolled duplicate order.

The engine reconciles the existing protective order first.

## 22. Protective Order Rejection

If the exchange rejects a mandatory protective order:

PROTECTION_FAILED

The Live Risk Control Plane must immediately evaluate the emergency response.

Possible actions:
- retry according to policy;
- alternative approved order type;
- reduce-only market protection;
- symbol freeze;
- account freeze.

A rejected protection order cannot simply be ignored.

## 23. Unknown Protective Order

If the protective order is submitted but acknowledgement is unknown:

PROTECTION_UNKNOWN

The system MUST NOT blindly submit a second order.

Required:

query exchange
-> reconcile order
-> reconcile fills
-> reconcile position
-> determine remaining quantity
-> decide next protective action

## 24. Slippage

Protective execution may experience slippage.

Record:

trigger_price
execution_price
slippage_absolute
slippage_relative
liquidity_context

Slippage alone does not imply a strategy failure.

It becomes a risk incident if it violates the configured policy.

## 25. Gap Through Stop

If price moves through the stop threshold without an executable fill at the anchor price:

the engine records:

STOP_GAP

The protection action uses the configured emergency execution policy.

The engine MUST NOT claim that the position was closed at the stop anchor if the exchange execution price was different.

## 26. Stop vs Liquidation

Protection and liquidation are different states.

Normal path:

Position
-> Protective Stop
-> Exit

Failure path:

Position
-> Protection Failure
-> Increasing Risk
-> Liquidation Guard
-> Emergency Action

The system must never intentionally rely on liquidation as normal stop execution.

## 27. Liquidation Guard Integration

If:

distance_to_liquidation
approaches
policy.minimum_liquidation_buffer

the Live Risk Control Plane may force emergency reduction according to policy.

Protection failure + liquidation proximity is a higher-severity condition than either event alone.

## 28. Protection Health

Each live position has:

PROTECTED
PROTECTION_PENDING
PARTIALLY_PROTECTED
PROTECTION_FAILED
PROTECTION_UNKNOWN
TRIGGERED
EXECUTING
CLOSED

The account-level protection state is the most restrictive applicable position state.

## 29. New-Entry Interaction

If any required protection is unhealthy:

new exposure may be denied according to policy.

Examples:

PROTECTION_FAILED
-> NEW_ENTRY = DENIED

PROTECTION_UNKNOWN
-> NEW_ENTRY = DENIED

This prevents the system from increasing exposure while unable to reliably protect existing exposure.

## 30. Protection Priority

Protection actions have priority over new speculative orders.

Ordering:

Emergency Protection
>
Existing Position Reduction
>
Normal Position Management
>
New Entry

This priority must be enforced by Permission/Execution layers, not merely by strategy convention.

## 31. Manual Intervention

Authorized manual actions may include:
- reduce position;
- close position;
- cancel protection;
- replace protection.

Any manual change must:
- be authorized;
- produce an audit event;
- update ProtectionRecord;
- trigger reconciliation.

Manual cancellation of mandatory protection requires a policy-defined replacement or explicit emergency state.

## 32. Protection Policy Versioning

Protection behavior depends on:

- anchor policy;
- trigger policy;
- same-candle policy;
- execution policy;
- slippage policy;
- emergency policy.

Every live ProtectionRecord stores the policy versions used to create it.

Changing a policy does not silently rewrite historical protection decisions.

## 33. Protection Reconciliation

Continuously compare:

ProtectionRecord
vs
Exchange Orders
vs
Exchange Position
vs
Local Position

Expected invariant:

required_protection_quantity
<=
authoritative_position_quantity

and:

protective_order_state
matches
local protection state

within defined reconciliation tolerance.

## 34. Protection Drift

Examples:

Local says protected
Exchange has no protective order.

Local says 10 protected
Exchange position = 6.

Local says order active
Exchange says rejected.

These are protection-drift conditions.

Response depends on severity but cannot be silently ignored.

## 35. Recovery After Restart

After restart:

1. reconstruct position;
2. reconstruct ProtectionRecord;
3. query exchange protective orders;
4. reconcile fills;
5. verify anchor/policy identity;
6. determine remaining quantity;
7. restore protection state;
8. deny new exposure if protection cannot be proven.

The system must prefer safety over continuity of strategy execution.

## 36. Multi-Position Protection

Each position is independently protected.

The system must support:
- multiple symbols;
- long and short positions;
- independent anchors;
- independent protective orders;
- account-level emergency restrictions.

One position's failure may restrict the account without corrupting unrelated position records.

## 37. Position Netting

If the exchange uses net positions:

Protection quantity must be derived from authoritative net position state.

If the exchange uses hedged positions:

Protection must be associated with the correct position side/leg.

The adapter must expose the position model explicitly.

## 38. Order Type Policy

Approved protective order types must be explicit.

Examples:
- stop-market;
- stop-limit;
- market reduce-only;
- exchange-native conditional order.

The engine must not silently switch order types because one type was rejected.

Fallback types require an approved emergency policy.

## 39. Exchange-Native Protection

Where exchange-native conditional protection is used:

The system must track:
- exchange order ID;
- trigger condition;
- quantity;
- reduce-only flag;
- activation state;
- cancellation/replacement state.

Exchange-native protection is not considered active merely because the local API call succeeded.

The exchange acknowledgement must be authoritative.

## 51. Failure Escalation

Protection failure severity:

### P0
- unauthorized exposure;
- protection bypass;
- signing violation;
- critical position mismatch.

### P1
- required protection absent;
- unknown protective order;
- unrecoverable reconciliation drift;
- liquidation proximity with failed protection.

### P2
- temporary protection latency;
- recoverable exchange rejection.

### P3
- non-critical telemetry degradation.

Severity classification is operational policy and does not alter the underlying event facts.

1. authoritative position known;
2. remaining quantity known;
3. exchange state reconciled;
4. approved protection action available;
5. permission valid;
6. signing valid;
7. action recorded;
8. protection verified.

FAILED/UNKNOWN
-> PROTECTED
or
-> CLOSED
