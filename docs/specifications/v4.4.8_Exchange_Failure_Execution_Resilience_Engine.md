# v4.4.8 — Exchange Failure & Execution Resilience Engine

## 1. Objective

v4.4.8 defines the exchange connectivity and execution-resilience layer for production trading.

It protects the system against:
- WebSocket disconnects;
- REST failures;
- request timeout;
- acknowledgement loss;
- duplicate submission risk;
- cancel/replace races;
- exchange rate limits;
- nonce conflicts;
- network partitions;
- exchange maintenance;
- stale exchange state;
- repeated rejects;
- delayed fills;
- inconsistent local/exchange state.

The primary rule is:

UNKNOWN execution state MUST be reconciled before any non-idempotent retry.

## 2. Design Principle

The engine separates:

TRANSPORT FAILURE
from
EXECUTION UNKNOWN
from
EXECUTION CONFIRMED FAILURE.

These are not interchangeable.

Example:

REST timeout
does NOT mean
order rejected.

The exchange must be queried before the system assumes the final state.

## 4. Exchange State Model

Exchange health:

HEALTHY
DEGRADED
DISCONNECTED
PARTITIONED
MAINTENANCE
UNKNOWN

Execution health:

NORMAL
ELEVATED_FAILURE
RESTRICTED
FROZEN

The two dimensions are tracked independently.

## 5. Connection State Machine

DISCONNECTED
-> CONNECTING
-> AUTHENTICATING
-> CONNECTED
-> DEGRADED
-> RECONNECTING
-> CONNECTED

Failure:

CONNECTING
-> FAILED
-> BACKOFF
-> RECONNECTING

Repeated failure may trigger:

RECONNECTING
-> EXCHANGE_DEGRADED
-> RESTRICTED
-> FROZEN

## 6. WebSocket Reliability

WebSocket sessions must track:

- connection ID;
- exchange;
- channel;
- subscription;
- last message timestamp;
- last sequence;
- heartbeat;
- reconnect count;
- authentication state.

A WebSocket disconnect does not imply exchange order state.

REST or another authoritative channel must be used for reconciliation.

## 7. Heartbeat

The connection manager tracks:
- last heartbeat;
- last data message;
- heartbeat latency;
- missed heartbeat count.

A missed heartbeat moves the connection toward DEGRADED.

Thresholds are policy parameters.

## 8. Sequence Integrity

For exchanges exposing sequence numbers:

expected_sequence
vs
received_sequence

If a gap exists:

SEQUENCE_GAP

The system must:
1. mark the stream degraded;
2. stop trusting incremental state derived after the gap;
3. resynchronize;
4. reconcile authoritative state;
5. restore normal execution only after validation.

Missing sequence data must never be fabricated.

## 9. REST Request State

Every request has:

REQUESTED
-> SENT
-> ACKNOWLEDGED
-> COMPLETED

Failure paths:

SENT
-> TIMEOUT
-> UNKNOWN

or:

SENT
-> REJECTED

TIMEOUT != REJECTED.

## 10. Unknown Request

For an order-changing request:

UNKNOWN
-> QUERY_AUTHORITATIVE_STATE
-> CONFIRMED_SUCCESS
or
-> CONFIRMED_FAILURE
or
-> STILL_UNKNOWN

STILL_UNKNOWN triggers policy-defined restriction.

## 11. Retry Classification

Every failed request is classified:

### SAFE_RETRY

Only when retry cannot create an unintended duplicate side effect.

Examples:
- read-only query;
- explicitly idempotent request.

### CONDITIONAL_RETRY

Requires idempotency key or authoritative state confirmation.

### NO_RETRY

Used when another submission could create uncontrolled exposure.

The retry engine must never retry solely because a transport error occurred.

## 12. Idempotency

Every order mutation must have a stable client-side idempotency identity where supported.

Recommended conceptual key:

idempotency_key =
hash(
  account
  + symbol
  + side
  + intent_id
  + order_action_version
)

The same logical action must not accidentally become multiple independent orders.

## 13. Order Intent Identity

An OrderIntent is not an ExchangeOrder.

Lifecycle:

OrderIntent
-> Permission
-> Signing
-> ExchangeRequest
-> ExchangeOrder
-> Fill

This distinction prevents transport retries from creating a second logical intent.

## 14. Duplicate Submission Protection

Before retrying an unknown order submission:

1. check local request state;
2. query exchange by client order ID where supported;
3. query open orders;
4. query recent fills;
5. reconcile position;
6. determine whether the original order exists.

Only then may the retry policy permit another action.

## 15. Cancel Reliability

Cancel request:

CANCEL_REQUESTED
-> SENT
-> ACKNOWLEDGED
-> CANCELLED

Failure:

TIMEOUT
-> UNKNOWN
-> QUERY_ORDER
-> FILLED / OPEN / CANCELLED / UNKNOWN

A timeout must never be interpreted as cancellation.

## 16. Cancel/Fill Race

Possible sequence:

Cancel requested
+
Order fills before cancellation is processed.

Final state must come from authoritative exchange data.

The system must reconcile:
- order;
- fills;
- position.

It must not force local state to CANCELLED because a cancel request was sent.

## 17. Replace Race

Order replacement must be modeled as:

OLD_ORDER
-> CANCEL_REQUESTED
-> CONFIRMED_CANCELLED
-> NEW_ORDER

unless the exchange provides an atomic replace primitive.

Creating the new order before knowing whether the old order remains active can create duplicate exposure.

## 18. Reduce-Only Retry

Protective reduce-only orders receive special handling.

If the first request is UNKNOWN:

do not blindly submit another protective order.

Reconcile:
- exchange order;
- fills;
- position;
- remaining protection.

Then submit only the remaining required protection.

This integrates with v4.4.7.

## 19. Rate Limit Controller

The system tracks:
- request count;
- remaining quota;
- reset time;
- rejection;
- backoff.

Rate-limit responses trigger controlled backoff.

The strategy cannot bypass rate limits.

## 20. Rate Limit Escalation

Repeated rate-limit failures can cause:

NORMAL
-> DEGRADED
-> RESTRICTED

New-entry authorization may be suspended while:
- reconciliation;
- protection;
- emergency operations

retain higher priority according to policy.

## 21. Nonce / Sequence Manager

Where an exchange uses client nonce or request sequence:

Nonce state must be persisted and reconciled.

States:

VALID
CONFLICT
UNKNOWN
RESYNC_REQUIRED

A nonce conflict must not cause uncontrolled rapid retries.

## 22. Nonce Recovery

On conflict:

1. stop affected request class;
2. query authoritative exchange state;
3. reconstruct local nonce/sequence;
4. persist corrected state;
5. resume only after validation.

If correction cannot be proven safe:

RESTRICTED or FROZEN.

## 23. Exchange Maintenance

Maintenance detection may come from:
- exchange status;
- API errors;
- WebSocket status;
- scheduled maintenance configuration;
- repeated connectivity failure.

Maintenance state:

MAINTENANCE
-> NEW_ENTRY_DENIED

Protection/reduction behavior follows the emergency policy.

## 24. Exchange Health Score

The architecture may maintain an internal health model based on:

- connection status;
- request error rate;
- acknowledgement latency;
- reject rate;
- sequence gaps;
- reconciliation freshness;
- rate-limit pressure.

The health model is diagnostic.

It must not silently override hard safety rules.

## 25. Network Partition

A network partition occurs when:

local runtime is alive
but
authoritative exchange communication cannot be established.

During partition:

- no new exposure;
- unknown order states remain unresolved;
- existing protection follows emergency policy;
- local state cannot be treated as authoritative;
- recovery requires reconciliation.

## 26. Split-Brain Prevention

If multiple runtime instances can potentially execute against the same account:

only one active execution authority may exist.

The system requires an execution lease or equivalent fencing mechanism.

A stale instance must not submit orders after losing authority.

## 27. Execution Lease

Lease fields:

lease_id
account_scope
instance_id
epoch
issued_at
expires_at
status

Order authorization requires a valid lease.

The lease must be checked before irreversible execution.

## 28. Fencing

Every execution authority has an increasing epoch.

A lower/stale epoch cannot authorize execution.

This protects against:
- delayed process;
- zombie instance;
- network partition;
- stale restart.

## 29. Exchange Rejection Taxonomy

Rejections should be classified:

- invalid parameters;
- insufficient margin;
- invalid quantity;
- invalid price;
- reduce-only conflict;
- position mode conflict;
- rate limit;
- authentication;
- permission;
- maintenance;
- unknown.

Retry behavior is determined by class.

## 30. Permanent vs Transient Failure

### Permanent
Do not retry automatically.

Examples:
- invalid order;
- permission denied;
- unsupported order type.

### Transient
May retry according to policy.

Examples:
- temporary network failure;
- service unavailable;
- recoverable timeout.

### Unknown
Must reconcile before retry.

Examples:
- timeout after submission;
- lost acknowledgement;
- network partition during mutation.

## 31. Backoff

Retries use bounded exponential backoff with jitter where appropriate.

Backoff parameters are deployment policy.

The engine must cap:
- retry count;
- retry duration;
- total mutation exposure.

## 32. Retry Budget

Every operation has:

retry_budget
retry_attempts
retry_deadline

When budget is exhausted:

NO_MORE_AUTOMATIC_RETRY

The operation escalates to reconciliation or incident handling.

## 33. Order Lifecycle Authority

Order status priority:

1. Exchange authoritative order state
2. Exchange fills
3. Reconciled position
4. Local request state
5. Local intent state

Local optimistic state must never outrank authoritative exchange evidence.

## 34. Fill Authority

A fill is authoritative only when supported by exchange data.

Repeated WebSocket fill messages must be deduplicated.

Fill identity should use exchange trade/fill identifiers where available.

## 35. Fill Deduplication

If the same fill is received:
- via WebSocket;
- via REST;
- after reconnect;

the system must recognize the same authoritative fill.

Duplicate processing must not double-count:
- position;
- realized PnL;
- fees;
- capital reservation.

## 36. Reconnect Reconciliation

After reconnect:

1. resubscribe;
2. verify stream sequence;
3. fetch open orders;
4. fetch recent fills;
5. fetch positions;
6. compare local state;
7. repair state;
8. restore execution authority.

Normal new-entry execution resumes only after required reconciliation passes.

## 37. Startup Reconciliation

Every runtime startup must reconcile before live order authorization.

Startup flow:

BOOT
-> LOAD_STATE
-> CONNECT
-> AUTHENTICATE
-> RECONCILE
-> VERIFY_PROTECTION
-> VERIFY_POLICY
-> VERIFY_LEASE
-> READY

If reconciliation fails:

READY is not granted.

## 38. Protection Priority During Recovery

During reconnect/recovery:

Protection
>
Position Reduction
>
Reconciliation
>
New Entry

New speculative exposure remains disabled until safety state is restored.

## 39. Exchange Clock

Where exchange timestamps/signatures depend on clock synchronization:

track:
- local clock;
- exchange timestamp;
- drift;
- last successful synchronization.

Excessive drift blocks affected signed requests.

## 40. Authentication Failure

Authentication failure is not treated as a generic network error.

Repeated authentication failure may indicate:
- expired credential;
- permission change;
- configuration error;
- security event.

New execution is blocked until resolved.

## 41. API Permission Drift

Compare approved permission policy with observed exchange capability.

Unexpected permission changes trigger:

PERMISSION_DRIFT

The system must not expand execution scope automatically.

## 42. Exchange Symbol/Contract Drift

If exchange contract metadata changes:
- tick size;
- lot size;
- min quantity;
- leverage limits;
- contract status;

the adapter must refresh and revalidate.

Orders based on stale contract metadata must be denied.

## 43. Price/Quantity Normalization

Exchange-specific rounding is performed before submission.

The normalized order must be recorded.

If normalization changes the requested risk beyond policy tolerance:

DENY

The system must never silently round an order into an unsafe exposure.

## 44. Network Timeout Policy

Timeout classification depends on operation stage.

Before request transmission:
may be safely retryable.

After transmission but before acknowledgement:
UNKNOWN.

After authoritative exchange confirmation:
no retry of the same logical mutation.

This distinction is mandatory.

## 45. REST/WebSocket Cross-Validation

Where both channels are available:

REST and WebSocket data should be cross-validated during recovery.

Conflicting states require authoritative reconciliation.

Neither channel is assumed infallible.

## 46. Exchange Event Ordering

Exchange events may arrive:
- delayed;
- duplicated;
- reordered.

The system must use exchange sequence numbers, timestamps and authoritative queries where available.

Local arrival time must not be treated as exchange event order.

- request;

## 54. Security Invariants

I1 — Transport timeout does not equal order rejection.
I2 — Unknown mutation state cannot be blindly retried.
I3 — Duplicate fills cannot alter position twice.
I4 — Stale execution instances cannot submit orders.
I5 — Losing the execution lease removes execution authority.
I6 — Reconnect requires reconciliation before new exposure.
I7 — Rate-limit controls cannot be bypassed by strategy.
I8 — Permission drift cannot increase authority.
I9 — Exchange metadata drift cannot create unsafe orders.
I10 — Exchange failure cannot silently convert unknown state into success/failure.

## 55. Failure Matrix

| Failure | New Entry | Existing Protection | Required Action |
|---|---|---|---|
| WS disconnect | Deny/Restrict | Continue per policy | Reconnect + reconcile |
| REST outage | Deny/Restrict | Emergency policy | Restore authoritative channel |
| Timeout after mutation | Deny affected path | Continue | Query exchange |
| Unknown order | Deny affected path | Continue | Reconcile |
| Rate limit | Restrict | Higher priority | Backoff |
| Nonce conflict | Deny affected mutation | Continue | Resync |
| Maintenance | Deny | Policy-defined | Wait/reconcile |
| Position mismatch | Freeze/Restrict | Emergency | Reconcile |
| Lease loss | Freeze | Emergency | Fence stale instance |
| Permission drift | Freeze affected scope | Emergency | Verify permissions |
| Contract drift | Deny affected symbol | Existing protection | Refresh metadata |

## 56. Exit Criteria

v4.4.8 passes when:

1. WebSocket lifecycle is resilient.
2. REST failure states are explicit.
3. UNKNOWN is separated from REJECTED.
4. Retry classification works.
5. Order mutation idempotency works.
6. Cancel/fill races are reconciled.
7. Duplicate fills are deduplicated.
8. Rate-limit handling works.
9. Nonce recovery works where applicable.
10. Exchange maintenance is handled.
11. Network partitions fail closed for new exposure.
12. Execution lease/fencing prevents split-brain.
13. Reconnect requires reconciliation.
14. Contract metadata drift is detected.
15. Protection remains higher priority than new entry.
16. Failures integrate with Live Risk Control.
17. Forensic replay captures execution incidents.
18. Chaos and regression suites pass.

## 57. Scope Boundary

v4.4.8 does not define a specific exchange connector implementation.

Exchange-specific adapters must map their own:
- WebSocket protocol;
- REST API;
- order states;
- error codes;
- rate limits;
- nonce/sequence rules;
- contract metadata;
- maintenance signals

into this common resilience contract.

The common engine remains exchange-agnostic.
