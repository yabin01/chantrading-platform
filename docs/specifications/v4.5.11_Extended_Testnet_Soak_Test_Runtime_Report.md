# v4.5.11 — Extended Testnet Soak Test & Runtime Report\n\n## 1. Objective\nv4.5.11 defines the measurement contract for extended Hyperliquid Testnet runs.\nThe goal is to establish operational evidence rather than only unit-test evidence.\n\n## 2. Report Metrics\nThe machine-readable report records:\n- started_at_ms;\n- ended_at_ms;\n- duration_ms;\n- orders;\n- fills;\n- reconnects;\n- recoveries;\n- drift_events;\n- watchdog_events;\n- halted_duration_ms;\n- replay_equivalent.\n\n## 3. Determinism\nThe report is serialized as canonical JSON with sorted keys and compact separators.\nThis makes reports suitable for archival, CI comparison and later audit.\n\n## 4. Soak Test Levels\nRecommended staged runs:\n\n    Level 1 — 30 minutes\n    Level 2 — 2 hours\n    Level 3 — 24 hours\n    Level 4 — 72 hours\n    Level 5 — 7 days\n\nProgression should occur only after the previous level completes without unresolved safety drift.\n\n## 5. Failure Injection\nEach extended run should include controlled scenarios where practical:\n- WebSocket disconnect;\n- reconnect delay;\n- order acknowledgement delay;\n- UNKNOWN order result;\n- duplicate fill delivery;\n- missed fill processing;\n- position drift;\n- replay verification failure;\n- watchdog timeout.\n\nFailure injection must prove that the runtime freezes or halts rather than creating unverified risk.\n\n## 6. Replay Equivalence\nAt the end of a run, persisted events should be replayed into a clean State Store.\nThe reconstructed execution state must match the recorded final state.\n\nRequired report field:\n\n    replay_equivalent = true\n\nfor a passing run.\n\n## 7. Suggested Pass Conditions\nA run should not be considered clean when any of the following remains unresolved:\n- reconciliation drift;\n- failed recovery;\n- watchdog halt;\n- unprocessed fill;\n- unexplained position difference;\n- replay mismatch;\n- unknown live order without authoritative resolution.\n\nTransient injected failures may be present in the report when they were correctly contained and recovered.\n\n## 8. Operational Evidence\nFor each soak run preserve:\n- runtime report JSON;\n- event log;\n- reconciliation results;\n- recovery transitions;\n- watchdog events;\n- final position snapshot;\n- replay verification result.\n\nThese artifacts provide the evidence chain for later Testnet certification.\n\n## 9. Acceptance Criteria\nv4.5.11 is accepted when:\n1. a run can be started and ended with deterministic timestamps;\n2. metrics are machine-readable;\n3. injected failures are observable;\n4. safety freezes/halt are observable;\n5. replay equivalence is explicitly reported;\n6. unresolved drift prevents a clean pass;\n7. reports can be archived and compared across runs.\n\n## 10. Next Step\nv4.5.12 should add the executable soak-test runner, event persistence integration and a Testnet certification checklist.\n\n## 11. Production Boundary\nv4.5.11 remains Testnet-only. Passing a soak test is evidence of runtime behavior, not proof of profitability or authorization for Mainnet deployment.
