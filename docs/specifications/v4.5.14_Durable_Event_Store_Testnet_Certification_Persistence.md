# v4.5.14 — Durable Event Store & Testnet Certification Persistence\n\n## 1. Objective\nv4.5.14 adds a durable SQLite-backed append-only runtime Event Store and a persistent Runtime Event Bus.\n\nThe purpose is to survive process restart while preserving deterministic event order and event idempotency.\n\n## 2. Persistence Path\n\n    Runtime Event\n         ↓\n    Persistent Event Bus\n         ↓\n    SQLite Event Store\n         ↓\n    durable event log\n         ↓\n    Replay / Soak Report\n\n## 3. Append-First Rule\nAn event is persisted before it is dispatched to in-process subscribers.\nIf persistence fails, subscribers must not receive the event through this boundary.\nThis prevents a metric or State Store consumer from observing an event that was never durably recorded.\n\n## 4. Idempotency\nEach runtime event receives a deterministic SHA-256 event ID derived from its canonical name, timestamp and payload.\nA duplicate event ID is ignored by the durable store and is not dispatched a second time.\n\n## 5. Ordering\nThe SQLite sequence column provides durable append order.\nReplay consumers must iterate by sequence rather than by wall-clock arrival order.\n\n## 6. Restart Behavior\nA new process can reopen the same SQLite database and enumerate the existing event history.\nThis provides the minimum persistence foundation required for a crash/restart soak test.\n\n## 7. Testnet Certification Artifact Chain\nFor a certification run, preserve:\n\n    event_store.db\n    runtime_report.json\n    final_position_snapshot.json\n    reconciliation_report.json\n    replay_result.json\n\nThe exact production storage backend can later be replaced without changing the Runtime Event contract.\n\n## 8. Safety Boundary\nThe Event Store is persistence infrastructure only.\nIt cannot:\n- submit orders;\n- cancel orders;\n- resume trading;\n- bypass Recovery;\n- bypass Reconciliation.\n\n## 9. Acceptance Criteria\n1. events survive process reopen;\n2. duplicate event IDs are idempotent;\n3. durable sequence order is deterministic;\n4. persistence occurs before event dispatch;\n5. replay can enumerate the durable event history;\n6. the runtime safety hierarchy remains unchanged.\n\n## 10. Next Step\nv4.5.15 should add a complete Testnet Certification Runner that combines:\n- Persistent Event Bus;\n- Runtime Watchdog;\n- Recovery Orchestrator;\n- Soak Runner;\n- final venue snapshot;\n- replay verification;\n- certification report.\n\n## 11. Production Boundary\nv4.5.14 remains Testnet-only. Durable persistence does not imply that the strategy is profitable or that Mainnet deployment is authorized.
