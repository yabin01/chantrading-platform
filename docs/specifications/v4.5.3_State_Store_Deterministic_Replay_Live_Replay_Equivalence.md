# v4.5.3 — State Store Append, Deterministic Replay & Live/Replay Equivalence

## 1. Objective

v4.5.3 connects canonical market events to a deterministic in-memory State Store boundary and establishes the first explicit Live-vs-Replay equivalence test.

## 2. Event Store Contract

Each accepted event receives a monotonically increasing sequence number:

    0, 1, 2, ...

The stored record contains:
- sequence;
- event_id;
- timestamp;
- payload.

Event IDs remain immutable after append.

## 3. Append Invariants

The State Store rejects:
- duplicate event IDs;
- timestamps that move backwards relative to the append sequence.

This prevents silent corruption of the deterministic replay log.

## 4. Replay Contract

Replay is a pure ordered reduction:

    state_0
      ↓ event_0
    state_1
      ↓ event_1
    state_2
      ...
      ↓ event_n
    state_n

The reducer must not depend on wall-clock time, network responses, random values or mutable external state.

## 5. Live vs Replay Equivalence

The certification property is:

    reduce(initial, live_events)
      ==
    replay(store(live_events), initial)

The same ordered canonical event sequence must therefore produce the same resulting state.

## 6. Why This Matters for ChanLun

ChanLun structures are stateful. A single difference in event order or missing mutation can propagate through:

    分型 → 笔 → 线段 → 中枢 → 走势 → 背驰 → Decision

Replay equivalence gives us a way to distinguish market-data problems from deterministic engine problems.

## 7. Current Implementation

Added:
- DeterministicEventStore;
- StoredEvent sequence numbers;
- duplicate rejection;
- backward-timestamp rejection;
- deterministic replay;
- standalone replay_events helper;
- live/replay equivalence unit test.

## 8. Current Limitation

The current implementation is an explicit deterministic boundary, not yet the final durable production database implementation.

The next integration must connect it to the project's existing State Store / Event Schema persistence layer without changing event semantics.

## 9. Acceptance Criteria

v4.5.3 is accepted when:
1. every canonical event has one deterministic identity;
2. append order is deterministic;
3. duplicates cannot mutate state twice;
4. replay order is deterministic;
5. identical input produces identical output;
6. live and replay results are equal for the same event sequence.

## 10. Next Step

The order path must remain:

    Decision → Risk → Order Request → Signing Gateway → Testnet → Order Lifecycle → Fill → Reconciliation
