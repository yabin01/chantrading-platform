# v4.5.5 — Hyperliquid Testnet Order Submission & Signing Gateway Integration

## 1. Objective

v4.5.5 establishes the real Testnet order-submission boundary while keeping signing credentials outside the trading application.

Hyperliquid's exchange API accepts order actions through its exchange endpoint, while order status can be checked through the Info endpoint. citeturn0search0turn0search1

## 2. Architecture

       ↓

       ↓

The adapter does not own private-key material.

## 3. Order Mapping

The mapping layer converts the internal TestnetOrderRequest into a Hyperliquid-style order action containing:
- asset identifier;
- buy/sell side;
- size;
- price;
- reduce-only flag;
- order type / time-in-force.

The internal request remains the source of truth before signing.

## 4. Signing Boundary

SigningGateway is an explicit dependency.

The implementation intentionally contains no private-key field and no hard-coded signer.

A production implementation may inject an isolated signer, API-wallet signer, MPC signer or HSM-backed signer according to the project's security architecture.

## 5. Client Order Identity

The existing client_order_id remains attached to the local lifecycle request and is passed to the signer boundary for correlation.

After submission, authoritative order state must be resolved from venue acknowledgements and order-status/fill data.

## 6. UNKNOWN Rule

A submission timeout does not prove rejection.

Therefore:

    submit
      ↓
    timeout
      ↓
    UNKNOWN
      ↓
    orderStatus / openOrders / userFills reconciliation

A second order must not be submitted merely because the HTTP/WebSocket request timed out.

Hyperliquid exposes orderStatus by order ID or client order ID and provides user fills through the Info endpoint, supporting this recovery pattern. citeturn0search0

## 7. Testnet Only

v4.5.5 is an integration boundary for Testnet.

The submitter must be constructed with a Testnet exchange transport. Mainnet endpoint selection belongs to a separately authorized production runtime and is not enabled here.

## 8. Rate-Limit Safety

The implementation must avoid aggressive retry loops. Hyperliquid documents an aggregated REST request limit of 1200 weighted requests per minute per IP, with exchange requests contributing weight based on batch length. citeturn0search2

UNKNOWN recovery therefore requires bounded polling/backoff and reconciliation rather than immediate repeated submissions.

## 9. Reduce-Only

reduce_only is explicitly carried from the internal request into the venue order action.

It is not inferred after signing.

## 10. Tests

Added tests for:
- order action mapping;
- side mapping;
- quantity mapping;
- reduce-only preservation;
- injected signing gateway;
- absence of private-key ownership in the submitter.

## 11. Current Limitation

This version creates the exact submission boundary and validates mapping, but does not embed a real private key or automatically submit against a live account from the repository test suite.

Live Testnet credentials must be supplied externally at deployment time.
