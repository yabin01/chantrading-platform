# v4.5.6 — Hyperliquid Testnet Order Updates, Fills & Position Ingestion

## 1. Objective

v4.5.6 closes the first feedback loop from Hyperliquid Testnet back into ChanTrading.

The adapter normalizes three venue facts:

- orderUpdates;
- userFills;
- clearinghouseState / position state.

The adapter does not decide whether an order is valid. It reports authoritative venue observations to the existing lifecycle and reconciliation layers.

## 2. Feedback Architecture

    Testnet Exchange
          │
          ├── orderUpdates
          ├── userFills
          └── clearinghouseState
                    │
                    ▼
             Venue Normalizer
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Order      Fill     Position
       Update    Update     Update
          │         │         │
          └─────────┼─────────┘
                    ▼
             Reconciliation
                    │
                    ▼
               State Store

## 3. Order Update

Normalized order state contains:

- client_order_id;
- exchange_order_id;
- status;
- symbol;
- filled_quantity.

Client order identity is retained whenever the venue supplies it.

Exchange order ID is retained as the authoritative venue correlation key.

## 4. Fill Update

A FillUpdate contains:

- exchange_order_id;
- symbol;
- side;
- quantity;
- price;
- timestamp.

A fill is an execution fact, not an order-state guess.

Therefore fills must be processed idempotently by the downstream reconciliation layer.

## 5. Position Update

PositionUpdate contains:

- symbol;
- size;
- entry_price;
- timestamp.

Position state is treated as authoritative venue state for reconciliation.

The execution engine must not infer final position solely from locally submitted orders.

## 6. UNKNOWN Recovery

The intended recovery path is:

    local order = UNKNOWN
            ↓
      orderUpdates
            ↓
      userFills
            ↓
      clearinghouseState
            ↓
       Reconciliation
            ↓
      local state resolved

If an order update is missing but fills or authoritative position state prove execution, the reconciliation layer must resolve the local state from venue evidence.

## 7. Idempotency

v4.5.6 parsers only normalize venue messages.

The downstream Event Schema must assign deterministic event IDs before State Store mutation.

Duplicate order updates and fills must therefore be safe to receive more than once.

## 8. Symbol Scope

The current implementation accepts the venue's symbol/coin field without converting it into a different trading symbol.

A later canonical symbol registry should perform:

    venue symbol → canonical instrument ID

This prevents venue-specific naming from leaking into ChanLun core logic.

## 9. Tests

Added tests for:

- order update normalization;
- client-order-ID extraction;
- exchange-order-ID extraction;
- filled quantity extraction;
- fill normalization;
- position normalization.

## 10. Current Limitation

v4.5.6 implements normalization only.

It does not yet provide:

- persistent fill deduplication;
- complete position reconciliation;
- websocket subscription management for all three channels;
- recovery snapshot orchestration.

Those belong to the next reconciliation layer.

## 11. Next Step

v4.5.7 should implement:

    Order State
       +
    Fill Ledger
       +
    Position Snapshot
       ↓
    Reconciliation Engine
       ↓
    Consistent Local State

The acceptance target is that every Testnet execution can be reconciled against authoritative venue facts.

## 12. Production Boundary

v4.5.6 remains Testnet infrastructure and does not authorize Mainnet execution.
