# v4.5.7 — Hyperliquid Testnet Reconciliation Engine\n\n## 1. Objective\nv4.5.7 defines the reconciliation boundary between local execution state and authoritative Hyperliquid Testnet state.\nThe purpose is to detect execution drift before the runtime is allowed to continue trading.\n\n## 2. Reconciliation Inputs\nThe engine compares:\n- local orders vs venue orders;\n- processed fill IDs vs venue fills;\n- local position size vs venue position size.\nThe venue snapshot is treated as external authoritative evidence.\n\n## 3. Drift Types\nThe implementation defines:\n- MISSING_LOCAL_ORDER\n- MISSING_VENUE_ORDER\n- UNPROCESSED_FILL\n- DUPLICATE_FILL\n- POSITION_DRIFT\n- LIFECYCLE_DRIFT\n\nEvery drift is represented as a structured ReconciliationDrift.\n\n## 4. Order Reconciliation\nOrders are correlated primarily by exchange order ID (oid).\nThe engine detects both directions of mismatch:\nlocal order exists / venue order missing → MISSING_VENUE_ORDER\nvenue order exists / local order missing → MISSING_LOCAL_ORDER\nNeither condition is silently repaired.\n\n## 5. Fill Reconciliation\nFill identity prefers the venue trade ID (tid).\nIf no trade ID is available, the implementation falls back to a deterministic composite key: hash + oid + time.\nThe engine detects duplicate venue fills and fills that have not been processed locally.\n\n## 6. Position Reconciliation\nLocal and venue position sizes are compared using Decimal arithmetic.\nA configurable tolerance is supported. Default tolerance is zero.\n\n## 7. Reconciliation Result\nThe engine returns ReconciliationReport with consistent and structured drifts.\nNo drift means the local execution state is consistent with the supplied venue snapshot.\nAny drift means the local state is not certified.\n\n## 8. Trading Safety Gate\nThe runtime must treat a non-consistent reconciliation report as a trading safety event:\nDRIFT_DETECTED → stop new execution → obtain authoritative snapshot → reconcile again → CONSISTENT → resume.\nThe system must not continue opening new risk while reconciliation is unresolved.\n\n## 9. UNKNOWN Order Recovery\nAn UNKNOWN order is resolved through authoritative venue evidence rather than local assumptions.\nRecommended sequence: UNKNOWN → venue order lookup + fills lookup + position snapshot → ReconciliationEngine → resolved or drift.\nA timeout is therefore not interpreted as rejection.\n\n## 10. Idempotency\nReconciliation is observational. It does not itself mutate orders or positions.\nMutation is performed only after the reconciliation result has been accepted by the state-management layer.\nThis separation allows reconciliation to be repeated safely.\n\n## 11. Tests\nTests cover missing venue orders, missing local orders, unprocessed fills, duplicate fills, position drift and fully consistent state.\n\n## 12. Acceptance Criteria\n1. order discrepancies are detected in both directions;\n2. fill duplicates are detectable;\n3. unprocessed fills are detectable;\n4. position drift is detectable;\n5. reconciliation output is deterministic;\n6. unresolved drift blocks new trading;\n7. repeated reconciliation does not itself mutate execution state.\n\n## 13. Next Step\nv4.5.8 should implement recovery orchestration:\ndisconnect / restart / drift → freeze trading → authoritative snapshot → rebuild local execution state → reconcile → replay verification → resume only if consistent.\n\n## 14. Production Boundary\nv4.5.7 remains Testnet infrastructure and does not authorize Mainnet execution.
